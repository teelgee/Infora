The app builder — the stepped flow

Where a person defines an app step by step, with an agent beside them that asks the questions the wall needs answered. Two moments are drawn: the table step, where the agent asks whether the table holds contractual data and so needs an acceptance step; and the interface step, where it asks who may open each screen. The steps are in the owner's own words. This is the fourth tool on the Tools surface, and nothing here exists yet.

Pending — this screen does not exist yet. Drawn for T-438 against ADR-0056 (§1, §2a–§2b, §5, §10–§11, §13c–d) and ADR-0057. Built by T-442; photographed into the walkthrough's app-builder tool section by T-447, at which point this file is deleted (docs/design/README.md). Pattern it starts from (T-437, app-builder-ui-review.md): the steps borrow Retool Database's field editor for the table step, Lovable's chat-plus-live-preview for the interface step, Lovable's Jobs view for the schedule, and Nomic's three questions (what it does, what files it needs, what it produces) for the analysis step; the agent's placement follows Infora's own document creator; no product has a pattern for the acceptance question or for who-may-open-each-screen, so those are drawn fresh (§5 of the review). Every ruling below must reach an ADR addendum first. The tables

Each table is a set of columns people fill in, one row at a time. Every row remembers which organisation and which person entered it, and is read by that organisation and by Trentmoor Energy — nobody else. That is not a setting; it is how every app table works.

Does this table hold contractual data? A figure that triggers a payment, discharges a planning condition, or that Trentmoor Energy will rely on as its record. If it does, the table needs an acceptance step.
Yes — add an acceptance step
A row is a draft until its organisation submits it; Trentmoor Energy then accepts or rejects it. Acceptance is the moment the row changes hands: it becomes Trentmoor Energy's record and is never edited or deleted in place — a correction arrives as a new row that supersedes it.
No — rows never change hands
Each organisation's rows stay its own material. Trentmoor Energy can read them; nobody accepts them.

Notes — what is settled, and what rides here as an open fork
Settled (ADR-0056). The steps carry the owner's own list — data connections, the interface, how often it runs, analysis and prompts — with the table step added because everything else refers to the tables. The agent asks the three questions §2b names: contractual data (step 2), who opens each screen (step 4), what a run may touch (step 6). Rows are stamped with organisation and person; an accepted row never changes in place; screens run in the browser as the viewer (§11).
Fork — step order. Drawn: what the app is → tables → connections → interface → schedule → analysis → check and open. Reasoning: a screen cannot be described before its table exists, and the run's "what may it touch" question needs both. The owner's own list put connections first; the drawing puts tables ahead of them because the returns app has none. T-438 closes only when the owner confirms the order.
Fork — where the app's scope lives. Drawn in step 1, as "who the app is open to" (the ADR-0036 ladder), with per-screen "who may open it" in step 4 narrowing inside it. The alternative is one question in step 4 only. Drawn this way because §1 makes scope a property of the instance at creation, and because a builder who sets it first sees the agent's later questions in terms of it.
Fork — the agent as a pane, or inline. Drawn as a separate pane beside the steps, on the document creator's "Ask the agent" precedent and the design rule that a tool acting on a thing is its own card. The alternative is a callout inside each step. The pane keeps the conversation continuous across steps; the callout puts the question exactly where the setting is. Both keep the choice itself in the form, never only in the chat.
Fork — a seventh "check and open" step. Not in the owner's list. Drawn because a definition read back in one place before it opens to three organisations is where a builder catches "the dashboard is open to everyone" — and because "save as a playbook" needs a home. Could instead be the header's own buttons.
Fork — steps with an agent beside them, or a chat that fills the steps in. The research found both Retool's new builder and Lovable are chat-first with a live preview, and neither has a stepped flow (review §1c, F1). Drawn with the steps as the spine because ADR-0056 §2b says the builder is walked through the wall's choices, and a form records a choice where a chat only discusses it. The alternative keeps the same steps as a checklist the conversation completes. The owner's call.
Step 7 assumes a proposal not yet ruled. "Check and open" is drawn as a publish act — the app's people see the published definition, not the builder's working edits — which is the review's PROPOSED P1 (Retool's draft-versus-live releases). If the owner declines P1, step 7 is a read-back only and saving in any step is live at once.
Connections and the schedule are shown, not hidden. Step 3 declares a requirement that cannot be filled until deployment (ADR-0056 §13c, ADR-0057); step 5 stores a schedule that is honoured when a clock exists (§13d), with "Run now" until then. Drawn present and honest rather than absent, so the built flow matches the ruled shape and the owner's test walk meets the real steps.
Reference tables. Offered by the agent in step 2 as a lookup list the firm fills itself. Per §10 as amended 2026-09-06, a playbook carries the table's shape and never its rows — the agent's wording says so.
Not drawn, on purpose. The Tools card for the builder, the list of a project's apps, the playbook shelf in the workspace, the share-a-table and defunct-app dialogs — all follow the kit and T-438's entry excludes them. The agent-written screens themselves are drawing 2.
Icons and copy. Rail glyphs stand in for the Lucide icons the shell uses (a mockup limitation, not a proposal). Every noun is `CONTEXT.md`'s: app, app table, scope of an app, playbook, connection. "Contractor" is the owner's word for a submitting organisation; the seeded world has consultants, cast as contractors here.
