# ADR-0018 - Ethical walls are the standing posture, not an exception: organisations are isolated by default, two things are private even from the owner, and only the owner's sharing opens visibility

**Status:** Accepted. Refines ADR-0015 and ADR-0016. Refined in Session 3: the private floor splits — org context (with the workspace sandbox) stays absolute, while a private *project* sandbox is owner-overridable (audited, exceptional), and the inbound question (what may *enter* the floor by distillation) is added by the Session 3 confidentiality work. **Further refined 2026-07-06 (surfaces alignment session):** the workspace sandbox is per-user — each user holds a **personal sandbox** within the organisation's workspace. The floor is unchanged: nothing in the workspace is reachable by another organisation or any project owner. Whether an org admin can reach a user's personal sandbox is a small open item (grill tracker), to settle with the sandbox drawer. **Also ruled 2026-07-06:** the wall's treatment of agent-execution records follows the same working-area/record line — work-item-bound Runs are project record (owner-readable in full); ad-hoc Runs are org-private with the same audited owner override as a private project sandbox (recorded in ADR-0028's status note).

**Context:** The glossary defined an ethical wall as "enforced isolation so members cannot see each other's private contributions," which is both vague and, after ADR-0007 and ADR-0014, wrong in detail, because an open review round shows comments across organisations. We also flipped the library to default-deny (ADR-0016). So the wall needs stating precisely: what is isolated, what is private even from the owner, and what overrides the isolation.

**Decision:** Isolation between organisations is the default, not a feature switched on. It has three parts.

A private floor: an organisation's org context — precedents, custom workflows, private knowledge, and its workspace sandbox — is never shared, not even with a project owner, and no grant can expose it. A private *project* sandbox is private by default too, but because it is hosted on the owner's project the project owner holds an audited override to reach it when necessary; this is exceptional, not the standing state, and never extends beyond the owner's own project into the organisation's workspace or org context (refined in Session 3).

Default-deny project data: the library is default-deny per deliverable per organisation (ADR-0016); an organisation sees only its own deliverables and those the owner has shared with it. The deliverable plan and status, and shared sandboxes the organisation is in, are visible because they are shared, not because the wall is off.

The overrides, all deliberate and owner-driven: the owner shares a deliverable with an organisation; the owner adds an organisation to a shared sandbox; the owner appoints review access, and within an open review round comments are visible across the organisations in the review group (ADR-0014), the one place cross-organisation comment visibility is live. Nothing else crosses.

Because isolation is the default, competing organisations on one project need no special wall: they do not see each other's work unless the owner shares it.

**Consequences:** The wall is a standing guarantee rather than a configured state, which is the defensible posture for a multi-organisation platform. The owner is the single point that opens any cross-organisation visibility, so the audit of who-can-see-what reduces to the owner's sharing actions plus review appointments. The org-context floor sits outside even the owner's reach, which is what lets a consultant keep private IP in its own workspace without risk; a private project sandbox, by contrast, is owner-overridable, so truly private IP belongs in the workspace, not in a sandbox hosted on the owner's project (refined in Session 3). Supersedes the loose glossary line. Builds on ADR-0011, ADR-0014, ADR-0015 and ADR-0016.
