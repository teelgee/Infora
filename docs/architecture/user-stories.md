# Document management - user stories

Five stories built from the document management ADRs (0001-0012, with the later refinements 0032–0052 where a beat names them), using a Routewide EIA Scoping Method Statement for Land Quality as the worked example. Three owner-side stories open it — the plan decides first, and the owner decided what the plan records; then the consultant who produces the chapter, and the client lead reviewer who reviews and accepts it. All run on a project in record configuration, where Infora holds the controlled record. A beat that is ruled but not yet built says so in place *(italics, naming its ticket or question)* — the same designed-not-surfaced boundary [the walkthrough](user-stories-walkthrough.html) draws with its gap cards.

---

## The owner: deciding what the plan records

*As the project owner's super user, I want to define the project's deliverable schema before any organisation plans a deliverable, so that every reference is generated rather than invented and every organisation's plan speaks the same language.*

Before anyone plans a deliverable, I define what a deliverable row *is* on this project: the naming scheme that will generate each coded reference, and the attribute fields — title, discipline, and the rest — that every plan row carries. If my consultancies already keep their schema in a spreadsheet, I import it rather than retype it; the parsed fields land in the editing table for me to check before I save. And because teams draft their deliverables lists in Excel before a super user touches the plan, the schema exports as a fillable template whose columns are exactly these fields — what comes back later arrives as a batch of plan rows, each reference generated by the naming scheme at the moment its row is created, never drafted in a spreadsheet. I set one more thing on this screen: the project's default review period, ten working days, which every round inherits and a lead author may adjust for a particular submission. It sits beside the schema rather than in it — it is project configuration, not an attribute of a deliverable, and as a schema field it would arrive as a column in the exported template that nobody should be filling in.

*Decisions exercised: the plan decides first and the reference is generated, never invented (0008); schema definition and import as the owner super-user's act (T-156, T-188, T-337); the template export and batch import (2026-08-09 session, component 5); the project's default review period, beside the schema and not in it (0005 addendum, 2026-08-19 session).*

## The owner: deciding what "accepted" means, and what the AI may rely on

*As the project owner's super user, I want to define the project's acceptance codes and say which of them admit a deliverable to the AI's reach, so that "accepted" means what this project means by it, and the AI never answers from something we have not actually agreed.*

The scheme is not blank when I arrive. The project was created with a copy of the ISO 19650 code set — `S0` to `S5` for work in progress and sharing, `A1, An…` for what is published and contractual — and because it is a copy, nothing I do here touches another project. I check the labels first: this client says *approve* where the default says *accept*, so I change the word and only the word, because the state underneath is fixed and everything downstream keys on what happened rather than on what we call it. Then the two properties that decide what a code *does*: whether it ends the cycle, which is what makes it an accepting code at all, and whether it is **contractual** — because that is what issues the C revision, and it is the whole difference between *we have agreed this* and *we have agreed most of this, with comments*.

Beside them is the column I came for: whether a deliverable accepted under this code enters the AI's reach. It arrives set the way the revision column implies — contractual codes in, preliminary ones out — and most projects will never touch it. But I have to be able to, because the standard itself leaves the meaning of each published code to my project's information standard: `A4` means suitable for construction here only because we said so, and whether that grounds an answer is therefore my decision and not the platform's. I can see the consequence before I make it, because each row tells me how many live deliverables currently carry that code — turning one off is not a checkbox, it reads as *this will exclude forty-one deliverables from AI answers*, and I would rather know that now than meet it later as an answer that was quietly thin. There are things I cannot configure and the screen says so rather than letting me discover it: a deliverable that has been **superseded, withdrawn or rejected never feeds the AI**, whatever code got it there. That rule is the platform's, not my project's, which is why I can change this scheme without worrying I have opened a route back to something we withdrew.

What I change here is recorded the way a rails change is — who, when and why — because I am deciding what the AI may rely on across a whole project, not adjusting my own view. And a code that has been used is never redefined: if it is wrong I retire it and add its replacement, so a deliverable coded last year still reads as what it meant last year. I come back rarely, and usually because a producing organisation has asked for a code the scheme does not carry — the same negotiation as the naming scheme, settled at the level of the scheme rather than per deliverable.

*Decisions exercised: acceptance coding, the per-project copied scheme and retire-never-redefine (0003, and its 2026-08-27 amendment adding `is_contractual` and `grounds`); the 2021 UK National Annex as the seeded set and its stage-agnostic published codes ([iso-19650.md](../reference/iso-19650.md)); the contractual revision issued on acceptance (0041); library membership no longer sufficient for grounding (0011 rider, 0013 §6); configuration that changes what the AI may rely on is audited like a rails change (0030).*

## The owner and the consultant: ending a deliverable that is no longer current

*As the project owner, I want to stop the AI relying on a deliverable that has been overtaken or found wanting; as the consultant who produced it, I want to propose that myself and to be told when it happens.*

**The owner.** A consultant's drainage study sits in my library, accepted and live, and a newer study — a different document, not a new revision of this one — has overtaken it. I record that as a link between the two: the consultant proposes it or I do, and my confirmation is what makes it live. From that moment the old study reads as superseded, and the AI stops answering from it. A second case has no such link to draw: a study we now understand to be wrong, with nothing replacing it. I withdraw it, and I have to say why — the reason is not optional, because a deliverable that stops being relied on without an explanation is a decision nobody can audit. In neither case does the document leave the library or become unreadable; it stops being current, which is a different thing.

**The consultant.** My firm produced that study, and I find out because Infora tells me — not the reason, which is not the sort of thing that belongs in an email leaving the platform, but the fact and a link. *(Ruled, not built: the notification itself is the notifications slice — `T-329`–`T-332`. Everything else in this story is built (T-383–T-391); until that slice lands the fact reaches the producing organisation on the Documents screen and in the plan, where the withdrawal and its reason are read, rather than by a pointer that arrives.)* When I follow it I can read why, because the reason is visible to anyone who can see the deliverable it is about, and my firm authored it. If I think the owner is wrong I have somewhere to go: the withdrawal is reversible by the party that made it. What I cannot do is quietly restore it myself, which the platform used to allow — a document the owner has withdrawn and the consultant has restored, with neither act recording the other, is a disagreement the record cannot show.

**And either of us can still use it deliberately.** Comparing the old assessment against the new one is ordinary work. I pin the superseded study to my question, the answer comes back marked as drawing on something I supplied and carrying the withdrawal reason, and nothing about it enters the shared record as a citation. What ended is the AI reaching for it silently — not anyone's ability to reach for it on purpose.

*Decisions exercised: record state, the publication boundary and the reason's visibility (0013, 2026-08-27 amendment, closing `Q-036`); supersession as a confirmed edge (0045 amendment); the producing organisation notified by pointer and never content (0049 amendment); the attached source as the deliberate path (0022); nothing deleted, currency by state (0013).*

## The consultant: producing and getting a chapter accepted

*As an environmental consultant at the appointed consultancy, I want to draft my Land Quality chapter, put it through review, and resolve the client's comments, so that the chapter is accepted as a controlled deliverable without me ever maintaining a separate review spreadsheet or chasing a document controller.*

When the project was set up, the team agreed the schedule of deliverables, and my Land Quality chapter already exists as a row in the deliverable plan. Its reference was generated from the project's naming rules the moment the row was created, its reviewers are named on it, and its status reads not-yet-produced. I did not have to invent a name or decide who reviews it; that was settled in the plan.

The sandbox I draft in was structured before drafting began. Our super user laid out the folder tree — by hand, or by asking the built-in assistant for a structure based on our disciplines and sub-areas, then editing and confirming what it proposed — and on some projects the sandbox is locked to the plan itself: a folder per discipline, a working folder per deliverable, appearing as the plan rows are created and following them if they are retitled. Either way I work within the structure, and filing my draft in its deliverable's folder means that when I bind it, the right container is already selected — I confirm the act on a card that shows the reference and metadata the draft is about to wear; nothing binds silently.

I draft in the sandbox. As I write in Word, the drafting assistant grounds on the project library, the curated set of accepted material the owner trusts, so the text it helps me produce is anchored to the project's real positions, not to whatever half-finished files happen to be lying around. My messy working drafts stay in the sandbox and never leak into anyone's answers. Once bound, my draft wears its plan row's title and metadata by reference — if the title needs to change, that happens on the plan row, and it follows through everywhere.

Before it goes anywhere, a colleague runs the QA checker over the draft. It is one of the standard tools, and it is also on the editor's own toolbar — the same launcher either way, with the draft already chosen when I start from the editor. I pick how hard to look, and before anything is spent I am shown the plan: how the run will be broken up, roughly what it will cost, and exactly what it will and will not cover. Nothing about that plan is the AI's choice; it is worked out in ordinary code, so the same draft produces the same plan tomorrow. If our house style is too long to sit alongside a section, the run is split into two passes over that section rather than quietly dropping half the rules, and the plan says so.

What comes back is not a corrected draft. It is a list of findings, each one anchored into a paragraph, saying what is wrong and what it rests on — a passage of the project record, cited; a clause of the project's style guide or of our own drafting manual, quoted verbatim and never dressed up as a citation. Beside the findings, in the same words the plan used, is a statement of what was actually read, so "nothing found" never means more than it should. I work through them in the draft: the corrections that are the same small change made over and over I take in one click, and the ones where the AI has written new prose I read one at a time. Nothing is applied to my document without me. Anything I leave open stops the draft being promoted, exactly as an open comment thread does.

When the chapter is ready, it goes through our own assurance first. I freeze the draft — a check-out that locks the head — and an internal QA round runs inside our own organisation: the same review cycle the client will later run, but org-private, and its record stays our QA evidence, never crossing the wall. On a project sandbox, promotion requires QA acceptance unless a super user has deliberately turned that off, so what I promote is the QA-accepted frozen version — never the head as it has drifted since QA looked at it.

With QA accepted, I promote into the container that has been waiting for the chapter. Promoting opens a window that reconfirms what is about to happen rather than asking me to compose it: the coded reference and the plan's identity metadata shown and locked, my own authoring metadata there to adjust, the review group listed by name, and the review period prefilled from the project's default. I can change the reviewers here — the lead reviewer included — and I can change the period for this round; I cannot touch the reference or the identity fields, because those belong to the plan, which is what stops a window I see on every promotion from becoming a place to get metadata wrong in a hurry. Nothing I do here confers access: naming a reviewer proposes them, and the client's side is still where access begins. The window comes back every time I promote, so at version two — which may be six months later, with half the team moved on — I am looking at the review group as it stands rather than trusting one named at planning. Infora then freezes my draft as an immutable version one, generates the PDF that will be reviewed, and keeps my native Word file in the same container as the source I still own. What promotion does is submit the version, not open the review: the round waits until the lead reviewer has accepted the appointment and acknowledged the submission. From there I see nothing of their review while it is open; that is deliberate.

Some time later the lead reviewer closes the round and the comment set comes to me, and now several of us on the consultant side can work it. I open the live review record, a table where every comment sits against the exact place in my version-one PDF that it refers to, with its code. I work the comments back in the sandbox and prepare version two. For each comment I write a response, and I cannot mark it addressed without pointing at the specific change in the version-two PDF that answers it; the only way out is to say explicitly that no change was made and why. Where my draft had already moved on, I reconcile the rejected points into it by hand rather than letting anything merge silently.

I promote version two, which opens a fresh round, and we repeat until the lead reviewer applies an accepting code. At that point the work item closes, the accepted version becomes the controlled record, and it enters the project library automatically, so from now on it is part of what the project treats as true.

*Decisions exercised: deliverable plan and planned containers (0008); sandbox structure modes and the builder agent (0040); binding as a confirmed act with read-through row metadata (0038); the freeze, the org-private internal QA cycle and the promotion-requires-QA gate (0032); project library grounding (0011); the QA checker's findings — structured, anchored, quotable-but-uncited, never auto-applied (0048) — its run computed in code, splitting rather than dropping, and stating its coverage before and after (0053); immutable versions, one in flight, conscious reconciliation (0002); PDF review with native source retained and mandatory response links (0004); the promotion window, reconfirming the review group and the review period at every promotion, and promotion as a submission the client must receive (0008/0033/0051 addenda, 2026-08-19 session); phased DRR access with no live consultant visibility (0007); anchors carried into the DRR (0006); the assurance cycle and acceptance closing the work item (0005); record configuration (0001).*

## The client lead reviewer: running review and accepting

*As the client's lead reviewer for this chapter, I want my reviewers to mark up the document where they read it, moderate their comments into one position, and decide when it is good enough to accept, so that the review is faster and clearer than an emailed spreadsheet and I stay in control of the contractual decision.*

I was named as lead reviewer on this chapter when the deliverable plan was built, and the consultant reconfirmed that naming when they promoted version one. Before I do anything with the submission I accept the appointment itself — a short, deliberate act that states what I am taking on: I set the authoritative code on each round, only I close a round, and I hold the accepting code that makes this a contractual revision. I can decline it, with a reason, and the deliverable then visibly waits for someone else to be named rather than drifting into a review nobody owns. Because I sit in the client's own organisation, accepting is also the confirmation that admits me, so the appointment and the access are one act; a lead reviewer from outside would need us to confirm them first, and would still accept for themselves. Then I acknowledge the submission, and that is what opens the round. The receipt is mine — or my organisation's super user's, if I am away — and nobody else's, least of all the consultant who sent it. My reviewers and I are the review group; some of us sit in different organisations on the project, which is fine.

I open the version-one PDF in Infora's viewer. My reviewers comment by highlighting the text they mean or dropping a point on the page, and each comment lands in one shared review record that all of us in the group can see as it is written. There is no assembling of separate spreadsheets and no guessing what "page three, paragraph four" refers to, because every comment is pinned to the place it came from. Each reviewer codes their comment on our project's scheme, where a blocking code means it must be addressed before we accept. Any of us can open that record as a table — my reviewers throughout, the consultant's team from the moment a round is issued: every comment in order with its code, its author and its response, closed off by the deliverable code the round concluded with. A further round appends to the same table rather than starting a fresh sheet, so the chapter's whole review history reads in one place. Nothing is ever issued out of it; the table is the record, and it is live.

I moderate in the open. I can edit or amend my reviewers' comments and their codes, resolve duplicates, and shape the group's position before any of it goes back — and there is deliberately no delete, so a duplicate is amended to say so rather than quietly emptied. I can do it only while the round is open: issuing freezes the snapshot, so what the consultant receives is the record as I left it, once, and nothing can be edited behind an issued verdict. There is a target date on the round — ten working days by default, set once for the project and adjustable by the lead author when they promote — but nothing closes the round on a clock *(the reminder nudges and the overdue flag arrive with notifications, Slice V1-N, T-329–T-331)*. I decide when review is complete. When it is, I set the one authoritative code for the deliverable, and mine is the one that counts *(a suggestion derived from the comment codes is designed and unticketed — the walkthrough's gap card records it)*. Closing the round issues the record to the consultant; only then do they see it.

When version two comes back, I do not go hunting for what changed. The consultant's response sits beside each of my comments in the same record, each pointing at the specific change in the version-two PDF that answers it *(the click-through that jumps to the highlighted change is the unbuilt half — the walkthrough cards it)*. My reviewers keep working the record — approving the responses they are satisfied with is designed and not yet surfaced anywhere *(no endpoint, no state; `Q-038`)* — and raise new comments on version two where they need to. When the chapter meets the standard we are paying for, I apply an accepting code, the deliverable is accepted and the work item closes, and the accepted version passes into the project library as trusted project knowledge.

*Decisions exercised: review group appointed in the plan (0008); cross-organisation, live, shared DRR scoped to the review group (0007); in-PDF anchored comments (0004, 0006); two-level configurable acceptance coding with the lead reviewer authoritative (0003); the appointment accepted by the person taking it on, and receipt narrowed to the lead reviewer or the owner's super user (0033/0051 addenda, 2026-08-19 session); human-closed rounds with the review period as a guide, now defaulted and adjustable at promotion (0005 addendum); the DRR readable as one appended table, with nothing issued out of it (0009); one live DRR with response links and internal snapshots on issue (0009); transmittal as an event record (0010); accepted version auto-admitted to the library (0011).*
