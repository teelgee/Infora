# ADR-0051 - A review submission is a gated act: the round opens for review only after the owner organisation acknowledges receipt, so `round_state` gains an initial **`submitted`** state and the submission transmittal carries the acknowledgement record

**Status:** Accepted (owner-ruled 2026-08-06, raised by the Review Surface mockup session). The gate itself is the owner's decision — reviewing the deliverable status page mockup, the owner defined the bar's first state as *"issued to the library **and acknowledged by the owner**"* and confirmed on challenge that this is a real gate, not shorthand. The mechanics — where the state lives, who may fire the acknowledgement, and the sandbox-scope exemption — are Claude's, defended here. Refines **ADR-0005** (the round lifecycle) and **ADR-0014** (DRR visibility and the edit lock); extends **ADR-0035**'s acknowledgement pattern from the issue-for-information path to the review-submission path. References **ADR-0032** (one review workflow at two scopes) and **ADR-0050** (retention of review-cycle metadata).

**Context:** Until now, submitting a version into a review round was one act with immediate effect: the producing organisation's review transmittal froze the snapshot, created the round open, and put the pen with the review group. Nothing recorded the owner *receiving* the submission. That is not how the receiving pattern works in document control practice — ISO 19650's receipt step, which ADR-0035 already adopted for issue-for-information (*"receipt precedes distribution"*), applies equally to receipt into review: the appointing party accepts a deliverable into its review process before reviewers act on it. The gap surfaced the way the board says design gaps should — a surface tried to draw the state and the state was not there.

**Decision:**

**1. `round_state` gains `submitted`, and it is the initial state of a project-scope round.** The producing organisation's submission transmittal creates the round in `submitted`, not `open`. No review comment can be created on a `submitted` round — comment creation is legal only on an `open` round, which turns the gate into a schema-adjacent invariant rather than a UI convention. The full lifecycle reads `submitted → open → issued → responded`, with the cycle's terminals unchanged (ADR-0005: explicit human action, never time).

**2. The acknowledgement is recorded on the round, not the transmittal and not a new table.** The first draft of this decision put the two fields on the submission transmittal — the thing being acknowledged — and the build refused it: **`transmittals` is append-only by database trigger** (`forbid_mutation`, the ADR-0009/0010 record discipline), and weakening that invariant with a carve-out for one pair of columns would trade a load-bearing guarantee for a tidy noun. The record is therefore two fields on the **round** — the acknowledging Participant and the timestamp — set in the same statement that moves it `submitted → open`; the round is the thing the act transitions, is one-to-one with the submission being acknowledged, and is already mutable by design (its `state` is a lifecycle). A migration CHECK binds the pair together. This still mirrors ADR-0035's acknowledgement one level up: organisation-level in effect, a single low-effort accept, audited with who and when. A non-review transmittal's acknowledgement machinery (`deliverable_acknowledgements`, controller/open modes, per-version re-trigger) is not reused here because it keys on the receiving organisation's visibility gate, which is a different consequence; what is reused is the pattern.

**3. Any Participant of the owner organisation may acknowledge.** Receipt into review is a routine coordination act, not a destructive one — it belongs to the owner's document-control function, not the elevated tier. This is ADR-0035's open mode applied to the one organisation that always exists on the review side; if a pilot firm wants a single accountable receiver, the controller-mode narrowing ADR-0035 defines is the natural extension and is deliberately not built until asked for.

**4. Sandbox-scope cycles are exempt: their rounds are created `open`.** ADR-0032's org-private internal cycle crosses no wall and has no owner in the loop — a gate there would make a firm acknowledge its own submission to itself. The exemption is decided by the cycle's scope at round creation, not by configuration.

**5. The status bar reads directly off the states.** The deliverable status page and the review interface (the Review Surface slice) render the same four-state bar: **Submitted** = round `submitted`, awaiting the owner's acknowledgement; **In review** = `open`, pen with the review group; **Responding** = `issued`/`responded`, pen with the authoring team; **Complete** = the cycle's accepting terminal. A non-accepting verdict loops to the next round, whose bar restarts at Submitted — the bar never pretends one pass ends a cycle.

**Personal data:** the acknowledgement stores a named Participant and a timestamp — the same class as the existing acknowledgers row in [personal-data.md](../../build/personal-data.md) (review-cycle metadata, retained by the library owner under ADR-0050); the register's row is extended rather than grown by one.

**Considered and not taken.** *Keeping auto-open* (the status quo) — rejected by the ruling; it records no receipt and leaves the owner's first recorded contact with a submission being the verdict. *Per-reviewer acknowledgement* — receipt is an organisational act (the ADR-0035 §"Considered" reasoning applies unchanged); reviewers already have propose-then-confirm for their own appointment, which is a different question. *A separate acknowledgements table for review submissions* — a table keyed on a row that already exists one-to-one with the act is a join with no second use.

**Cost:** one enum value, two nullable columns on `rounds`, one new API act, and every existing project-scope round fixture learns the extra step. The migration is hand-written per the standing rule, drawn in [data-model.md](../../build/data-model.md) drawer 5's narrative, and lands with ticket T-346.

---

**Addendum (owner-ruled 2026-08-06, same day): confirmed reviewers may also acknowledge.** §3 as first written gave the act to the owner organisation alone. Reviewing the built screen, the owner extended it: **a live, confirmed reviewer of the deliverable may fire the acknowledgement too** — the review group is who actually receives the submission into review, so the group's receipt is as faithful a record as the owner's document-control receipt, and on a project where the lead reviewer is not owner-side, gating on the owner alone would park every round behind an organisation with no stake in that round's pace. The audit fact widens accordingly: the record already stores *who* acknowledged, and the surface states *on whose behalf* (the acknowledger's organisation), so a reviewer-fired receipt reads as exactly what it was. Proposal confers nothing here as everywhere: an unconfirmed reviewer cannot acknowledge (ADR-0033's confirmation boundary holds).
