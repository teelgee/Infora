## Completed sessions

### Session 1 — The grounded corpus vs the working input
*Resolves gaps 1 & 2; finishes parked Q1 (access-resolved grounding).*

**Key questions asked**
- ADR-0011 says the project library is the *sole* grounded corpus; CONTEXT.md says org context and Knowledge feed the working input and are the moat. How do these reconcile?
- Are there distinct input channels — grounded-and-cited project fact vs informing/steering material never cited as project fact? How does generation keep them separate?
- What does the governance rail do differently for each?
- Confirm access-resolved grounding (organisation-scoped, pre-retrieval filter, citations safe by construction).
- Where does distilled Knowledge sit — inside the groundable library, or a separate informing store?

**Answered by**
- **ADR-0021** — the three-channel model (grounded / guiding / informing); the grounding invariant is **privacy** ("only non-private sources may ground"), generalising the corpus rule beyond the library.
- **ADR-0011 (refined)** — "sole grounded corpus" annotated as the project-side case of the privacy rule; the authority corpus added as a second grounded corpus.
- Access-resolved grounding folded into **ADR-0020** and **ADR-0021** (access resolved *before* retrieval).
- Distilled Knowledge settled as a non-citable overlay that cites *through* to a source — but full distillation is Session 4.

### Session 2 — The org and project context split as two stores
*Candidate ADR from the architecture; depends on Session 1.*

**Key questions asked**
- Confirm org and project context as two distinct stores.
- How do they combine into one working input at query time without org context leaking to other members?
- What does each hold; which is access-resolved (project) and which is private-by-construction (org)?
- How does the ground-vs-inform line map onto them?
- Does a third scope — programme context — exist, or is it out of scope?

**Answered by**
- **ADR-0020** — three scoped stores (org, programme, project); org & programme private-by-construction and inform-only, project access-resolved and the grounding store; per-request, per-Participant assembly; no-leak by construction (not a redaction pass). **Programme context was a deliberate third store** (chosen over a two-store recommendation).

### Session 3 — Org context confidentiality and portability across clients ⭐
*Resolved gap 3 (the deepest); the critical pre-code session. Built on Sessions 1 & 2.*

**Key questions asked**
- Org context is portable to every project, but Knowledge is distilled from confidential, client-owned project work. What may and may not be distilled into a firm's portable org context, so a consultant serving competing clients cannot carry one client's confidential positions into another's project?
- Is portability of abstracted know-how only (style, structure, approach) or of concrete project facts — and how is that enforced **at distillation time**, not at query time?
- What happens when private precedent text is baked into a deliverable that is then shared or promoted into the project library?
- How does the moat compound at all without leaking — retrieval vs training vs codified workflows?

**Answered by**
- **ADR-0025 (assembly environment)** — the substrate: every request runs in one environment (a project, or the org's own workspace), and the environment, not the user's identity alone, sets which channels are reachable; the informing channel is portable, everything else fixed; access resolution before retrieval. Defines the "own workspace, no project" case ADR-0020 omitted; separates sandbox-privacy from channel-reachability.
- **ADR-0026 (distillation & egress boundary)** — confidentiality enforced by **two mechanisms**: the environment makes another client's material unreachable elsewhere (structural), and a **destination rule** restricts what may feed portable org context to the firm's own material with client facts stripped (the two filters: ownership of the material, then of the facts within it). Admission is a deliberate, abstracting curation act, never automatic. The moat compounds by **retrieval and codified workflows, never by training on customer data** (per-tenant fine-tune flagged as future-only). The output question resolves by the store being clean-by-construction. Honest limit: defeats automated and accidental leak; deliberate human egress is tracked and audited, not physically prevented.
- **Offshoot — ADR-0027 (thinking vs doing)** — placeholder; the deterministic-by-default principle (LLM compiles a rule into code once, code runs it forever) surfaced as the third, confidentiality-clean improvement path. To be grilled.
- **Refined locked ADRs:** **0018** (private floor splits — org context/workspace sandbox absolute, private *project* sandbox owner-overridable and audited; inbound question added), **0020** & **0021** (programme context may ground/guide its *own* projects, configurably — the rule becomes "a scope may ground its own projects but never outside itself"), **0016** (*visible ≠ distillable*), **0024** (domain-tuned embeddings only on de-identified/non-client data). New glossary terms: **Assembly environment**, **Project artefact**, **workspace sandbox**.

### M1 — Orchestration / run / agent model ⭐ *(done 2026-06-29 → ADR-0028)*
*The one real pre-code gap. Run against Legora's aOS and Anthropic's multi-agent research system as adjacent references.*

**Key questions asked & answered**
- Work item ↔ Run cardinality? → **one Work item, many Runs**; the Run is the immutable per-invocation execution unit, the Work item the persistent unit with its own status state machine. Survives the redraft loop.
- Is a Run the unit for *any* agent execution, including ad-hoc chat? → **yes.** One execution model: every Run has one parent **Conversation** and an **optional Work item** link (chat = no work item; workflow = bound). New term **Conversation**.
- Is the Run/audit record append-only and immutable? → **yes**, mirroring the DRR and ADR-0002; "regulator-defensible" requires it. M1 scoped to the **agent-execution** audit sense only (not document-content tracked-changes, not doc-management versioning, not user-UI actions).
- Run → Step: flat or a sub-agent tree? → **a tree**, and **sub-agents are real from v1** (the main chat agent delegates retrieval to a sub-agent that folds documents into its context). New term **Step**.
- Sub-agent retrieval — through Context or around it? → **through the Context-assembly API (M3) only**, so access-resolution-before-retrieval (ADR-0020/0022) and the ethical wall hold by construction.
- Coded chain or agentic planner? → **coded spine, agentic leaves**: the chain `retrieve → draft → ground-check → cite` is code (guarantees ground-check + cite always run); agentic freedom is confined to retrieval within a step. Legora ships exactly this as its "Workflows" mode (vs the open "Agent" mode) — named as the post-MVP divergence (Work item → Workflow, Conversation → Agent).
- Sequential or parallel sub-agents? → **parallel-capable, isolated** (Anthropic orchestrator-worker; Legora/Tabular-Review fan-out); v1 exercises one. The standalone `cite` step matches Anthropic's separate citation pass.
- What each Step records? → identity/parent, agent + provenance, type, status, timestamps, model+version, token/cost, **plus the access-resolved source set and the rail outcomes** (the two fields that make the trail defensible, not just observable).
- Agent provenance/deployment? → **folded in here** (not a separate ADR): Agent is the first-class actor, Infora-built vs custom(org-built), one environment, rails tighten-only. v1 = Infora-built only.
- Real vs stubbed? → real: the run/step/audit model, the coded chain, retrieve-through-Context, grounded generation (one adapter), ground-check, cite, the retrieval sub-agent, access-resolution, Signal capture. Stubbed: other capabilities, custom agents, fan-out, the Signal sink, multi-model routing.

**Answered by**
- **ADR-0028** — the orchestration/run/agent model. Folds in the first-class Agent concept and discharges the candidate "audit-of-every-action" invariant for the agent-execution case. **New glossary terms: Conversation, Step; Run refined.**

### Slice A — the review drawer / document management design session *(2026-07-18 → ADRs 0032, 0033, 0034)*
*The pre-ticketing design session for Slice A, run drawer-first per the house rule. Alignment drawn live in [diagrams/slice-a-review-model.tldr](../architecture/diagrams/slice-a-review-model.tldr) (agent) and [diagrams/review roles.tldr](../architecture/diagrams/review%20roles.tldr) (owner); benchmarked against the ProjectWise/AssetWise friction map (added to docs/reference this session) and Legora's Editor.*

**Key questions asked & answered**
- Where does internal QA review happen, and is it the same workflow as client review? → **ADR-0032:** one role-agnostic review cycle (authoring side / reviewing side) at two scopes — sandbox (org-private internal formal review; its DRR is the firm's QA evidence, never crossing the wall) and project (the wall-crossing cycle, ADR-0014 unchanged). Internal ceremony is optional, never a system gate.
- What is sandbox versioning? → **ADR-0032:** SharePoint-style *ambient* history (a tool — nothing binds to it) is distinct from the **freeze** ("check out") — promotion's twin at sandbox scope, one Version substrate, head locked while an internal round is open. Promotion takes the head snapshot *or* a QA-accepted frozen version, never a drifted head.
- The cycle's stored shape? → **ADR-0032 + Drawer 5 rebuild:** the cycle is the instance unit (DRR absorbed as its record; terminals accepted / closed-rejected, the latter an explicit audited close by lead author or owner); beneath it Rounds (one open per cycle, schema-enforced), Transmittals, Snapshots, Comments, and the previously unmodelled **Response**. Rejected deliverables stay in the library (`rejected` state), never grounding.
- Who plans, who appoints, who administers? → **ADR-0033:** per-organisation deliverable plans (TIDP) consolidated by the owner (MIDP); appointments as append-only interval grant tables with reviewer propose-then-confirm; the roster visible to all Participants ("the wall hides work, never presence"); org admin + auditable Membership/Participant edges.
- What is a work item? → **ADR-0032 addendum:** the deliverable's work half, 1:1 with its Container by type; status event-driven, never hand-set; per-role click-throughs follow the data links.
- What format is a document? → **ADR-0034:** canonical format follows origin (uploaded = native file; authored = Infora structured text with one-way Word/PowerPoint exports; slides = an authored document kind); renditions stored immutable (docx/xlsx/pptx/pdf; dwg-class deferred); the Slice B add-in serves the native-docx population.
- Acceptance codes + library metadata → per-project `acceptance_code` table (copied at creation, retire-never-redefine, `is_accepting` ends the cycle); Documents-view metadata derived by query, plan extras in `Container.metadata` jsonb.

**Parked from the session:** the sandbox-scope review surface (PDF rendition vs frozen native text — establish the workflow, then the method); mention delivery (T-112 residual); the per-project metadata schema + naming scheme (standing ADR-0008 deferral). **Ticketed and then built the same day: T-113–T-129 all landed 2026-07-18, CI green** — the review cycle is browser-drivable end to end (see the board's Slice A status note for the honest deviations: text-first review reads with the PDF rendition downloadable, the in-PDF anchored viewer as follow-up; ADR-0016 shares landed as data mid-slice at T-119).

### Session B — the producing-side deliverable lifecycle *(2026-07-22 → ADRs 0036, 0038, 0039)*
*Walked as one continuous user story from the perspective of a consultant (Org B) working in a client-owned project (owner Org A), with Org C brought in to probe cross-organisation sharing. Eight beats: set up the TIDP → create the sandbox → create documents → collaborate (team + AI) → internal review → freeze → promote + launch the project cycle → what happens after. Design only (no ticketing this session).*

**Key questions asked & answered**
- Who owns the naming scheme; generate or receive codes? → **Owner-defined, project-wide, but not fixed** (a producer proposes additions, the owner folds them in); the producer **self-generates** each code within the current scheme, cross-org uniqueness on the originator field. Glossary (Deliverable plan) refined; no ADR (refines 0008/0033).
- The sandbox model? → **ADR-0036:** unlimited sandboxes; a broad→narrow participant-scope ladder (multi-org ⊃ single-org ⊃ team ⊃ named users) as strict subset; **live/revocable access** (retiring "sharing set at creation"); **separation by provisioning a narrower sandbox, never walling a shared one** (participant-private); self-serve within one's own org, cross-org shared sandboxes owner-gated (create or propose-then-confirm); "team" not a first-class entity; the single-org sandbox is the default home for TIDP deliverables. Super-user scoping parked (T-133).
- The two document tracks + metadata? → **ADR-0038:** **bound** (linked to a planned container, wears its code, identity locked) vs **unbound** (free working document, may never leave); the distinguishing fact is the `container_id` link alone. **Identity metadata** is plan-owned and read-only on a bound doc; **authoring metadata** accrues in the sandbox and carries on promotion. The lock is a consequence of binding (unbound docs edit all metadata freely). Refines 0008 without reopening "not a metadata gate".
- The binding transition? → **ADR-0038:** a **first-class, audited, one-way event distinct from and prior to promotion** — it links a draft to its planned container (identity locks) as a coordination act ("this draft will become deliverable X"), but the doc stays a live editable sandbox draft and may sit **bound-but-not-promoted** indefinitely. Fired by the producing side; unwound only through the records lifecycle, never by unbinding; does **not** snapshot (promotion does).
- Is attached-source enough for team collaboration? → **No; refined ADR-0022 (note):** one *or several* sources — sandbox file(s), an uploaded PDF, or a web search — persisting across a **Conversation** as a working set. Still never grounds, never cited. What grounds is unchanged.
- Is the document's agent chat private or shared? → **ADR-0039 (the editor is *multiplayer*):** the document's Conversation is a **shared thread scoped to the sandbox participant set** (chat visibility follows document access, like the guidance note). The initial private-chat recommendation was reversed on the build fact that drafting is inline-accept-to-text with no persistent suggestions panel. New glossary term **Multiplayer**.
- How does informing work in a shared thread? → **ADR-0039 (already fixed by 0025/0020/0028, made explicit):** the **informing channel is resolved per-run to the *invoking* participant's org, never pooled by the shared thread** — B's run reaches B's informing, C's run reaches C's, never each other's; run audit internals stay producing-org-private (T-104). A shared thread shares *outputs*, never private steer or run internals.
- Internal review mechanics? → **0032 (refined):** runs in a private *or* shared sandbox; **initiation open to the author or anyone in the team** (vs project-scope, launched by the lead author promoting); the initiator **names the review participants and thereby sets DRR access** (grain = the cycle's named participants ⊆ sandbox set); **freeze is automatic at initiation**, head unlocks at round close. The internal DRR is participant-private and never crosses the wall (in a shared sandbox, private to the B+C set, invisible to client A).
- The terminal verb? → **Confirmed (0003):** a **configurable label over a fixed state** — state is `accepted`/`closed-rejected`, the word ("accept"/"approve") is per-project and the internal gate may label differently from the client gate; behaviour keys off state (`is_accepting`), never the label.

**Side-quest (owner-initiated) — the JR / "defensibility" reframe.** The owner challenged the "judicial review" framing baked into the docs. Resolved: (1) **cross-org access (the ethical wall)** is a **confidentiality/commercial/IP** matter — the risk is competitive leakage between consultants sharing a project — *not* a JR matter; (2) a JR / legal challenge tests the soundness of the human **decision**, not how a document was generated; (3) the **audit trail is a safeguard for the human checker/reviewer** (visibility into what the system did — which documents it drew on) and producer-side evidence of grounding, **not the object a court reviews**. Infora *assists*; humans check, edit and sign off, and the consultant carries the professional liability (T-104). Edits: ADR-0035's risk restated with the Org B/Org C example (JR removed); component-3-governance.md's headline and §39 reframed; overview:115 left (legitimate "defensible autonomy" sense). Recorded in the audit-liability-model memory.

**Parked / adjacent open items:** the super-user / elevated tier (T-133, unchanged); a deliberate *co-driven* single agent session (two users steering one run in real time — a future affordance flagged in ADR-0039, not designed); whether an org admin can reach a user's personal sandbox (unchanged, sandbox-drawer item); the sandbox-scope review rendition (PDF vs frozen native text — still parked, ADR-0032). **Ticketed 2026-07-23 → Slice A2 (T-145–T-162 on the [build board](../build/plan.md)):** the producing-side lifecycle as interactive surfaces on the Slice A spine — the standalone TIDP page + schema/code-builder, the SharePoint-shaped sandbox drawer with folder-view actions, the bind action, the attached-source working set, and the multiplayer shared thread (visibility now, real-time deferred). One full-lifecycle slice; not started.

### Session I — the infra / security decision session *(2026-08-01 → ADR-0047; ADR-0037 amended)*
*A **decision session, not a grill** — bucket (C). Run split explicitly: the commercial and strategic forks brought to the owner in plain language, the mechanics owned and defended by Claude in the ADR. First act was re-cutting [nfr.md](../build/operating-envelope.md) for V1, which closed **Q-027**.*

**What the owner ruled.** **AWS London (`eu-west-2`)** as the pilot cloud. **Password authentication carries V1**, with Entra deferred — the owner's call, made against the recommendation, to keep the pilot off the critical path of another organisation's IT department; the deferral was given an edge rather than left open (see below). **Cyber Essentials now, Plus before go-live**; ISO 27001 and SOC 2 clocks start post-pilot. The corpus **lands in the pilot environment only**, with development and evaluation on synthetic fixtures. And, after the findings below, **Claude on Anthropic's public API for the pilot**, with the requirement that switching to EU-region Bedrock or Azure OpenAI be genuine configuration rather than a rebuild.

**The three findings that reshaped the session** — recorded because the outcome is not the obvious one, and because two of them invalidated a choice already made mid-session:
1. **The Microsoft-shaped dependencies do not constrain hosting.** Entra is OIDC; CSPP/WOPI (ADR-0043) is plain HTTP. The instinct to host on Azure because the customers are M365 shops bought nothing.
2. **There is no UK-region route to Claude on any hyperscaler.** Foundry serves it only on Global / Data Zone (US) deployments with EU support still forthcoming; Bedrock's London region does not carry it, and Bedrock's EU inference profile routes to Ireland, Frankfurt, Paris, Stockholm, Milan and Spain — the UK is absent. **UK-only inference and Claude are mutually exclusive.** The owner picked Azure UK South on the first pass and reversed to AWS once this was verified.
3. **ADR-0037's `standard` tier was buying less than it appeared to.** Its "UK region" line cannot be met by the model the product runs on, while the case UK-only genuinely serves — SECRET-capable work — is already answered by `sovereign`'s self-hosted open-weight models, precisely because a UK region of a US-headquartered hyperscaler does not escape foreign legal process anyway.

**The mechanics Claude owns and defends** (full argument in [ADR-0047](../architecture/adr/0047-pilot-deployment-substrate.md)): SPA on S3/CloudFront and API on ECS Fargate behind an ALB with WAF; **S3 as the real store behind `file_ref`**, with bytes always streamed through the API and **never presigned** — a bearer capability that outlives its entitlement check would break ADR-0024's revoke-in-the-same-transaction guarantee; RDS PostgreSQL 17 single-AZ with managed PITR at five-minute granularity; one VPC over two AZs with RDS and tasks private and an S3 gateway endpoint; **customer-managed KMS keys**, chosen over platform-managed for the key-policy evidence an assessor asks to see, at about a dollar a key per month; Secrets Manager with **no long-lived IAM credentials minted at all** — task role for runtime, GitHub OIDC for deployment; migrate-then-deploy in a separate task preserving the T-247 role split through the pipeline; Terraform in `infra/`, outside the pnpm workspace so the dependency rules stay untouched; **logical tenant isolation**, because ADR-0037 already makes the deployment the physical boundary and building per-tenant infrastructure now would build that lever twice.

**The load-bearing ruling — a third security tier rather than a bypass.** The owner's choice of Anthropic's public API is US-region and conforms to neither existing tier, so ADR-0037's router fails closed, correctly. Both dishonest exits were rejected: relaxing `standard` to admit `us` would silently degrade the guarantee for every future deployment selecting it, and bypassing the router at the call site would convert an enforced invariant into a comment. Instead ADR-0037 §2's promised extensibility was used as intended — **a `pilot` tier whose declared attributes are true** (`region: us`, `jurisdiction: foreign-reachable`, OFFICIAL only), valid **only** under a zero-data-retention agreement with Anthropic, never a default, the only tier admitting `us`, and **expiring at nfr.md's revisit trigger 2**. The name is deliberately self-limiting: a tier called `pilot` cannot quietly become the production posture the way a relaxed `standard` would.

**Two things made honest rather than tidy.** *Residency is three-part* — documents, database and backups **UK**; inference **US** under zero retention; error telemetry **EU** — and a pilot agreement must disclose the inference position rather than let a buyer infer UK-only from "UK data residency". *The identity deferral carries three conditions* — the seeded shared dev password must not exist in the pilot environment (a build task, not a note), rate limiting and revocable sessions become preconditions, and Entra lands before any paid contract. A deferral without an edge is an abandonment.

**Also settled, as the first real infra dependencies the build had named:** the Slice A3 P2 dev-harness engine is **Collabora Online Development Edition, run locally only** and never deployed to the pilot environment (ADR-0043 §3 makes it a disposable rig; Collabora exercises the more representative WOPI surface than OnlyOffice, whose primary path is its own Document Server API); and the **notification channel's provider is Amazon SES in `eu-west-2`**, discharging Q-012's infrastructure dependency.

**Carried out of the session as lead-time items** (owner-driven, outside the ticket board): the **DPA with the pilot firm**, which gates the corpus load; a **zero-data-retention agreement with Anthropic**, without which the `pilot` tier's declared `retention: zero` is false and the tier must not be used; **SES domain verification and the sandbox-mode exit**; **Cyber Essentials**; and cyber/PI insurance. CSPP remains tracked against ADR-0043.

**Ticketed the same day → Slice V1-I (T-316–T-327 on the [build board](../build/plan.md)):** the pilot environment as Terraform, the S3 store behind `file_ref`, the deployment pipeline, the `pilot` tier, the second adapter pair that proves portability, SES, Sentry, the pilot-user provisioning path, the restore rehearsal and the synthetic fixture corpus.

### Session DMS — the document-management walkthrough, comment-directed *(2026-08-09 → addenda to ADRs 0032, 0033, 0038, 0040)*

Nothing was edited during the session, which is what let a later entry reverse an earlier one without leaving a half-applied change behind. **The sweep found no reversals and no conflicts**; two pairs compounded rather than clashed (S3's never-amend principle recurs in S7's never-delete; S6 and S7 share the discipline-derived tree, seeded once versus derived live).*

**What the owner ruled, in one line each.** The story **opens with the owner defining the schema** — the plan decides first, and someone decided what the plan records (S1). The schema **exports as a fillable Excel template** and the plan **imports the filled sheet back** as a **create-only batch** — never an amend, never a delete, with **references generated by the naming scheme in file order** and a reference-like column ignored, because numbering is never drafted in a spreadsheet (S2, S3). Plan columns are an **organisation standard, locked** — no personal overrides (S3). The row's detail becomes a **card**, not a drawer (S4). **Row editing follows lead authorship** — title, classification, other authors, reviewer *proposals* — while withdraw, lead-author reassignment and the coded reference stay elevated or super-user acts (S5). The sandbox tree builder gains **both halves**: a no-model seed from the plan's disciplines, and an ADR-0027 propose-confirm **agent** for free-form shaping (S6). A **third folder mode — plan-locked** — derives the tree from the organisation's own plan rows, renaming as rows retitle and badging withdrawn rows off-plan rather than deleting anything (S7). **Binding confirms on a card**, and a bound document **reads its row through** rather than copying it, so a bound draft is retitled on the plan (S8). And **promotion-requires-QA becomes a per-sandbox setting, default on** (S9).

**The load-bearing ruling is S9, and it is a policy, not a feature.** ADR-0032 had made internal QA "optional ceremony, never a system gate". The owner turned that into a *choice a team records*: the gate is on by default for project sandboxes, and turning it off is a deliberate, visible super-user act. With it on, promotion's two legal sources narrow to one — the QA-accepted frozen version — and the live-head source is refused. The ruling came from reading the built path against the **ISO 19650 CDE** state machine (the ProjectWise service definition): WIP is the ambient v0.x series, Content Check / Approve for Sharing is freeze plus the internal cycle, Shared is the QA-accepted frozen version, Approve for Publication is promotion, Published is acceptance issuing the C-revision, and Archive is history plus supersede. **The mapping is on the record in [component-5](../architecture/components/component-5-document-management.md)** precisely so the anchoring is checkable rather than asserted.

**Deferred by the owner, with a reason:** the organisation-level structure **template** (save a confirmed tree, reuse it next project — the ProjectWise standard) is org-context knowledge and deserves its own pass on where templates live and who edits them. It is in [the deferred register](../build/plan.md#beyond-v1--the-deferred-register), not lost.

**Built the same day → Slice Walkthrough (T-358–T-366 and T-368, plus T-355 grown in place; migrations 0042–0045).** What the build found is worth as much as what the session ruled, because three of the rulings only became *safe* once an adversarial review had been at them: the QA gate could be walked around entirely by drafting in a personal workspace and binding from there (the personal sandbox is now gated too — scratch work is unbound and cannot promote, so the exemption bought nothing); a spent QA acceptance silently re-issued *identical* content on the next revision while the responses claimed changes (now refused until a fresh pass); and an internal "revise" verdict was **unanswerable** — the freeze container carries reviewers but no authors, so nobody could respond, the head could never be re-frozen, and the deliverable could never be promoted. That last one mattered exactly because S9 promotes internal QA from optional ceremony to the main road. **One question came out of the build:** `Q-039` — a plan-locked *shared* sandbox derives folder names from the whole TIDP, disclosing its shape to every granted organisation.

**The method note worth keeping.** Comment-directed review of the built product found nine real design gaps in an afternoon, against a walkthrough that had itself been built to show the product honestly — including its gaps. The artefact earned its keep twice: once as a way to see the product, once as a way to interrogate it.

### V1 definition *(2026-07-31)*
- ~~**How a legacy corpus enters the controlled record.**~~ ✅ **Ruled 2026-07-31 (Claude's call, owner-delegated).** A customer's 100–500 document corpus arrives with no TIDP, no cycle, no acceptance code — it is *received* material, not *produced* material, and V1 must not invent a fake lifecycle to admit it. No new state, no new table, no parallel lifecycle. **One consequence to build, not merely note:** a loaded reference document must be *visibly* distinguishable in the Documents view from an accepted deliverable, or the corpus quietly launders itself into the produced record — the marker is an ingest ticket, not a later polish item.
- ~~**The admin / super-user access tier.**~~ ✅ **Ruled 2026-07-31 (Claude's call, owner-delegated) — promoted to a V1 blocker, because the full DMS lifecycle in [v1.md](../build/v1.md) needs the destructive actions reachable.** **The answer is the smallest of the three options the question posed: extend the existing `Participant.elevated` flag, not a new platform tier.** The mechanism already exists (`drawer1-parties.ts`, T-174 with T-133 realised); what was missing was the policy. `elevated` holds **close-as-rejected** and **owner supersede/withdraw**, every use audited with the acting Participant named. **ADR-0016 does not reopen**, and that is the load-bearing part: `elevated` is a *capability flag on a Participant*, not a standing role, so "standing roles collapse to owner and member" is untouched — the question's fear was that a super-user tier meant a third role, and it does not. **The org admin is deliberately not extended.** Enrolment (ADR-0033) and destructive lifecycle have different blast radii and different audiences: enrolment is org-internal and affects only that organisation's own people, while close-as-rejected changes the project record *every* organisation on the scheme reads. Folding the second into the first would quietly turn an intra-org power into a cross-org one — the single direction ADR-0033 was careful not to travel. Owner supersede/withdraw is likewise gated on `elevated` **within** the owner organisation; not every owner Participant carries it. **Left open on purpose:** the retention/deletion powers, which wait on the audit-record theme's retention ruling below rather than being folded in here on the way past. *(Original question, for the record:)* Destructive, governance-level lifecycle actions should not sit on the general surface for ordinary users. The reconciliation to make is the crux: today's model has the **org admin** (`org_role`, ADR-0033 — an intra-org *enrolment* power, not a lifecycle one) sitting alongside ADR-0016's deliberate "standing roles collapse to owner and member." ### Session 2 — the checker: `Q-007` + `Q-008` *(2026-08-01 → ADR-0048)*
*Grill method. The two questions were put on the board separately and **ruled together**, because working them in order showed they were one decision seen twice: what the rulebook is decides what a finding may say, and what a finding may say is the whole of what the rulebook is for.*

- ~~**Q-007 — The rulebook's channel.**~~ ✅ **Ruled 2026-08-01 (owner).** **The tracker's framing offered a fork the record had already closed**, and finding that was most of the work. The 2026-07-29 two-tier authority ruling settled that **placement does not set channel role** — an organisation-tier provision lives in org context and still grounds and cites, because the operative test is what the material *is* (a published external instrument), not who loaded it. So "guiding-in-org-context vs the org tier" was never a choice about *where* the rulebook lives; both live in org context. The live question was whether a firm's rulebook passes that existing test, and **it does not**: a house drafting manual is the firm's own preference document, not a published external instrument. A middle position was raised and rejected in session — that a rulebook *restating* IEMA guidance or an ISO clause thereby becomes groundable. It does not: **a restatement is still the firm's own document**, and where a rulebook points at an instrument the firm has separately licensed and loaded, the citable thing is that instrument, never the manual's paraphrase. **A V1 fact then shrank the question again:** [v1.md](../build/v1.md) defers the authority corpus in *both* tiers, so in the pilot the organisation tier does not exist and no ISO or IEMA material can ground however this were ruled. **What was actually decided, therefore, is what the checker may *say*** when its only rulebook is guiding material: **a finding may quote the rulebook verbatim, and that quote is not a citation.** This is the third option `Q-007`'s own stress test hypothesised — quotable-but-uncited — and it reconciles with ADR-0021 precisely rather than conveniently: the guiding channel forbids material being cited **as project fact**, and a house rule is not a fact about the scheme but an **instruction to the author**. Two obligations fall out and are build constraints, not notes: **the render must differ from a grounded citation** (a quoted rule is not a source chip and must not resolve like one), and **a quoted rule is org-private** — a finding quoting Org B's manual must never appear on a surface Org A reads, because leaking a competitor's internal drafting standards through a review comment would be an ethical-wall breach delivered by a feature nobody thought of as crossing the wall. *(Owner considered and declined: building the org tier into V1 after all — the strongest checker and where the product ends up, but it pulls T-277's store and interval model into the pilot and adds a standards-licensing conversation on top of the DPA; and findings that describe a breach without quoting it — the strict reading, rejected because it makes every finding homework.)*
- ~~**Q-008 — The checker's output shape.**~~ ✅ **Ruled 2026-08-01 (owner): checking, not generative — with an optional fix that rides the existing Suggestion mechanism.** Output is a list of **findings**, structured records rather than prose, each naming the input it arose from (corpus, attached document, rulebook), an **anchor into the draft**, a severity and its evidence. **Anchoring is the ruling's practical half**: a finding that does not point *into the text* is a report, not a tool, which makes **locators (T-271) a hard dependency the checker did not visibly have while it was unruled**. The generative half is bounded deliberately: a finding may carry a proposed revision, but that revision **enters the existing accept/edit/reject Suggestion path** and is never auto-applied, so **the checker gains no write path the drafting side does not already have** and every change to a deliverable stays a human act through a mechanism already audited and reversible. Two guards keep it from collapsing: proposed fixes are **collapsed by default and never applied in bulk** — the moment findings arrive with fixes and an "accept all" beside them, reviewers accept patches instead of reading findings, and the human check the professional-liability model depends on (the 2026-07-12 ruling) evaporates while appearing to be performed — and **a finding states a defect, never a verdict**, component 6 §6's first answer invariant applied where it would be easiest to cross by accident. *(Owner considered and declined: checking-only, the purest separation but it makes every finding homework; and the checker rewriting the section, the most impressive demonstration and the one that leaves nothing independent to check, since the run that judges the work would also produce its replacement.)*

**Ticketed the same day:** the finding schema in `contracts` as **T-328**, minted *ahead of* the checker DAG and the findings surface because both depend on it. **T-308, T-310 and T-311 unblocked.** Left open on purpose in ADR-0048: severity's vocabulary (a naming question for the schema ticket), whether findings persist across redrafts (a review-cycle lifecycle question), whether the checker runs automatically at freeze or promotion (`Q-006`), and **whether open findings block promotion — deliberately handed to `Q-012`'s promotion rider so it and the comment-thread question are answered consistently**.

### Session 3 — notifications and the promotion gate: `Q-012` *(2026-08-01 → ADR-0049)*
*Grill method, scoped deliberately to the **minimum for the pilot** rather than the full model. Could not have run before the infra session, which fixed the transport (Amazon SES, ADR-0047 §16).*

- ~~**Q-012 — Mention delivery, and the missing notification model.**~~ ✅ **Ruled 2026-08-01 (owner).** The session's first move was to separate two things the question had bundled: the **notification record** — persisted, in-app, read/unread — from the **delivery channel**. The record is cheap and is what actually makes "design it once rather than per-feature" true; the risky decision is which events earn a *delivery*, because an event that fires often is the one that teaches a pilot user to mute the feature in week one. **The pilot set is `round-issued` + `@-mention`; lock-flipped is deferred** — round-issued is the named failure (a cycle nobody is told about runs on WhatsApp instead, on a channel Infora cannot see, audit or wall), `@`-mention is nearly free since T-112 already stores and renders mentions and only the *telling* is missing, and lock-flipped fires far more often while mattering to one person usually already looking at the document. **The guard against designing a general channel from a sample of two is explicit: adding the third event must not require a schema change** — if it does, the abstraction was wrong. *(Owner considered and declined: all three events, which would prove the abstraction better but risks the noise problem; and round-issued alone, which leaves the cheapest half of the problem undone.)*
  **The mechanics Claude owns and defends.** A notification's **visibility follows the thing it points at**, always — it is never a channel by which a fact reaches someone who could not otherwise reach it, which is the wall (ADR-0018) applied to a surface nobody thinks of as a data surface. **Email carries a pointer and a bare fact and never content** — this is the load-bearing rule, because an email leaves the platform into a mailbox where access resolution no longer applies, where it survives revocation and can be forwarded outside the organisation; so the body names the document and links back, and never the comment text, the finding text, or a quoted rulebook clause (which ADR-0048 §6 had already made org-private). **Access is resolved at *send* time, not enqueue** — ADR-0024 makes a revoke effective in the same transaction as the read it governs, and a queue resolving entitlement at write time would reintroduce that gap in the one medium that cannot be recalled. In-app is the surface of record; preferences, digests and batching are deliberately not built at ≤ 25 users and two event types.
- ~~**The rider — do open comment threads block or warn at promotion?**~~ ✅ **Ruled 2026-08-01 (owner): block — and on open findings too**, discharging the deferral [ADR-0048](../architecture/adr/0048-the-checker-findings-not-prose.md) made to this session precisely so both halves would be answered consistently. **Ruled against Claude's recommendation**, which was to warn and record the warning; that argument is preserved in ADR-0049 decision 7 — blocking makes Infora the arbiter of professional judgement, which sits awkwardly beside the liability model in which the consultant carries the judgement (the 2026-07-12 ruling), and a hard gate can teach people to close threads without resolving them, destroying the signal the gate protects. The owner's position is that nothing reaches the controlled library with loose ends, and threads and findings are treated identically so the surface never has to justify why one list stops you and the other does not. **Claude's added mechanic, flagged rather than folded in silently: the block is overridable only on `Participant.elevated`, and every override is audited.** A block with no escape is not a stricter gate but a **deadlock** — a finding raised against a paragraph a later redraft deleted, or a thread whose author has left the project, would otherwise prevent promotion permanently with no lawful action available. The override reuses the tier ruled 2026-07-31 rather than inventing a bypass: `elevated` already holds close-as-rejected and owner supersede/withdraw, and forcing a promotion past open items belongs in that company. An ordinary Participant cannot pass the gate, so the block is real; ADR-0016 does not reopen, because `elevated` remains a capability on a Participant rather than a standing role.

**Placement ruled the same day, after the options were drawn** (ADR-0049 §6a–6c). The ADR as first written said only "an unread indicator and a simple list", which was too little to build from and would have left the decision to whoever picked up T-331. Three candidates were mocked against the real shell — the nav rail, the project home, and a floating panel — and the owner took **both** of the first two. **The rail carries the durable count** (the only placement that survives wherever the user is, which matters because the person a round-issued event most needs to reach has been in the editor all afternoon and will not visit a home page); **the project home carries a "Needs you" panel above the work items**, so the notification sits beside the thing it is about, absent at zero rather than showing an empty state. Neither works alone — the rail reaches you without saying what to do, the panel says what to do without reaching you — and **if the ticket splits, the rail ships first**. **The floating panel was rejected** as the home for the record: drawing it revealed it lands on the *drafting canvas*, where a consultant spends the day, and it reads as transient against the durability §1 exists for; that shape belongs to confirming an action just taken, which is a different mechanism. **The scoping question the mockup exposed was settled rather than deferred (§6b):** the **rail count is the user's own across every project they can reach**, grouped by project, while the **panel is project-scoped** — without the split, a mention on a second project would be silently invisible, because the rail sits beneath a project switcher and would otherwise inherit its scope.

**Ticketed the same day → T-329–T-332.** The promotion gate carries a dependency that is easy to miss: promotion must be able to **count** open threads and open findings, which is a query obligation on the finding schema (T-328), not a display concern.

### Session 4 — the privacy programme: `Q-032` + `Q-033` *(2026-08-03 → ADR-0050)*
*Grill method, run first of the remaining five V1-blocking questions **not** because it blocked the most tickets but because it gates the **DPA with the pilot firm** — a procurement item moving through another organisation's legal team, which ADR-0047 §18 makes a precondition for loading the corpus. External calendar time a design ruling does not have. The two questions were taken together: both are the privacy programme, both filed under component 3, and the same session settled them.*

**The framing correction that shaped the session, recorded because it is a method finding rather than a design one.** The first question was put as a design fork and the owner rejected the framing outright: *"what's the user situation, what would I see as a user, if it's purely about tech and backend, explain it to me as a non-engineer."* Every subsequent question opened with the person, the screen (or the explicit absence of one), and the mechanism in plain English before the fork. Two of the three Q-032 questions have **no user-visible surface at all**, and saying so plainly turned out to be the necessary framing rather than a reason to skip it.

- ~~**Q-032 — Operator access, and what "eyes off" can honestly claim.**~~ ✅ **Ruled 2026-08-03 (owner).** **The tracker's own recommendation was wrong and the session's first act was correcting it.** It proposed *"no human holds the credential, and every use is break-glass"* — but ADR-0047 §9 runs migrations with the owner credential on **every deploy**, which is routine and continuous, so the second clause falsifies itself the first time anyone asks. The honest cut is **two roles**: a **pipeline role** that is non-human, OIDC-federated, and with which no interactive session is possible; and a **human break-glass role**, time-bounded, reason-stated, with CloudTrail as the out-of-band record. The claim that survives is **"no human holds a standing credential to customer data"** — not *"no human can read it"*, which would be a lie. **Disclosure is a right to ask, not a notification** (a DPA clause; proactive per-event notice named as the destination): ADR-0049 has already built the notification record it would ride on, so the objection is not plumbing — **the role checkout happens in AWS, outside the product**, so the faithful version is real infrastructure work and the cheap version is an engineer remembering to post a notice, an honour system wearing the costume of a control, which is *worse* than the right to ask because a customer would reasonably read it as automatic. **The conflict register is protected procedurally, and the gap is stated rather than papered over** — it is the sharpest case here because a stolen document exposes one project while the register is a map of the firm's whole book of business, from which its engagements can be inferred (ADR-0046 §7 says so itself). **Application-level encryption was raised by the question and rejected on a finding, not on cost:** the person who can read the database also controls the deployment and can therefore reach the application's key material, so the only construction that holds needs the *customer* to hold a key Infora never has — at which point a lost key is a lost register. The reduction that does work is **minimisation**: `reason` is nullable free text and is the one field that turns "a person and two project ids" into a client roster, so it stays (a compliance partner reviewing a two-year-old wall needs the why) with its purpose narrowed on screen. **No support access in V1**, and the shape of any future one ruled while it is still free: **customer-initiated, time-bounded, self-expiring, customer-visibly audited** — operator-initiated impersonation forbidden with or without notice, because the difference is who holds the switch and once the operator holds it no wording repairs it. *(Claude's call on the residual, flagged rather than folded in silently: the access report is **one undifferentiated list**, with the stated reason on each entry carrying whether it was customer-requested — a category is a place to park things, a reason is not.)*
- ~~**Q-033 — Deletion in use, and deletion at the end of a contract.**~~ ✅ **Ruled 2026-08-03 (owner), and the ruling corrected two recommendations — the tracker's and the session's own.** The enabling finding came from the code rather than the design: **the product has never been asked to erase anything.** `DELETE /sandbox-documents/:id` is a *soft* delete with self-service `undelete` (T-128), and nothing in the controlled library can be removed by anyone at all — so "delete" in Infora means *put in the bin*, with the row, the text and the derived retrieval passages all surviving. **Delete and Purge become two acts**: the bin stays, because recovery-without-a-helpdesk-ticket is a product virtue being deliberately kept, and Purge genuinely erases including the derived stores, org-admin only, behind a typed confirmation and audited with a name. **What may be purged is bounded by *whose material it is*, not by where it sits** — which is where the tracker's **three-zone** recommendation broke: the zones described the outcome and mistook it for the cause. Org B may require complete deletion of **its own material wherever it lives** (sandbox and personal sandbox, org context, drafts, its own producer-private Runs, Signals, cost attribution, its conflict register); Org A **retains the deliverables and the review-cycle metadata, named individuals included**. **The session's own proposal was also rejected, correctly:** it tried to license purge by the *absence of a work item* — V1's marker distinguishing loaded reference material from produced deliverables — and the owner ruled that **a stakeholder's report loaded into the library is full corpus**; it grounds and is cited, and that absence records how a document arrived, not what it is worth. **Removal from the library is two steps and the second is the owner organisation's**: withdraw first — already built and already sufficient, since `containers.state = 'live'` is a pre-filter *inside* the retrieval query ([retrieval.ts:90](../../packages/knowledge/src/retrieval.ts#L90)), so a withdrawn container stops grounding in the same statement as the wall — then removal by the **owner organisation on the producing organisation's request**. **The owner's shape was taken over the session's for a reason worth preserving:** putting the lever with the producing firm would let a consultancy purge six months of corpus ahead of a dispute, leaving the produced record intact but **uncheckable**, every citation in every accepted deliverable resolving to nothing — and uncheckability is the one thing the grounding argument cannot survive. Removal means **erased, not delisted** (chunks, embeddings and S3 object versions, since versioning is on and a delete writes a marker), with the citing run reporting T-253's **`unreconstructable`** rather than lying or being erased. **At contract end:** the hand-off is documents as files *plus the review record in readable form* — not a database dump, unusable and schema-leaking; not files alone, which discards the evidence they were properly produced — and no export path exists today, so it is named as **post-V1** build work rather than discovered when a contract ends. The lag is **stated as a number** (erased from live systems on exit, aged out of the 14-day PITR window and backups within a fortnight after), because "immediately" is false the moment anyone checks. Attribution inside Org A's record is **retained and disclosed, never pseudonymised**: a sign-off is worth something because a named person made it.

**One consequence accepted rather than solved**, and it is what the DPA promises against: remediating a wrong-client load now depends on **another organisation acting**, and the request itself discloses the document's presence to them. Defensible — it is their library and they can already see it — but the response time on a confidentiality incident is set by somebody else's inbox.

**Ticketed the same day → T-339–T-342.** The break-glass access path in Terraform (Slice V1-I), Purge, library removal after withdraw, and the conflict register's narrowed `reason` guidance. **`Q-035` was raised rather than resolved**: the controller/processor model surfaced twice in session and blocks the DPA alongside the two questions just closed, because a DPA is literally a controller–processor agreement.
