# ADR-0028 - The orchestration / run / agent model: every agent execution is a Run inside a Conversation (optionally bound to a Work item), decomposing into an append-only tree of Steps run by parallel-capable sub-agents that retrieve only through Context; v1 runs a coded chain (retrieve → draft → ground-check → cite) with agentic retrieval leaves

**Status:** Accepted. **Refined 2026-07-06 (surfaces alignment session) — run-record visibility:** a Run bound to a **Work item** is part of the project record and is readable in full by the owner role (prompt text, step tree, source set, rail outcomes, suggestions and resolutions) — the M5 cross-role read; an **ad-hoc** Run (Conversation with no Work item, including every Copilot run in v1 per ADR-0031) is working-area material, visible to the requester's own organisation only, with the project owner holding the same audited, exceptional override as for a private project sandbox (ADR-0018). **Superseded in part 2026-07-12 (owner-ruled, T-104) — the record turns inward:** every Run is readable by its **producing organisation only**, work-item-bound or not; the 2026-07-06 owner read and the owner-override-for-runs clause are withdrawn. The record is retained background data anchored to the work — the consultant carries the professional liability for the work product, even using Infora, and the client owner reviews the *document* through the review cycle (ADR-0005–0014), never the agent's internals. §3's append-only immutability and §7's defensibility fields stand unchanged; whether provenance ever re-surfaces document-anchored on demand stays on the grill tracker's audit-record item. The one real pre-code gap on the MVP critical path (the M1 grill): ADRs 0001–0026 cover the document lifecycle, access and context, but none defined how work is orchestrated and run. Builds on ADR-0012 (document management owns only the review cycle; all other workflows run in the Engine), ADR-0025 (the assembly environment every agent executes in), ADR-0022 (access-resolve before retrieve) and ADR-0002 (immutable controlled revisions, the precedent for append-only records). Feeds M2 (ADR-0027, thinking vs doing — the chain this ADR fixes is what that classifies) and M3 (the Context-assembly contract this ADR's `retrieve` step calls). Folds in the first-class **Agent** concept and partially discharges the candidate "audit-of-every-action as an invariant" ADR for the agent-execution case. Validated against Legora's aOS (its Agent / Workflows split and parallel sub-agents) and Anthropic's multi-agent research system (orchestrator-worker, isolated parallel sub-agents, separate citation pass).

**Context:** The walking skeleton runs a real chain — a consultant asks the chat to draft a governed section, the orchestrator runs retrieve → draft → ground-check → cite and logs every step, the draft appears with citations, the consultant accepts/edits/rejects and that Signal is captured, and the owner sees the work item with live status and the full audited run. Every other M1 artefact — the data model's `Run` tables, the audit trail, the M3 assembly contract — reads against a run model that did not yet exist. Four things were undefined: what a Run *is* against a Work item and a chat interaction; how a Run decomposes into steps and sub-agents; what each step records to make the trail regulator-defensible; and whether v1 orchestration is a coded chain or an agentic planner. The adjacent reference points are Legora's aOS (the nearest public analogue — an "agentic operating system" whose orchestration layer handles tool routing, control flow, memory, model selection and guardrails, and which ships *two* execution modes: an open-ended **Agent** that plans its own steps, and **Workflows** that are "agentic in the sense that it can make some decisions, but you still define the steps … it doesn't go off-script") and Anthropic's multi-agent research system (an orchestrator-worker pattern where a lead agent spawns isolated sub-agents in parallel, each with a self-contained task and fresh context, and a separate citation pass runs after synthesis).

**Decision:**

**1. One execution model for chat and workflow.** Every agent execution — a chat answer or a workflow step alike — is a **Run**. A Run has exactly one parent **Conversation** (the persistent thread it happens in) and an **optional Work item** link. A Conversation accumulates many Runs over its life; a Work item, when present, accumulates the Runs that advance it. There are not two machines: a workflow run is a run whose Conversation is bound to a Work item; an ad-hoc chat question is a run whose Conversation has no Work item. This matches the Assistants-API sense of *Run* and *run step*, adopted deliberately so the term is not idiosyncratic. Legora's aOS is the adjacent confirmation: it unifies Agent, Workflows, Tabular Review and Research as "a single connected system" for the execution of work — one workflow can itself invoke a Tabular Review, a web search and a citation check as tools — and "picks up where the last round left off," i.e. one orchestration-plus-memory substrate beneath every mode. "One execution model" means precisely this **one substrate** — one Run/Step/Conversation record, one audit, one tool-routing and memory layer; it does *not* mean one control flow. The control-flow **modes** ride *above* the substrate and may diverge (point 5): a chat run may plan openly while a Work-item run follows a defined spine, exactly as Legora's open **Agent** and defined-step **Workflows** are two modes on one aOS. Points 1 and 5 are therefore complementary, not in tension.

**2. A Work item has many Runs; the Run is the immutable execution unit.** A Work item is the persistent unit of work (it carries a type, a status and an assignee, per the glossary) and is *not* one-to-one with a Run. Each invocation — first draft, redraft after review — is a new Run. The Work item's status is driven by its Runs and by human actions but is a separate state machine from any one Run's state (`running` / `completed` / `failed`); an accepted deliverable is not a "running" anything, and a failed execution does not fail the work item.

**3. The Run / Step record is a tree, append-only and immutable.** A Run decomposes into **Steps**; a Step may delegate to a sub-agent, spawning a **child Run**, so the record is recursive. Once written, steps and runs are appended and never mutated or deleted — mirroring the DRR's append-only history and ADR-0002's immutability, because a regulator-defensible trail that can be quietly rewritten is not defensible. The recursive shape is fixed now even though v1 populates only a shallow tree: an immutable audit store cannot be restructured later, so the sub-agent boundary must be representable from the first migration (a nullable `parent_step_id` / `parent_run_id`).

**4. Sub-agents are real from v1, parallel-capable and isolated, retrieving only through Context.** Orchestration deploys specialist sub-agents (Legora's pattern; Anthropic's orchestrator-worker). Each sub-agent runs as its own child Run with a self-contained task and a fresh context, does not coordinate with siblings mid-task, and returns its result into the calling agent's context for synthesis. The model is **parallel-capable** (sibling child Runs may run concurrently — the substrate for Tabular-Review-style fan-out), though v1 exercises only one sub-agent: a **retrieval sub-agent** the main chat agent calls to find relevant documents and fold them into its context. **All retrieval — the baseline per-request assembly and any agentic sub-agent retrieval — runs through the Context-assembly API (M3), never reaching stores directly**, so access-resolution-before-retrieval (ADR-0020, ADR-0022) and the ethical wall hold by construction. A sub-agent that could read stores directly would bypass the wall; routing every retrieval through the one Context gateway is what prevents it.

**5. v1 orchestration is a coded spine with agentic leaves.** The chain shape — `retrieve → draft → ground-check → cite` — is **code**, run the same way every time; the orchestrator is not an LLM deciding the plan. *Within* a step an agent may act agentically (the draft step's agent may spawn a retrieval sub-agent and choose what to search for), but it cannot change the chain. This is ADR-0027's "code with an LLM escape hatch" applied to orchestration, and it guarantees by construction that ground-check and citation always run — which a planner LLM could skip, defeating the grounded-output promise. The target post-MVP architecture mirrors Legora's two modes and this ADR's two parents: a **Work item** run trends toward a *defined-step Workflow* ("doesn't go off-script"), a plain **Conversation** run toward an *open Agent planner*. v1 holds the coded spine for **both**, because even chat must guarantee ground-check and cite; the divergence is named, not built.

**6. Capabilities are called as typed tools through a registry.** Orchestration routes to **capabilities** (reusable skills — grounded generation, compliance checking, tabular review, plain-English, document understanding, chat/QA) as typed tools with input/output contracts, each independently callable (Legora's "tool routing"; the typed contracts of component 1). The v1 chain binds: `retrieve` → the Context-assembly API (M3) plus the retrieval sub-agent; `draft` → grounded generation (one model adapter, behind the Router); `ground-check` → the grounding / NLI verifier (governance, component 3); `cite` → citation resolution. Per ADR-0027, only `draft` is *thinking* (the LLM); `retrieve`, `ground-check` and `cite` are *doing* (code plus model calls for embedding and entailment). The standalone `cite` pass matches Anthropic's separate citation pass.

**7. What each Step records.** Each Step is one atomic action and records, append-only: identity (`id`, `run_id`, `parent_step_id`); the acting `agent_id` and its provenance; `type` (retrieve / generate / ground-check / cite / delegate); `status` and start/end timestamps; the **model and version** used (the Router's selection); **token and cost usage**; and the two fields that make the trail regulator-defensible rather than merely observable — the **access-resolved source set the step saw** (what grounding drew on, so any output can be shown to have been grounded properly) and the **rail outcomes** (which rails applied and whether output was withheld). A delegating step also records its `child_run_id`.

**8. The Agent is a first-class actor with a provenance and a deployment model.** An **Agent** is the software actor that runs a workflow's steps, drawing on capabilities and the assembled working input. It has one of two provenances: an **Infora-built agent** ships with the platform and runs the standard workflows; a **custom (org-built) agent** is built by an organisation, held in org context, and deployable to any project it works on. Both execute identically: inside exactly one assembly environment (ADR-0025), reaching only that environment's channels, within the governance envelope and bound by the project owner's rails — a custom agent may tighten its own organisation's private work but can never loosen the owner's rails (the access-model invariant, ADR-0015, applied to governance). The Agent is recorded here, with the run/orchestration model, rather than in a separate ADR, so the actor / run / orchestration trio cannot drift apart. The detailed governance authority for deploy-time rails inheritance remains component 3's forthcoming ADR.

**9. What is real versus stubbed in the skeleton.** *Real:* the Conversation / Run / Step model and the append-only audit trail; the coded chain; retrieve-through-Context with hybrid retrieval (ADR-0022); grounded generation through one model adapter; the ground-check verifier; citation resolution; the one retrieval sub-agent (to exercise the tree); access-resolution before retrieval; and accept / edit / reject **Signal** capture. *Stubbed or deferred:* the other capabilities (compliance checking, tabular review, plain-English, document understanding); custom / org-built agents (Infora-built only in v1); parallel fan-out beyond the single sub-agent; the Signal **sink** (capture is real, the moat-write loop is Session 7); and multi-model routing (one adapter behind the Router interface). Memory beyond the Conversation's own thread is out of v1 scope.

**Refined 2026-07-22 (router selection axes) — security-tier filter before task-based selection:** The Router selects along two distinct axes that must never be conflated. **Security-tier enforcement** (from the forthcoming deployment-security-tiers ADR extending this §9) is a *hard constraint*: it fixes which models and endpoints are even *eligible* — by region, jurisdiction and retention — and filters the candidate set of routes first. **Task-based model selection** (the future capability the `task` parameter on the Router already reserves) is an *optimisation within that set*: choosing the model best suited to an activity — heavy synthesis to a frontier model, quick extraction to a small fast one — across capability, cost and latency. The two are distinct layers applied in a fixed order: the security tier filters the candidate routes, then task-based selection optimises over whatever the tier allows. Security tier is **not** a task and must never be collapsed into a task-based heuristic, because a performance choice would then be able to override a security boundary. At the **sovereign** tier the candidate set may be a single self-hosted model, so task-selection is moot; at the **standard** tier task-selection ranges over the tier's eligible models. No code changes now — v1 still ships one adapter behind the Router interface — but the intended Router behaviour is **constraint-then-optimisation**, and a later build implements it in that order.

**Refined 2026-07-22 (Signal-corpus partitioning):** The deferred Signal **sink** inherits the partitioning rule fixed in ADR-0026: the Signal corpus is partitioned by organisation, and pooling Signals across organisations to derive shared insight is prohibited — any signal-derived training or feature draws only on the originating organisation's own Signals and owned, abstracted material. Session 7 builds the sink under that constraint.

**Consequences:** The data model (the gating item 0 before any migration) gains the spine it writes against: `Conversation` (1) ─< `Run` (>─ optional `Work item`), and `Run` ─< `Step` with self-referential `parent_step_id` / `parent_run_id` for the sub-agent tree, every row append-only. The audit trail's shape is fixed and immutable, so it survives the redraft loop that is the core MVP journey, and the candidate "audit-of-every-action" invariant is discharged for agent execution (the user- and document-management audit senses remain owned by component 3 and component 5 respectively — M1 is scoped to agent execution alone). M3 is pinned as the sole retrieval gateway, including for agentic sub-agent retrieval, so the ethical wall is structural rather than enforced per call. The coded spine makes "every grounded answer is ground-checked and cited" provable, at the cost of naming — not yet building — the more agentic chat planner; that divergence is the post-MVP target, and building a chat path now that could never open up is the failure this defers against. ADR-0027 (M2) now has a concrete chain to classify thinking from doing against, and should be promoted from placeholder next. New glossary terms minted: **Conversation**, **Step** (and **Run** refined off "behind a work item"). The provisional Engine component doc (component 6, §1) can be firmed: orchestration, run and agent are no longer ungrilled. Honest limit: this fixes the *model*; the MVP workflow set, workflow-definition mechanics and human-in-the-loop checkpoints (Engine §2, §4) and the custom-agent building interface (Engine §5) remain open and are not on the skeleton's critical path.
