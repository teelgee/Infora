# Infora — the open-questions index

The whole-system grill tracker and the **sole source for open questions** across
every component. Grilling walks the design tree one branch at a time (see the
`grill-with-docs` method), turning open questions into decisions captured as
ADRs. The agent running a session **edits this file afterwards**: ticking off
what it answered and re-prioritising what is left.

**This file is an index, not a store.** The *agreed position* for each decision
lives in its component doc or its ADR; the *record of how it got there* — every
completed session, every closed ruling, the Path-to-MVP analysis — lives in
**[grill-history.md](grill-history.md)**. Split 2026-07-31, mirroring the build
board's own `plan.md` / `plan-history.md` convention, because this file had
become 350 lines of mostly-settled material and the open backlog was no longer
readable inside it.

> **Standing convention: when a question is ruled, its record moves to
> [grill-history.md](grill-history.md) in the same commit**, leaving a one-line
> pointer here. A ruling written out in full in this file is a bug.

**A third file joined this folder on 2026-08-17: [parking-lot.md](parking-lot.md)
(`P-###`).** It holds proposals that cannot be built **without amending an
accepted ADR** — which is why they are not open questions and are not listed
here: a `Q` is a gap the *current* model owes an answer to (two accepted ADRs
disagreeing counts), while a `P` is a change *to* the model that nobody has
agreed to make. ⚠ **Do not open it during a grill session unless the owner has
named it.** Every entry is, by construction, a description of rules it would
break, so reading one mid-session contaminates the session with positions the
decision record does not hold. Nothing there may be cited, built against, or
used to soften an ADR.

The five artefacts divide the labour: `CONTEXT.md` is the **language**, the
[overview](../architecture/infora-overview.md) is the **vision**, the component
docs are the **structure**, `docs/architecture/adr/` holds the **decisions** — and this doc
is the **process log**.

## How to read an entry

`Q-###` — title. **Next free number: Q-050** — **derive it, don't trust it:
`pnpm run check:questions -- --next`** (T-343) scans this tracker,
[grill-history.md](grill-history.md) *and* `git log`, and prints the next free
number. Bump this line in the same commit that claims one; `pnpm run check`
fails if it falls behind, or if a `Q-###` is defined twice. The line stays
because it is readable, but the script is the authority — the prose convention
alone let two concurrent sessions both reach for `Q-034` on 2026-08-03, caught
by eye rather than by any check. A **struck** entry left behind as a pointer to
its record in the history is the tracker's own convention and passes; an
unstruck duplicate does not. Each entry carries:

- **Method tag** — the triage that decides *how* it gets answered, not just when:
  - **[A] reference-decidable** — a precedent exists (Legora and adjacent
    products). Decide in fast-mode, Claude-drafts-you-intervene. Do **not** grill.
  - **[B] must-still-grill** — a genuine Infora-specific fork with no precedent,
    which is where Infora diverges from single-firm Legora. Keep the slow
    adversarial method. These are the moat.
  - **[C] not a grill** — a build doc or a decision session.
- **Blocks** — what cannot proceed until it is answered. Empty means nothing is
  waiting, which is a legitimate and common state.

The current destination is **[v1.md](../build/v1.md)** (the first pilot); the
board is **[plan.md](../build/plan.md)**.

### Foundational and cross-component

- **Q-001 — Audit-of-every-action as a foundational invariant.** **[B]** · *Blocks: nothing; wanted before further audit-adjacent build.* Discharged for the agent-execution sense by ADR-0028 (append-only, immutable Run/Step). Still open for the **user-UI-action** and **system-action** senses owned by component 3. Interacts with **Q-015**.
- **Q-002 — The per-document guidance artefact.** **[B]** · *Blocks: the moat loop (deferred register, key E).* The *guidance note*: signal-derived, steers but never grounds, lives beside the immutable revision (ADR-0002), visibility follows document access. Needs an ADR, and carries **Q-003**.
- **Q-003 — Signal-derived guidance crossing organisations.** **[B]** · *Blocks: Q-002.* A guidance note's visibility follows document access, so once the owner shares a deliverable the note — generated from one organisation's edits and agent interactions — becomes visible to another organisation. A deliberate scope choice, not the org-private informing rule (ADR-0020); the residual is whether signal-derived steer carrying one organisation's private approach should be scrubbed or re-scoped first. Settle with **Q-002**.
- **Q-035 — Who answers a person about their own data.** **[C → owner/legal, plus a ruled product half]** · *Blocks: **nothing on the board**.* **⚠ Narrowed 2026-08-26, and the narrowing is the point.** This question had been written as *"Controller or processor, and for whom"*, blocking the DPA — and it was **two questions wearing one label**. The **legal** half (which characterisation applies) turns on who decides the purposes and means of processing, which is a matter of fact about the arrangement and is **advice a solicitor gives, not a ruling a grill session makes**; it leaves the tracker. The **product** half — who the platform points a person at when they ask about their own data — was real, and was **ruled 2026-08-26**: see below. The DPA is a **lead-time item, not a gate** (plan.md gate 1, struck the same day); ADR-0050 supplied its positions and it can be drafted today. **✅ The product half, ruled:** *the record decides, not the organisation.* Whatever act lands in the **project review record held in the library owner's project** — a reviewer's comment, an acceptance code, an authoring-side response — the **library owner** is the party that answers a person asking about it, and Infora forwards rather than refusing in its own name. Symmetrical across both sides of the cycle, and it holds when the person's own employer has left the project. A sandbox-scope record is its own organisation's and answers for itself. Recorded as an addendum to [ADR-0050](../architecture/adr/0050-the-privacy-programme-operator-access-and-deletion.md); reasoning in [grill-history.md](grill-history.md). **What remains open and is genuinely a fork:** *(retained below, because the divergence-at-exit case is not answered by the rule above.)* Raised 2026-08-03, having surfaced **twice** during the privacy session without an answer either time. [personal-data.md](../architecture/personal-data.md) already recorded the model as owner-deferred; what changed is that ADR-0050 hit its edge. **The concrete failure:** a named reviewer at a **departed** consultancy asks, eighteen months later, for their name removed from the owner organisation's review record. ADR-0050 decision 8 rules that attribution is **retained** — but it does not rule *who answers the person*, and Infora replying "no" to an individual exercising a personal right is a materially different act from Infora forwarding that request to the party who owes the answer. **Recommendation:** Infora is **processor** for both firms. The label is the easy half; the real shape is that Infora is processor for **two controllers whose interests diverge at exit** — Org A retaining what Org B wants erased — and the individual's request belongs to **Org A to answer, with Infora forwarding rather than refusing**. **Stress test:** a processor acts only on the controller's documented instructions, but ADR-0050 decision 7 gives the **owner organisation** a removal lever over material the **producing** organisation created and may still owe its own client a copy of. Two controllers, one object, opposing instructions — and Infora executing either one is acting against the other. Does the DPA need to name which controller wins per object type, or does the answer collapse into Org A being sole controller of the project library and Org B sole controller of its sandbox? **↩ One fact for whoever drafts the DPA, recorded 2026-08-26 rather than left as a question:** [ADR-0026](../architecture/adr/0026-distillation-egress-boundary.md)'s amendment adds a **second processing purpose** — a de-identified characterisation of user behaviour crossing to Infora to improve the shipped product. Nobody instructs it; it is Infora's own purpose, not either firm's, so it is **not** processing carried out for a controller and the agreement should say so plainly rather than fold it in. That is a drafting fact, not a design fork, which is why it sits here as a note and not as an open question.

- **Q-045 — Who at Infora may read signal material, and how far does "eyes off" still reach.** **[B]** · *Blocks: the craft path's abstraction step (🌫 fog in Slice E) — **and nothing else**. Corrected the day it was raised: it was written as riding with the DPA, which was the same over-weighting `Q-035` had just been narrowed for. A DPA can describe the craft path in general terms; the access control tightens when the step is built.* Raised 2026-08-26 by the signals session, which reversed ADR-0026's cross-organisation pooling prohibition and thereby created an Infora-side read path that [ADR-0050](../architecture/adr/0050-the-privacy-programme-operator-access-and-deletion.md) never contemplated. **The user situation: none — there is no screen.** This is entirely about what Infora's own staff may do. **The concrete failure:** ADR-0050's headline claim is *"no human holds a standing credential to customer data"*, and the craft path is defended on the ground that what crosses is de-identified and therefore not customer data. But **somebody has to know the abstraction step is actually working** — that it is emitting *"the author deferred a significance verdict"* and not *"the author changed 54 dB at Willowbank Farm"* — and validating that means looking at what went in. A de-identification step nobody is allowed to audit is a promise, not a control. **Recommendation:** a **third role** beside ADR-0050's two, scoped to signal material only, break-glass rather than standing, audited, and time-boxed — with the abstraction's *output* sampled routinely and its *input* reachable only on a recorded, reasoned act. **Stress test:** ADR-0050 rejected support access in V1 outright, and the only shape it said one might ever take was customer-initiated. This role is Infora-initiated by construction, since the customer has no reason to ask for it — so either the "customer-initiated only" line was about support and not about all access, or this needs a carve-out that weakens the sentence the privacy programme is sold on. And the honest floor: if no human may ever see the input, the de-identification claim rests on a test suite over data nobody has read.

- **Q-029 — What an unentitled user is told, and whether it can be anything.** **[B]** · *Blocks: PERM-01's second half; the honesty half of every refusal a user meets.* Raised 2026-08-01 while authoring the eval seed set (T-259). The seed table specifies PERM-01 as *"a user with no Participant gets nothing, **and is told the question cannot be answered from what they can reach**"* — and the second half **cannot be built as written**. Denial and nonexistence read identically (contracts principle 4), so an unentitled requester gets `404`, and telling them "this cannot be answered from what you can reach" distinguishes a project they cannot reach from one that does not exist. That is the leak principle 4 exists to close, and it is not a small one on a platform whose product is a wall between competing consultancies: "which schemes does this firm work on" is commercially valuable and is exactly what the message would leak. **The fork is real in both directions.** A user who asks a reasonable question and gets a bare "not found" experiences a broken system, and the refusal-must-be-actionable principle applies everywhere else in the build (T-249's label refusal names both labels; T-246's grant refusal names the exclusion). **Candidate shapes to weigh:** (a) accept the bare refusal and carry the explanation in the *surface's* empty state, which knows only that this user has no projects and leaks nothing; (b) distinguish "you are a Participant of nothing at all" — which is an account fact the user already knows — from "you cannot reach *this* project", which is not; (c) an owner-configurable disclosure, which is how the underlying question is really "whose secret is it". **Stress test:** if (b) is admitted, a user removed from one project of several still learns the difference between the two cases the moment they compare, so the boundary is between *account-level* and *project-level* facts and not between phrasings. *(PERM-01 ships today asserting the refusal itself, which is the half that is buildable; the case file records why the other half is absent rather than dropping it silently.)*

- **Q-040 — Issuing a document to someone with no Infora account.** **[A/B]** · *Blocks: the external-issue tickets, unminted per the Q/T boundary; [v1.md](../build/v1.md) now names the capability **in scope for the pilot**, so this is the only V1 capability whose shape is still open.* Raised 2026-08-17 (owner). **The user situation:** the project needs to issue a promoted deliverable to a party who is not on the project and never will be — a landowner, a consultation respondent, a supplier engaged for one piece of work. **Today there is no path at all:** ADR-0035 issues to an *organisation* holding a Membership, and ADR-0016's default-deny means no Membership is no visibility, full stop. **What the owner would see:** pick the deliverable, choose "issue externally", type an email address; the recipient receives a link and the file, and sees nothing else of the project — no roster, no library, no sandbox. **Recommendation:** a **third transmittal kind**, not a second issue-event — the audit facts are identical (sender, deliverable, version, purpose code, date), and forking the record would cost the single place "who was this issued to" is answerable. The recipient is a **recipient record** (name + email), never an Organisation or a Participant, so no Membership is created and no clause of the wall changes. The link serves **one named version** and expires; there is **no acknowledgement gate** — the download *is* the receipt, recorded — and supersede does not retract an issued link, because an issued document is a snapshot, which is the ISO 19650 position. **Personal data:** the recipient record is the first place the platform names a person who has no account — it lands in [personal-data.md](../architecture/personal-data.md) at ruling. **Stress test:** the recipient forwards the link, so "who received this" becomes a claim about who was *sent* it rather than who read it — is that weaker than the emailed PDF this replaces, which has the same property, or does hosting the file make Infora answerable for the difference? And on the producing side, ADR-0035's addendum shows a producer only that issues *occurred*, without the recipient list — so Org B would learn its deliverable had left the platform and never to whom.

- ~~**Q-036 — Who may end another organisation's deliverable.**~~ ✅ **Ruled 2026-08-27** → amendments to [ADR-0013](../architecture/adr/0013-supersede-withdraw-states.md) (with 0003, 0041, 0045, 0011, 0049). **The two ADRs never disagreed** — ADR-0013's withdraw and T-189's plan-row removal are *two different acts sharing one enum value*, and the build implemented only the second. **Authority follows the publication boundary, not the party**: pre-publication the record is the producing organisation's, once published into the library it is the owner's, with the producer proposing — the record-scope principle ruled the day before, applied to a lifecycle boundary. **Supersession by a different document is a confirmed `supersedes` edge; withdrawal is a state**, because nothing replaces it and there is no second endpoint. Ticketed as **Slice Document Status (T-383–T-391)**, absorbing T-301's remaining half. Record in [grill-history.md](grill-history.md). *(Original entry retained below for its stress test, which the ruling answers.)* Raised 2026-08-04 by T-301, which found it by trying to build the thing. **The user situation:** the owner organisation's project lead opens the Documents view and sees a consultant's accepted deliverable that a newer study has overtaken. Today there is **no button**, and there is no way to make one without answering this. **The mechanism, plainly:** a deliverable carries a state — live, superseded, withdrawn, rejected — and only `live` grounds, so setting it is how the owner stops the AI answering from a stale document. **ADR-0013 says supersede and withdraw are "owner-set states". ADR-0033 and T-176 built the opposite** — every container write in the API is guarded by `producingOrganisationId === slice.organisationId`, commented *"even the owner edits only its own rows"* — and nothing in the codebase sets `superseded` at all. So the two rulings disagree, and the build followed the later one. **Recommendation:** the owner may supersede and withdraw a deliverable **in its own library**, as the first cross-organisation container write, audited and reason-stated — this is what ADR-0050 decision 7 already assumes when it gives the owner the removal lever. But the producing organisation's existing `/containers/:id/restoration` must **stop being symmetric**: as built, a member can restore what the owner withdrew, and neither act leaves a record of the other. **Stress test:** the consultant is contractually obliged to keep its issued deliverable available to its own client, and the owner has just made it ungroundable. If the answer is "the owner wins", the member firm's copy obligation is met by a document the platform now treats as stale — and if it is "the member wins", the owner cannot stop its own library grounding on a study it has superseded. *(Note the ordinary case is untouched: promoting a new version supersedes the prior one structurally and automatically. This is only the deliberate act on a container.)*

### Retrieval

- **Q-028 — Who selects the retrieval scope.** **[B]** · *Blocks: wiring T-242; belongs to Session 6.* The ontology slice (O) part 1 built the ontology's semantic pre-filter but **nothing populates it**: `AssemblyRequest.request` is `{ text, mode }`, so `classificationTermIds` is structurally unreachable from the agent path and every run scans the whole library. ADR-0045 settles how the agent classifies *documents*; it does not settle how a *question* becomes a scope. **Recommendation:** the scope filter is a declared, auditable part of the plan artefact — selected pre-retrieval, recorded on the run, visible to the user — never an implicit narrowing inside the retrieve leaf. **Stress test:** a wrongly-scoped question grounds a confident, fully-cited answer on a partial library; every citation resolves, so neither ground-check nor the user can see what was excluded. What makes a wrong scope *visible*, and is the fallback widen-and-retry or refuse? Until answered, leaving the lever unwired is the safe state, not a bug. *(Measured 2026-07-31: scoping one term cut a 20k-chunk project query from ~133 ms to ~6 ms — the stakes are real on both sides.)*

- **Q-038 — Do reviewers approve responses, and what does approval gate?** **[A]** · *Blocks: nothing on the board — the built flow closes rounds without it.* Raised 2026-08-09 by the component-5 code review behind the user-story walkthrough. **The user situation:** version two is back. The lead reviewer's group reads the consultant's responses beside their comments — [user-stories.md](../architecture/user-stories.md) says reviewers "approve the responses they are satisfied with, keep open the ones they are not" — but on the built screens a response has no state at all: nothing to approve, nothing to keep open, no way to tell a satisfied reviewer from one who has not looked. **The mechanism, plainly:** a per-reviewer verdict on a response (approved / kept open), stored like the ADR-0052 completion signal and visible to the group. **Recommendation:** reviewer-side positioning only — it informs the lead's verdict and gates nothing (ADR-0005's no-gate rule: the lead's code closes rounds, never a count), and "kept open" pre-fills that reviewer's next-round comment rather than blocking acceptance. **Stress test:** the lead applies an accepting code while two responses stand kept-open — if approval gates nothing, what did the reviewer's act mean; if it gates acceptance, a silent reviewer holds the contractual decision hostage, which is exactly the clock ADR-0005 refused to build.
- **Q-039 — A plan-locked shared sandbox discloses the whole TIDP's shape.** **[B]** · *Blocks: nothing built — T-365 shipped; the exposure exists only if an owner both plan-locks a sandbox and grants it across the wall.* Raised 2026-08-09 by T-365's adversarial review. **The user situation:** a producing organisation plan-locks a cross-org shared sandbox (a deliberate, owner-gated share, ADR-0036/0018). The derived tree now names **every live row of that organisation's plan** — references, titles, disciplines — as folder names, to every granted organisation, including people the plan read itself denies (`GET /plan` is owner/producer only, ADR-0008). Nothing leaks by accident: each grant is an explicit act. But the grant admits people to a *working area*, and the mode silently upgrades that to a read of the whole TIDP's shape — the sharer may have scoped the sandbox for one narrow collaboration. **The fork:** (a) accept it and say so in the settings copy ("locking a shared sandbox to the plan shows every granted organisation your plan's structure"); (b) refuse plan-locking on sandboxes with live cross-org grants (and refuse the grant on a plan-locked sandbox) until the owner rules; (c) derive only rows *bound to documents in this sandbox* for shared sandboxes. **Recommendation:** (a) for V1 — the share is already owner-gated and wall-deliberate — with the copy stating the consequence; (b)/(c) only if the owner reads the TIDP's shape as commercially sensitive between its own suppliers. **Stress test:** two consultancies on one project, one granted into the other's plan-locked sandbox for a joint deliverable — supplier A now reads supplier B's entire delivery schedule shape; is that a wall breach or ordinary project transparency? The wall hides *work*, and a plan's shape sits between work and presence.

### The record

- ~~**Q-041 — Where the review record lives.**~~ ✅ **Ruled 2026-08-22 (owner): its own pane.** Raised by T-375 as the one fork its approved mockup left marked *"needs your yes/no"*, and answered as built — the record keeps its own route (`review/:containerId/record`), so it is a place you can send someone rather than a view of a screen, and the round tray stays the working surface it is. Record in [grill-history.md](grill-history.md).
- **Q-042 — Does the internal QA lead give the undertaking too?** **[A]** · *Blocks: nothing — the built exemption is ADR-licensed.* Raised 2026-08-22 by the slice-walkthrough-2 audit. **The user situation:** inside one firm's own sandbox, a colleague is named internal QA lead and the QA round simply opens — no Accept click, because sandbox rounds are born open (ADR-0051 §4: a firm should not acknowledge its own submission to itself) and the acceptance gate rides the acknowledgement. Yet the QA verdict is what promotion issues to the client, and the appointment surface at that scope shows the same undertaking card asking for a yes that nothing waits on. **Recommendation:** keep the exemption — the internal verdict is org-private QA, not the contractual verdict the undertaking exists for — and say so on the card at that scope. **Stress test:** the same fork hides a second one — at sandbox scope a declined QA appointment's *reason* is readable by nobody but its author, because "owner-organisation-private" names the wrong organisation on a container the owner cannot even see; whoever answers this question should say who reads a QA decline reason.
- **Q-043 — What does a declined reviewer's history still let them do?** **[A]** · *Blocks: nothing.* Raised 2026-08-22 by the same audit. **The user situation:** a reviewer marks "review complete" on the open round, then declines their lead appointment for the next. As built (T-372), the decline strips every reviewer act at once — so their standing completion mark can never be withdrawn (it renders forever), and they can no longer fix a typo in a comment that stays attributed to them on the permanent record. **Recommendation:** authorship of what they already wrote is a separate standing from the appointment they refused — let the author edit their own comment while the round is open, and let a completion mark be withdrawn by its owner regardless of the grant's state. **Stress test:** if a declined reviewer can still touch their comment, the wall must be clear that this is authorship, not membership — they gain no read on anything the decline lost them.
- **Q-044 — Resigning a lead appointment after accepting it.** **[A]** · *Blocks: nothing.* Raised 2026-08-22 by the same audit. **The user situation:** a lead reviewer accepted three months ago; they are leaving the firm's project team next week. There is no resignation act — decline is refused once accepted — so the only exit is the T-352 side door: as live confirmed lead they may revoke their own grant, which works but records **no reason**, the very thing the decline design insists a refusal must carry. **Recommendation:** a resignation act on the accepted grant — reason mandatory, revokes the grant, same one-live-lead consequences as a decline — so the record reads "resigned, because" instead of a bare revocation. **Stress test:** ADR-0033 §2's "the way out is re-appointment, never an override" was written about *others* overriding the appointee; a resignation is the appointee's own act, so it needs no ADR amendment — confirm that reading before building.
- **Q-047 — A declined withdrawal proposal leaves no record.** **[A]** · *Blocks: nothing — the built flow works; this is about what the record can later prove.* Raised 2026-08-28 by the Slice Document Status review. **The user situation:** a consultant proposes withdrawing its own published study (T-384's propose path); the owner declines. The proposal — its reason, its proposer, the fact it was ever made — **vanishes**: it rode the container's two withdrawal columns while state stayed `live`, and the decline clears them. Eighteen months later nothing can show the producing firm flagged its own study, which is precisely the fact that firm would want on the record if the study is later found wanting. **The mechanism, plainly:** the slice deliberately stored a proposal in the columns the act would fill (no proposals table was drawn), with record state telling proposal from act — a clean bet for the happy path, silent for the declined one. It also admits only **one** pending proposal, and the producer cannot retract its own (it asks the owner to decline — an act then recorded nowhere). **Recommendation:** follow the repo's own precedent — `elevated_refusals` exists because *an attempt is data exactly as a completed act is*, and the people who'd want a refusal gone are the people holding the lever. A small append-only `withdrawal_proposals` record (proposer, reason, outcome, who resolved it), the columns keeping their current role for the live proposal. **Stress test:** the decline reason cuts the other way — the owner declining is the owner making a claim about the producer's own study; is *that* reason owner-private, container-visible like the withdrawal reason itself (ADR-0013 §4), or not required at all? Whoever rules this should also say whether a declined proposal may be re-raised unchanged, or must say what changed.
- **Q-048 — Does an out-of-scope refusal belong in the run record?** **[A]** · *Blocks: nothing — the path is built and unreachable in the shipped configuration, because the default classifier never returns this outcome.* Raised 2026-08-28 by T-266, which built the classifier's fourth outcome and found the design names *what to say* and not *what to keep*. **The user situation:** a consultant asks the agent something the product does not do — "book me a meeting with the ExA", "what's the weather at the site" — and the classifier decides it is out of scope. The screen says so and says why, which is ruled. **What is not ruled is whether anything is written down.** Today nothing is: the refusal is a 400 and no Run row is opened, which is the reversible choice. **The fork.** *Record it* — the request text is already part of the record for every other run (`runs.request`, ruled 2026-07-06), a run that was asked for and refused is a fact about what the agent was used for, and the producing organisation's own cost and usage picture is incomplete without it. *Don't* — an out-of-scope refusal spends no model call and produces no work product, so a Run row would be an audit entry for something that did not execute, and the record's value is that everything in it happened. **Recommendation: record it, as a completed run with no steps and the refusal as its response.** The record already distinguishes states, `runs.request` is already the prompt text, and the alternative means the one class of interaction with no trace is the one where the user was told no — which is the class an incident review would most want to see. **Stress test:** an out-of-scope refusal is the cheapest thing to trigger repeatedly, so recording it makes the run table trivially floodable by anyone with a session — is that a rate-limiting problem (T-217 already throttles runs per user) or a reason the refusal should stay outside the record? And a second: a *misclassified* refusal is a product defect, and a defect with no record is one nobody can count.
- **Q-015 — The audit record: retention, cancellation, and granularity.** **[B]** · *Blocks: Q-001, Q-018.* Substantially ruled 2026-07-12 (T-104): the record is retained background data anchored to the work, producing-organisation-private, never a review surface — the consultant carries the professional liability. **Still open:** retention and expiry (may unaccepted refine-chain suggestions or old chat runs ever be deleted?), the cancellation state (**Q-010**), whether ad-hoc chat deserves a lighter record than governed work, and whether provenance ever re-surfaces document-anchored on an insurer or regulator demand.
- **Q-010 — Cancelling a run server-side.** **[A]** · *Blocks: nothing; decide with streaming.* T-097's cancel aborts the client's wait; the run completes and stands in the record. A real Stop needs a Run state-machine ruling — a `cancelled` terminal state vs `failed` with a cancellation rail outcome — and an abort path through the chain. - **Q-049 — The extractor as a tool.** **[B]** · *Blocks: the extractor's tickets — held as **fog** in Slice V1-T per the Q/T boundary rule, exactly as the QA checker was.* Raised 2026-08-30 by the checker session, when V1's tool set grew from two standalone tools to three. **The user situation:** a consultant must pull every commitment across twelve chapters into a register before submission. - **Q-034 — What an assistive agent inside a surface knows.** **[B]** · *Blocks: any in-surface assistant that **advises** rather than transcribes — the judgement residue of the review-cycle preflight, and the sandbox reorganiser (post-V1, and also blocked by `Q-020` and `Q-031`).* Raised 2026-08-03 alongside Slice V1-S. **The plumbing is already ruled three times over and is portable** — ADR-0027's never-apply, ADR-0048 §3's fixes riding the existing Suggestion mechanism, the Word add-in's tracked changes: an assistant proposes into whatever human-resolved queue its surface already owns, and gains no write path that surface lacked. **The content is not portable, and has no home.** An assistant that advises on an object must know what *good* looks like for that object, and there are four candidate homes, none right: a **worker's prompt** (TypeScript — a domain expert cannot edit it, which is the failure the Lens's `AUTHORING.md` and hot-reload exist to prevent); the **guiding channel** *(note 2026-08-30: ADR-0048's channel was corrected the same day — org context steers via the **informing** channel; read "guiding" here through that correction, the reasoning is otherwise unaffected)* (right *role* by ADR-0048's test — a rule about how to build a schema instructs the author rather than stating a fact about the scheme — but wrong *scope*, being org context, while ISO 19650 competence is Infora-wide); the **authority corpus** (the correct home, ISO 19650-2 and BS 1192 being published external instruments — and stubbed out of V1 in both tiers); or a **new declarative family beside the Lenses**. A schema assistant has no way to retrieve "the codes already allocated against this schema", and will confidently propose renaming a key that 500 containers are coded against. Same shape as **`Q-028`**, and the more fundamental instance of it. **Recommendation:** a declarative pack per object type on the Lens's proven pattern — file-based, validated at startup, expert-authorable, failure messages naming the file, field and rule — and treat the assembly gap as Session 6 work rather than widening the gateway ad hoc for one surface. **Stress test:** the moment a firm wants *its own* conventions in a pack, that content is org guiding material — and the deliverable schema is a **project-wide, owner-controlled** artefact that two other organisations build their TIDPs against, so Org B's conventions would be steering proposals into Org A's queue. The wall arrives through the content, not through the button. *(Deliberately sidestepped by **Slice V1-S**, which transcribes a user's own upload rather than advising and therefore needs no pack — that is precisely why it could be specified and this could not.)*

### Tier 2 — Moat & sophistication (post-MVP) — bucket (B), must-still-grill
*No precedent in Legora (single-firm); these are Infora's cross-org / confidentiality divergences (reference doc §10). Keep the slow adversarial method here. Defer until the skeleton runs.*

#### Session 4 — Knowledge distillation, provenance, and staleness
- **Depends on:** Session 3 ✅. The "knowledge grill" deferred during retrieval; builds the distillation *engine* whose boundary ADR-0026 already fixed.
- **The question:** > Decide how Knowledge is distilled from Sources and Signals: automatic, manual, or both, and who holds curation authority — including whether a consultant's distilled Knowledge can enter owner-controlled project Knowledge. Define the Source→Knowledge flow end to end. Give distilled Knowledge **provenance** back to its source and a **lifecycle**: when a source deliverable is superseded/withdrawn (ADR-0013), what happens to Knowledge distilled from it.
- **Outcome:** distillation + Knowledge-currency ADRs. Must honour ADR-0026's two filters and the manual-curation admission, and the Session-1 ruling that distilled Knowledge cites *through* to a source.

#### Session 5 — Precedent selection and application
- **Depends on:** Session 3 ✅.
- **The question:** > Decide how precedents in a firm's org context are selected and applied to a new project: how a relevant precedent is found, brought into a draft, and constrained by the Session-3 confidentiality boundary. Settle whether precedent application is grounding or informing (currently **informing**), and how a precedent's origin is or isn't surfaced.
- **Outcome:** an ADR if selection/application carries a real trade-off (the open "precedent selection within the informing channel" item).

#### Session 6 — Retrieval, ranking, merging & store choice *(finish)*
- **Depends on:** ADR-0022/0024 ✅; the MVP slice (M3) done first.
- **The question:** > Settle: **Library RAG strategy** — the contextual-retrieval problem ("everything about x *in the context of y*"): query decomposition into semantic intent + scope filter, the ingestion metadata that enables it, and modelling relationships between deliverables. **Full channel ranking & budget** (beyond M3's naive merge), incl. org-vs-programme precedence — note the **guiding-over-informing conflict precedence is already fixed** (2026-07-06, ADR-0029 §5) and constrains this ranking. **Per-viewer citation rendering** for shared deliverables.
- **Outcome:** RAG-strategy and ranking ADRs. pgvector is fixed.
- **⚠ Sharpened 2026-07-31 → carried as [Q-028](#retrieval).** The ontology's semantic pre-filter is built (T-242) but structurally unreachable from the agent path, so *who selects the retrieval scope for a given question* is now the concrete half of this session — with a recommendation and a stress test already recorded. Answer Q-028 and this session gains its scope-filter half; the ranking and per-viewer-citation halves are still open independently.

#### Session 7 — Signal capture into Knowledge (the moat loop)
- **Depends on:** Session 4.
- **The question:** > Decide how accept/edit/reject Signals feed back into the curated store: a live Signal→Knowledge path in v1 or training-data-only for now; who curates; how cross-organisation Signal data respects the walls. Define the Signal sink so the moat compounds, not merely captures.
- **⚠ A second half, added 2026-08-26 — the craft path.** ADR-0026's amendment gives this session a destination it did not have: **Infora's own** shipped domain layer, alongside the organisation's own store. So the sink is now two sinks, and the new one owns the harder mechanics — **the abstraction step** (a model call that reads an edit and emits a characterisation of *what kind of change* was made, running **inside** the customer's boundary so the raw row never moves), what a de-identified craft record's schema actually is, how corroboration across organisations is counted, and where the human at Infora sits. The behavioural half de-identifies mechanically; the **Teach** half is authored prose that can name a scheme in a sentence and needs real abstraction with a named curator. Nothing here is ticketed — it is 🌫 fog in [the deferred register](../build/plan.md), per the Q/T boundary, and there is nothing to collate across until a second customer exists.
- **⚠ Carve-out, added 2026-08-01 — Session 7 will not reach all the personal data.** Session 7 is the right home for **Signals** as personal data, but **T-254's cost attribution is already built and shipped**: `GET /organisation/costs` aggregates at organisation *and named-user* grain, so it is **per-person usage data live in V1**, and it is **not a Signal** — nothing in this session's scope touches it. It needs naming in [personal-data.md](../architecture/personal-data.md) and in the DPA regardless of when Session 7 runs.
**Outcome:** an ADR for the Signal sink — **constrained in advance by ADR-0026:** "training-data-only" must mean de-identified/aggregate, never a shared model on client data.
