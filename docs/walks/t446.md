# T-446 — the acceptance walk, photographed (2026-10-19)

**In plain terms:** an agent walked the app builder in the real running product,
signed in as the seeded people, with made-up figures, and photographed every
step. It built two apps: the monthly sustainability returns app (built by
talking to the agent) and a ground-investigation cost dashboard fed from a
spreadsheet. Nothing was fixed along the way. Every problem found is in the
**Defects** list at the end, each pointing at the shot that shows it. The
verdicts — whether the builder is finished, and blocks versus code — are the
owner's, given on this evidence.

**Headline:** the product got through both apps end to end, and the
separation between firms held at every point it was tested. But the building
agent is unreliable: some of its answers were thrown away whole, and twice it
said it had made changes it never made. The dashboards also have two problems a
client would notice straight away: months in the wrong order, and old
spreadsheet rows listed beside the current ones.

## How the walk was run

- **Where:** a separate copy of the code at `main` (773b924), its own database,
  the web app, and the in-browser spreadsheet editor (Collabora), all on this
  machine. The owner's own working copy was not touched.
- **Who:** Eleanor Price (Calder & Hale, builds apps); Owen Vance (Calder &
  Hale, may not build — used as a contractor and for the refusal shots); Nadia
  Okonjo (Redgate Ecology, a contractor); Rachel Bowen (Trentmoor Energy, the
  client and project owner).
- **The agent was real** — the same Claude model the product is configured
  for, not the scripted stand-in the automated tests use. To reach it at all,
  the walk had to declare four settings saying the model service is UK-hosted
  and keeps no data (see Defect 1). **Those declarations are not true of the
  development key used.** The owner authorised them for this walk only,
  because every figure in it is invented.
- **Figures:** all dummy. Six months of returns (May–October 2026) for each of
  the two contractor firms, and an eight-month cost report (March–October
  2026, then November added).
- **What went through the browser and what did not:** every shot is the real
  browser. One return (Nadia's October) was typed into the form on screen. The
  other ten were entered by the contractors themselves (each signed in as
  themselves) straight to the server, to save typing. It is the same act the
  form performs, and the same rules apply.
- **Shots** are full pages, 1440 pixels wide. Tall pages are tall because the
  app scrolls inside its own panel, and the shot shows all of it.

## The blocks-versus-code evidence

The shots for this verdict are **26–29** (the returns dashboard and its three
charts, close up) and **60–61, 65, 71** (the cost dashboard at each version of
the spreadsheet). What they show, without a verdict:

- The cost dashboard (one firm's figures, one row per month) draws well: a
  total, bars and a line with a trend, all matching the spreadsheet.
- The returns dashboard could not draw what was asked for. A chart can only
  group by a column in the table, and "which firm entered this row" is not
  one — so "electricity by contractor" cannot be built from the blocks.
  The agent labelled month-grouped charts "by contractor" without saying so.
- Charts put the months in the order the rows were entered, not calendar
  order, which makes a line chart and its trend misleading.

The owner's statement during the walk, for the co-captain to record (passed on
separately): *blocks are right for the first version; code-built apps later,
but only inside a sealed box that cannot reach across the ethical walls, leak
data, or touch Infora's own software.*
*(Recorded 2026-10-19 as [ADR-0056](../architecture/adr/0056-the-app-model.md)'s
fourth addendum, the board's "Code-built apps" register entry, and `Q-056`.)*

## Defects

Numbered for reference, roughly worst first. None was fixed.

1. **On a fresh setup the agent cannot reach the model, and nobody is told why.** The product refuses to call the model until four settings are declared (where the model is hosted, whether it keeps data, which law applies, what contract covers it). Neither the setup file nor the README mentions them; the conversation says only "could not be reached", and the server log records nothing. — shot 08
2. **The agent's answers are sometimes thrown away whole.** Of the six real build turns in Part 1, two were rejected outright, two changed nothing (Defect 3), and two worked; both turns in Part 2 worked. Cause, found by replaying the request to the model directly (it happened in one of three tries): the agent is told Infora fixes an analysis table's columns, so it sends that table with no columns, and the rules reject the entire answer — including the person's own wall answers it was recording. The model's raw reply is not kept anywhere, so this cannot be traced from inside the product. — shots 09, 13
3. **The agent says it made changes it never made.** When its reply comes as words followed by its structured answer, the product shows the raw answer in the chat as text and changes nothing, while the words say "I've added that column" and "Done". Separately, one message claims a screen the product's own note says was refused. — shots 14, 19, 20
4. **After a spreadsheet is replaced, the dashboard's table shows the old rows beside the new ones**, unmarked; after three replacements it listed 35 rows for 9 months. The total and the charts are right, so the table contradicts them. — shots 65, 67, 71
5. **Charts put months in the order the rows were entered, not calendar order.** October, entered first, comes first; the line and its trend line are therefore misleading. — shots 26, 27, 28, 29
6. **"By contractor" cannot be drawn, and a table cannot be changed once declared.** A chart can only group by a column, and the firm that entered a row is not one; the agent labelled month-grouped charts "by contractor" without saying so. Adding the obvious Contractor column is impossible: neither the person nor the agent can add a column to an existing table. — shots 19, 20, 26, 27, 29
7. **The client cannot accept or reject from the dashboard.** Accept and Reject sit only under "What it holds → Open". — shots 26, 30
8. **A contractor is not told their return was rejected.** No notification; the reason shows only inside the opened table, not on the form screen they use. — shots 35, 36, 37
9. **The written analysis is cut off mid-word, only has combined totals to work from, and counts a rejected return.** — shot 40
10. **A contractor is shown "Close the app" and "Give it to…"**, which the server would refuse them (from the server's rules; not pressed). — shots 21, 24
11. **An empty app says it is ready to open, and can be opened.** — shot 05
12. **There is no way to download a file from the sandbox.** A contractor cannot take their spreadsheet away to edit it. — shot 62
13. **Closing the in-browser editor writes an extra version with no change**, which refills a fed table a second time. — shots 70, 72
14. **The agent says the spreadsheet source works "once Infora is deployed"**; it works now. — shots 54, 55
15. **Every form field is a plain text box**, including the date and number columns. — shots 16, 22
16. **Chart finish:** month labels collide; the line chart has no scale of values; the pie repeats colours; the total has no £ sign or thousands separator. — shots 26–29, 60
17. **The "Not opened yet" label spills out of the app's card.** — shot 03
18. **The export's sheet names carry "(1)" and "(2)"; a rejection's reason is not in the file.** — shot 45
19. **The column matcher did not pair "Cost (£)" with "Cost in pounds".** — shot 57
20. **A deployed copy loses the app's description.** — shot 49

22. **The agent's words ask two of the three open questions; the product adds the third beneath.** Minor, but the two read as different lists. — shot 10
23. **The published app page still carries the old stepped builder's "New table" box, with example text that looks filled in.** — shots 16, 49

## What was not walked, and why

- **Three contractors.** The seed has two contractor firms on Wrenfield (Calder & Hale, Redgate Ecology), so the "three contractors" app was filled by two.
- **Ten of the eleven returns were entered straight to the server**, each by the contractor signed in as themselves, not typed into the form. One was typed through the browser (shots 22–23).
- **The by-contractor charts were not fixed.** After two turns in which the agent claimed changes it had not made — and given that no column can be added to a declared table — the walk stopped and kept the month-grouped charts (Defects 3, 6).
- **Download and edit of the cost report.** There is no download control (Defect 12), so Owen replaced the file with an updated copy prepared outside the product.
- **Correcting the rejected return** (Nadia's "Correct" button) was not exercised.
- **The schedule** is stored as monthly and does nothing until there is a server that stays on, as the panel says. Not walked.
- **The deployed copy in Marchwood** was not opened to that client or filled; the walk stopped at "empty, same steps".
- **The model connection** ran on stand-in settings that are not true of the development key, authorised by the owner for this walk only (see "How the walk was run"). An attempt to log the model's raw replies through a local relay was refused by the session's permission check, so the cause in Defect 2 was found by a separate direct replay instead.
- **The analysis** was run once, by the client. Runs by each contractor (which should each cover only their own firm's returns) were not photographed.

## Reviewed — 2026-10-23, the co-captain

**In plain terms:** before this walk was merged, every claim in it that could
be checked was checked — the thirteen explanations of *why* the product did
what it did were read against the code, and eleven of the 76 screenshots were
opened and compared with what the narrative says they show.

- **The code explanations all held.** Defects 1, 2, 3, 4, 6, 9, 10, 11 and 13
  each name a cause; each cause was found in the code where the walker said it
  was. Two details worth adding: the dashboard table listing every row it
  received is partly *by design* (its own test says so) — the defect is that a
  spreadsheet-fed table's retired rows carry no state at all, so the table
  cannot mark them; and the analysis run would also count superseded
  spreadsheet rows, not only rejected returns (Defect 9 is wider than written).
- **Ten of eleven opened shots matched the narrative exactly.** Shot 20 did
  not: see the review note on it above. Nothing else in the sample was
  overstated.
- **Three things the report did not say:** the walk's one board edit (the
  dated note on T-446's line) is not mentioned in this narrative; the folder
  this walk arrived in was not guarded by the docs check — fixed in the
  merging commit (the folder's README and `scripts/docs-rules.mjs`); and the
  authorisation of the stand-in model settings exists only in this file —
  which is the right place, since the walk is the only thing that used them.
- **The full check passed** on the walk's commit rebased onto main (exit code
  read directly).
