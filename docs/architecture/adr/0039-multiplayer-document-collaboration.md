# ADR-0039 - The editor is multiplayer: a document's agent chat is a shared thread scoped to the sandbox participant set; the informing channel and run internals stay per-invoker, never pooled by the shared thread

**Status:** Accepted (owner-ruled 2026-07-22, producing-side-lifecycle grill). Builds on ADR-0036 (sandbox participant scope), ADR-0025 (assembly environment), ADR-0020 (informing is org-private and portable), ADR-0028 (an agent inherits the invoking participant's slice), ADR-0002/component-4 §7 (the guidance note). References the liability model (T-104).

**Context:** The editor is a shared working surface — several Participants in a sandbox work the same document. But the agent chat's visibility was never ruled: when a user opens the editor chat and asks the agent to draft, is that thread private to them or shared with the document's other workers? An initial recommendation of *private-per-user chat, shared via a suggestions panel* fell to a build fact: the editor produces drafting **inline on the canvas** and accept turns it into ordinary text — there is no persistent suggestions panel. Under private chat a teammate would therefore see only the final text, indistinguishable from typing, losing all visibility into what was asked and how the draft evolved. Separately, once a chat is shared across a cross-organisation sandbox, a precise question arises about the informing channel: does a shared thread pool the participating organisations' private steer?

**Decision:**

**1. The document's agent chat is a shared, multiplayer thread.** A document's **Conversation** (ADR-0028) is shared, not private-per-user: its prompts and responses are visible to the document's **sandbox participant scope** (ADR-0036 participant-private). Teammates work one agent thread — the Claude-in-a-channel pattern, not a private DM. The shared thread, not an ephemeral inline suggestion, is the shared record of how a draft was worked. Signals from accept/reject still fire underneath (the Suggestion/Signal data model persists even without a panel), so the guidance note and the moat loop are unchanged.

**2. Chat visibility follows document access — the same rule as the guidance note.** The thread is shared with exactly the sandbox's participant set and never beyond it. In a single-organisation sandbox the org's team share it; in a cross-organisation shared sandbox the co-authoring organisations do — a scope the owner deliberately opened (ADR-0019/0036). Anything an organisation wants kept private belongs in its own single-organisation sandbox (the default home for its deliverables) or a personal sandbox, not in a shared document's thread.

**3. The informing channel is resolved per-run to the invoking Participant, never pooled by the shared thread.** Informing is org-private and portable — it travels with the invoker (ADR-0025) and never crosses the wall (ADR-0020), and an agent inherits the *invoking* participant's slice (ADR-0028). So when an Org B user fires a run the run reaches Org B's informing; when an Org C user fires a run in the same shared sandbox that run reaches Org C's informing and never B's. Informing binds to the invoker, not to the sandbox or the thread. A run in a shared sandbox therefore draws on three steers at two scopes: the project **guiding** channel and the document **guidance note** (both shared with the participant set) plus the invoker's own org **informing** (private, per-invoker).

**4. Run audit internals stay producing-organisation-private.** The shared thread shows conversational content — prompts and responses. A Run's audit internals (step tree, access-resolved source set, rail outcomes) remain visible only within the producing organisation (T-104). Two scopes held apart: chat content = sandbox participant scope; run internals = producing-organisation scope.

**Consequences:** The editor is **multiplayer** (new glossary term): the canvas, the shared Conversation, edits and the guidance note are shared to the sandbox participant set; the informing channel and run internals are not. A shared thread shares *outputs*, never one organisation's private steer or run internals — consistent with ADR-0026's honest limit (the boundary defeats automated and accidental leak; deliberately-shared outputs in a shared space are shared by construction, because working there was the organisation's choice). The Conversation term gains its visibility rule; the informing channel's per-invoker resolution — already fixed by ADR-0025/0020 — is now explicit for the shared-thread case, which is its non-obvious consequence. Private agent exploration remains available through a narrower or personal sandbox, so nothing forces private work into a shared thread.

**Considered and not taken.** *Private-per-user document chat* (each user's agent thread private, collaboration surfacing only through shared suggestions) — rejected because the editor has no persistent shared-suggestion artifact (drafting is inline, accept becomes plain text), so private chat would leave teammates seeing only final text, with no shared record of the drafting work. *A shared thread that pools the participating organisations' informing* — never on the table: it would breach ADR-0020's org-private informing rule; the shared thread shares outputs, not private steer.

**Open — not decided here.** A deliberate *co-driven* single agent session (two users steering one run in real time, beyond a shared thread of separate runs) is a possible future affordance, not designed here.

**Addendum (2026-07-25, ADR-0043 — the co-authoring substrate):** real-time collaboration splits by format. This ADR's shared multiplayer thread, presence (T-175) and any future Infora CRDT govern **Infora-native authored documents and the agent Conversation**; real-time co-authoring of **Office-format files** is delegated to the Office/WOPI engine (real Microsoft Office via CSPP), which Infora does not build. The two coexist in one surface — the file is co-authored in Office while the shared agent thread grounds against the library and the informing channel stays per-invoker (decision 3, unchanged).
