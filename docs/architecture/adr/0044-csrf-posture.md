# ADR-0044 - CSRF posture: SameSite=Lax session cookies defended by a content-type gate on state-changing requests, an Origin check on the one non-JSON write surface, and no token scheme until the infra/security session

**Status:** Accepted (2026-07-25; built and tested T-218). References ADR-0037 (deployment security posture; the infra/security session is the named upgrade point), T-216 (the CORS origin allowlist this ADR reuses) and contracts §4/§5 (the error envelope the rejections ride).

> Drafted as "ADR-0043" in the owner ruling; renumbered to **0044** on filing because the editing/coauthoring-substrate ADR took 0043 — the same renumber-on-collision precedent as ADR-0037.

**Context:** The API authenticates with an httpOnly session cookie (T-021). Browsers attach cookies to cross-site requests under the cookie's SameSite rules, so a malicious page could try to ride a signed-in user's session — the classic CSRF shape. The exposure here is already narrow: the cookie is `SameSite=Lax`, which excludes cross-site subresource and fetch/XHR/form POSTs and leaves only top-level navigations (GETs, which change no state on this API). The API is JSON-only on every state-changing endpoint except one: the multipart upload (`POST /projects/:projectId/sandbox-uploads`, T-122). A full token scheme (double-submit or synchronizer) is real machinery — issuance, rotation, propagation through the web client and any future Word add-in surface — and buying it now would duplicate work the infra/security session (ADR-0037's named home for production identity) will redo. The question is what minimal, layered defense is proportionate until then.

**Decision:**

**1. SameSite=Lax stays, and is the first layer.** The session cookie remains `SameSite=Lax`. Cross-site POST/PUT/PATCH/DELETE from HTML forms, fetch or XHR do not carry the cookie at all in a modern browser; a rider request arrives unauthenticated and dies at the session middleware.

**2. A content-type gate is the second layer.** State-changing requests (POST/PUT/PATCH) that carry a body must declare `Content-Type: application/json`, or they are rejected `400 { error: 'invalid' }` before any handler runs. A cross-origin HTML form can only send the *simple* content types (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`) — it cannot declare `application/json` — so even in a legacy or misconfigured-browser scenario where the cookie did ride along, the forged request cannot reach a JSON handler. Requests with no body (the bodyless action POSTs — promotion, freeze, revocations, presence heartbeats, `DELETE /auth/session`) are exempt: they are gated on the presence of a body (`Content-Length`/`Transfer-Encoding`), carry no forgeable payload beyond what the URL already encodes, and must keep working without a declared content type.

**3. The one non-JSON write surface gets an Origin check instead.** The multipart upload is legitimately `multipart/form-data`, which is a simple type — the content-type gate cannot distinguish it from a forged form post, and a cross-site multipart POST is a *simple request* that triggers no CORS preflight. For that route the gate instead checks browser-declared provenance against the T-216 origin allowlist: a `Sec-Fetch-Site` of `cross-site`, or an `Origin` that is neither the API's own origin nor allowlisted, is rejected `403 { error: 'forbidden' }`. Requests that declare neither header (non-browser clients, the test harness) pass — browsers always declare `Origin` on cross-site POSTs, so the forged case cannot arrive undeclared.

**4. What is deliberately not a vector, and what is deferred.** Cross-origin `DELETE`/`PATCH` are not simple requests — they always trigger a CORS preflight, which the T-216 allowlist answers bare for unlisted origins — so they are not simple-request CSRF vectors and need no additional gate. A token scheme remains the named upgrade path at the infra/security session, arriving with production identity (ADR-0037); this ADR's layers are the proportionate bridge, not the end state.

**Consequences:** CSRF defense becomes three independent layers (Lax cookie, content-type gate, upload Origin check), each of which alone covers the practical attack, enforced in one middleware ahead of every handler. The web client and e2e suites already send JSON and are untouched; non-browser API clients must declare `Content-Type: application/json` on bodied writes, which well-formed clients already do. Any future non-JSON write surface must either take the upload route's Origin check or wait for the token scheme — a deliberate speed bump. The upload gate trusts browser-declared fetch metadata, which is exactly the guarantee CSRF is about (a browser riding a victim's cookie declares honestly); it is not, and does not need to be, a defense against non-browser clients that hold no stolen cookie.
