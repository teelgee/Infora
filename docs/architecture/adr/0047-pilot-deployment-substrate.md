# ADR-0047 - The pilot deployment substrate: AWS London (eu-west-2), logical tenant isolation, S3 as the real store behind `file_ref`, RDS PostgreSQL with managed PITR, customer-managed KMS keys and OIDC-federated deployment — and a third `pilot` security tier, so the pilot's US-region Anthropic route is *declared and enforced* rather than bypassed; Entra is deferred behind password auth with a named expiry

**Status:** Accepted (owner-ruled 2026-08-01, the infra/security decision session). The **provider**, the **identity deferral**, the **certification pacing** and **where the corpus lands** are the owner's decisions; the mechanics — network topology, key management, secret handling, backup, pipeline shape, and how the pilot's non-conforming model route is made honest — are Claude's, defended here. Extends **ADR-0037** (deployment security tiers; this ADR adds a tier under §2's stated extensibility). References **ADR-0018** (the wall), **ADR-0024** (colocated store, revoke-in-the-same-transaction), **ADR-0025** (the assembly environment), **ADR-0028 §9** (the router seam), **ADR-0043** (WOPI host; `file_ref` as a pluggable pointer). Decided against **[operating-envelope.md](../operating-envelope.md)**, re-cut for V1 the same day.

**Context:** Everything Infora runs on today is a development substrate: Postgres in a local `docker compose`, no object store at all behind `file_ref`, a scrypt password login seeded with one shared dev password, and console logging. [v1.md](../../build/v1.md) names this session as **the gate before any external pilot**, and V1's three-organisation ruling raises the stakes: the ethical wall stops being a property taken on trust and becomes a screen a buyer looks at.

Three findings shaped the session and are recorded because they are the reason the outcome is not the obvious one.

*First, the Microsoft-shaped dependencies do not constrain the hosting choice.* Entra is OIDC and CSPP/WOPI (ADR-0043) is plain HTTP; both work identically against non-Azure infrastructure. The instinct to host on Azure because the customers are M365 shops turned out to buy nothing.

*Second, there is no UK-region route to Claude on any hyperscaler.* Claude in Microsoft Foundry is GA but only on Global Standard and Data Zone Standard (US) deployments, with Foundry EU support still forthcoming; Bedrock's London region does not carry Claude, and Bedrock's EU inference profile routes to Ireland, Frankfurt, Paris, Stockholm, Milan and Spain — the UK is absent. **UK-only inference and Claude are mutually exclusive**, and no configuration yields both. Azure OpenAI in UK South *does* meet a UK-only bar, but only with a regional (not Global or DataZone) deployment plus approval under Microsoft's Limited Access "modified abuse monitoring" programme, which expects a managed EA/MCA customer; absent that approval, prompts are retained 30 days.

*Third, ADR-0037's `standard` tier was buying less than it appeared to.* Its "UK region" line cannot be satisfied by the model the product actually runs on, while the place UK-only genuinely matters — SECRET-capable work — is already answered by the `sovereign` tier with self-hosted open-weight models, precisely because a UK region of a US-headquartered hyperscaler does not escape foreign legal process anyway.

Given those, the owner ruled the pilot runs **Claude on Anthropic's public API**, with the requirement that switching to EU-region Bedrock or to Azure OpenAI be genuine configuration rather than a rebuild. That endpoint is US-region and conforms to neither existing tier, which is the central problem this ADR has to solve honestly.

**Decision:**

**1. AWS London (`eu-west-2`) is the pilot's cloud.** One account, one region, for all customer data at rest. The Microsoft dependencies are protocol-level and do not pull toward Azure (Context); the residency difference between providers evaporated once UK-region Claude proved unavailable everywhere. Nothing here forecloses ISO 27001, Cyber Essentials Plus or SOC 2 Type II — the provider's own certifications are inheritable and audit-log export is available.

**2. Hosting follows the shape the apps already have.** `apps/web` is a Vite SPA that builds to static assets, so it is served from **S3 behind CloudFront** with an ACM certificate. `apps/api` is a Hono node server and the only deployable that touches the database or a model, so it runs as a container on **ECS Fargate behind an Application Load Balancer**. HTTPS only, HSTS, and **AWS WAF managed rule sets on the ALB** — cheap, and it is the first thing a security review asks about.

**3. S3 becomes the real substrate behind `file_ref`, and the API always serves the bytes.** ADR-0043 §1 anticipated this: `file_ref` was "a pointer either way". The bucket has Block Public Access on, versioning on, and SSE-KMS with a customer-managed key. Object keys are namespaced by organisation and project so an object's tenancy is legible from its key alone.

**Bytes are never handed out as a presigned URL to a raw key.** A presigned URL is a bearer capability that outlives the entitlement check that minted it, which would directly contradict ADR-0024's revoke-in-the-same-transaction guarantee and ADR-0036's grant model — the wall would hold at the API and leak at the object store. The API streams from S3 on every read, re-resolving entitlement each time. This costs a little latency and is the reason the wall is enforceable where the bytes are; it also falls out for free, because ADR-0043's WOPI host must serve `GetFile`/`PutFile` itself regardless.

**4. RDS PostgreSQL 17, single-AZ, with managed point-in-time recovery.** gp3 storage encrypted with a customer-managed key; automated backups with PITR at five-minute granularity and a 14-day retention window, which sits comfortably inside operating-envelope.md's RPO ≤ 1 hour. Single-AZ is deliberate at pilot scale: operating-envelope.md commits to 99.5% over business hours with **no SLA**, and RTO ≤ 8 business hours is met by a snapshot restore of a database this size several times over. Multi-AZ is the upgrade when operating-envelope.md's revisit trigger 2 fires, not before.

**The two-role split survives the move and is load-bearing.** The RDS master user runs migrations; the application connects as `infora_app`. On RDS the master is `rds_superuser`, not a true `SUPERUSER`, so it does not bypass RLS — but a table's *owner* does unless the table is marked `FORCE ROW LEVEL SECURITY`. Migration 0034 already sets `FORCE` on `version_chunks`; **T-297 must follow the same convention on `containers`**, or the wall's database backstop is theatre in exactly the environment where it matters.

**5. Network topology: one VPC across two availability zones.** Public subnets carry only the ALB and a NAT gateway. Fargate tasks and RDS sit in private subnets; RDS is not publicly accessible and its security group admits 5432 only from the task security group. S3 is reached over a **gateway endpoint**, keeping object traffic off the NAT entirely. Model-provider egress goes out via NAT. Two AZs is not redundancy theatre — an RDS subnet group and an ALB both require it.

**6. Key management: customer-managed KMS keys, not platform-managed.** Separate CMKs for S3, RDS storage and Secrets Manager, with annual rotation and key policies scoped to the task role and the deployment role. AWS-managed keys would be free and adequate for confidentiality; CMKs cost about a dollar per key per month and produce the artefact a Cyber Essentials Plus or ISO 27001 assessor actually asks to see — a key policy naming who can decrypt. At this price the evidence is worth more than the saving.

**7. Secrets: AWS Secrets Manager, and no long-lived credentials anywhere.** `SESSION_SECRET`, both database URLs and provider API keys live in Secrets Manager and are injected as ECS secret references, never as plaintext environment variables in a task definition. Runtime authorisation is the **task role**; deployment authorisation is **GitHub OIDC federation to an IAM role**. No IAM access keys are issued to a human or to CI — the credential that cannot be leaked is the one that was never minted.

**8. Backup and restore are a rehearsal, not a setting.** RDS PITR plus S3 versioning with a lifecycle rule; backups inherit the same CMKs and stay in `eu-west-2`. Per operating-envelope.md, **a restore into a scratch environment is rehearsed once before the pilot starts and written up**. An untested backup is not a backup, and discovering that during a live pilot carrying a real firm's documents is the failure this line exists to prevent.

**9. Deployment: GitHub Actions, OIDC-federated, migrate-then-deploy.** On merge to `main`: `pnpm run check` (unchanged — *corrected 2026-08-28: `check` is CI's fast half, not a mirror; CI additionally runs the dependency audit, migrate, seed, the eval smoke tier, the build and e2e, and this pipeline step runs the full CI workflow, not `check` alone*) → build and push images to ECR → run migrations as a **one-off ECS task using the owner credential** → deploy the new API service revision → smoke `/health` → sync the web build to S3 and invalidate CloudFront. Migrations run as a separate task with a credential the running application does not hold, which preserves the T-247 role split through the pipeline instead of only in development.

**Two environments only: local development (`docker compose`, unchanged) and `pilot`.** There is no staging. This is a deliberate omission at a scale of one pilot, revisited at operating-envelope.md's revisit trigger 2 — naming it here so its absence is a decision rather than an oversight.

**10. Infrastructure as code: Terraform, in `infra/`, outside the pnpm workspace.** State in S3 with DynamoDB locking. Keeping it out of the workspace leaves `scripts/dep-rules.mjs` and the package graph untouched; the alternative (CDK, which would match the repo's TypeScript) would put infrastructure inside the dependency rules for no gain. The restore rehearsal in decision 8 is only meaningful if the environment can be recreated from source, which is the real argument for IaC here.

**11. Tenant isolation is logical, and that is the designed position.** One deployment, one database, three organisations; isolation is the application wall (ADR-0018) plus RLS (T-247 landed on `version_chunks`; T-297 remains on `containers`). Not per-tenant databases, not per-tenant buckets. ADR-0037 already makes the **deployment** the physical isolation boundary and rules that a client spanning classifications runs separate deployments — so a client demanding physical separation pulls an existing lever rather than forcing a re-architecture. Adding per-tenant infrastructure now would build that lever twice.

**12. A third security tier, `pilot`, is added — because the alternative is a lie.** The owner ruled the pilot runs Claude on Anthropic's public API. That route is US-region and conforms to neither `standard` nor `sovereign`, so ADR-0037's router refuses to dispatch and **fails closed, correctly**.

There were two dishonest ways out and one honest one. Relaxing `standard` to admit `us` would silently degrade the guarantee for every future deployment that selects it. Bypassing the router at the call site would convert an enforced invariant into a comment. Both destroy the property ADR-0037 exists to create — that the posture is *provable per call*, not asserted. So instead this ADR uses the extensibility ADR-0037 §2 explicitly promised ("adding one is a policy addition, not a structural change"), and declares a tier whose attributes are **true**:

| axis | value | why it is honest |
|---|---|---|
| `region` | `us` | Anthropic's public API is US-region. Stated, not hidden. |
| `retention` | `zero` | **Only valid under a zero-data-retention agreement with Anthropic** — see the precondition below. |
| `jurisdiction` | `foreign-reachable` | US legal process reaches it. |
| `eligibility` | `enterprise-zdr` | A third-party API under an enterprise contract. |
| `classifications` | `official` only | The tier refuses anything above OFFICIAL, enforced. |

Four constraints keep the tier from becoming a back door:

- **The ZDR agreement is a precondition, not a formality.** Anthropic's commercial API retains data for trust-and-safety purposes absent a zero-retention agreement. Until one is in place, `retention: 'zero'` is false and **the tier must not be used** — the attribute would be a lie told to our own router, which is worse than no router. *(Note: "no training on our data" is already the default for commercial API use and is not what is being sought; the ask is specifically the retention waiver.)*
- **Sequencing, owner-ruled 2026-08-01: obtaining it is the *last* step, not the first.** The tier is built and tested without it (T-319); what waits is switching a deployed environment to it, which is its own ticket (T-333) so the final step is visible rather than assumed. Development is unaffected — it runs at `standard` with locally declared attributes, and the suites run on conforming fakes. **The risk is recorded rather than dismissed:** deferring the conversation does not shorten it, so a late start moves the pilot date by however long the agreement takes.
- **The two vendors' gates are split deliberately.** The router checks conformance on the **embedding** route as well, and embeddings run on the **ingest path** — so leaving both behind one gate would block loading the corpus into the pilot environment until Anthropic signed, putting a slow operator action behind a clock we do not control. Embeddings therefore move to Bedrock (decision 13's second adapter), whose no-retention posture arrives with the AWS agreement and needs no separate negotiation, leaving **only generation** waiting. This makes decision 13's second embedding adapter a **sequencing dependency**, not merely a portability proof.
- **It is never a default.** `standard` remains the default in `apps/api/src/env.ts`; a deployment runs at `pilot` only by saying so explicitly.
- **It is the only tier permitted to carry `us`**, so the whole residency posture stays readable in one glance at `TIER_POLICIES`.
- **It expires.** operating-envelope.md's revisit trigger 2 — any paid contract — ends its validity. The name is deliberately self-limiting: a tier called `pilot` cannot quietly become the production posture the way a relaxed `standard` would.

**13. Provider portability is proven, not asserted.** The owner's requirement is that swapping to EU-region Bedrock or Azure OpenAI be configuration, not a rebuild. Today there is exactly one `ChatAdapter` (Anthropic) and one `EmbeddingAdapter` (Voyage), and **an interface with one implementation is an assertion, not a seam**. So portability is demonstrated by building a second of each — a Bedrock chat adapter and a Bedrock embedding adapter — with route attributes and tier supplied by configuration, and tests asserting both that a configuration change switches the route and that each tier fails closed when nothing conforms.

Embeddings are pinned per index (ADR-0024), so a provider switch forces a deliberate re-index rather than a silent mix. At 100–500 documents that re-index is minutes — which is exactly why proving the swap now is cheap, and why proving it at a hundred thousand documents would not be.

**14. Identity: password authentication carries V1; Entra follows, with an edge.** Owner-ruled, against the recommendation, to keep the pilot off the critical path of another organisation's IT department. The deferral is made defensible rather than merely accepted:

- Hashing is scrypt with a per-user salt (`packages/db/src/credentials.ts`), login is rate-limited (T-217), and server-side revocable sessions are already in V1's Phase A floor.
- **The seeded shared dev password must not exist in the pilot environment.** Seed data is development-only; pilot users are provisioned individually. This is the single largest risk in the deferral and is a build task, not a note.
- The deferral has a **named expiry**: Entra lands before operating-envelope.md's revisit trigger 2 (any paid contract), not vaguely "after the pilot". A deferral without an edge is an abandonment.

**15. Residency is stated in three parts, because it is not uniform.** Honesty here matters more than a clean sentence:

- **Customer documents, database and backups: UK** (`eu-west-2`), at rest and in transit.
- **Model inference: US**, under the `pilot` tier's zero-retention agreement and no-training terms (ADR-0026 unchanged).
- **Error-tracking telemetry: EU** — Sentry's EU region, with PII scrubbing on and no document content, prompt or completion bodies transmitted.

operating-envelope.md requires any component that cannot meet UK residency to be named rather than tolerated silently; these are those components, and the pilot agreement must disclose the inference position rather than let a buyer infer UK-only from "UK data residency".

**16. Email: Amazon SES in `eu-west-2`** — in-region, IAM-native, no additional vendor or DPA. This is the notification-channel dependency Q-012 has been waiting on. Two real lead-time items ride with it: domain verification with DKIM records, and **SES begins in sandbox mode**, able to send only to verified addresses until a production-access request is approved.

**17. The Slice A3 P2 dev-harness engine is Collabora Online Development Edition, run locally only.** ADR-0043 §3 makes the engine a disposable test rig whose only job is to prove the WOPI host contract before pointing at real Office. Collabora's WOPI implementation is the more thoroughly documented of the two candidates and is what WOPI hosts commonly validate against, whereas OnlyOffice's primary integration path is its own Document Server API with WOPI secondary — so validating against Collabora exercises the more representative surface. It runs as a `docker compose` service in development and **is not deployed to the pilot environment at all**, since A3 P2 is build-and-validate and A3 P3 (real Office) is gated on CSPP, outside V1. The harness therefore costs nothing in the pilot environment.

**18. The corpus lands in the pilot environment and nowhere else.** The firm's 100–500 documents go into the pilot S3 bucket through V1's bulk-load path, as an operator action, **after the DPA with the firm is signed**. They are never on a laptop and never in the repository. Development and evaluation run on **synthetic fixtures** — which makes v1.md's "a few hundred fixture documents" a *generation* task rather than a copy, and is a build item that did not previously exist.

**Consequences:** `file_ref` gains a real object store, and every byte read becomes an API-mediated, entitlement-re-resolving stream — the wall now holds at the storage layer, at a small latency cost. The two-database-role split extends into the deployment pipeline. ADR-0037 gains a third tier and its `DeploymentTier` union, `TIER_POLICIES` and the `env.ts` enum all widen by one entry — a policy addition exactly as §2 promised, touching no structure. The model layer gains a second adapter of each kind, and the claim that the model is rented and swappable stops being architectural rhetoric and becomes a tested property. Password authentication survives into the pilot with a dated expiry, which is a real accepted risk and is recorded as one. The pilot's residency position becomes a three-part disclosure the sales conversation must carry, not a one-line reassurance. Cyber Essentials Plus, ISO 27001 and SOC 2 Type II all remain reachable; none is foreclosed.

**Considered and not taken.** *Azure UK South* — chosen briefly and reversed within the session on the Context findings: it forces GPT in place of Claude before the eval harness exists to measure the swap, and makes zero retention contingent on a Limited Access approval that expects a managed EA/MCA customer. *UK-only inference* — unobtainable with Claude on any provider; pursuing it would have meant changing the model to protect a residency line that ADR-0037's own Context already concedes is a risk-based judgement for OFFICIAL. *Relaxing `standard` to admit `us`, or bypassing the router* — both rejected in decision 12; they would have degraded an enforced guarantee into a comment. *Per-tenant databases or buckets* — rejected in decision 11; ADR-0037's deployment boundary already provides the lever. *Presigned S3 URLs* — rejected in decision 3; a bearer capability that outlives its entitlement check breaks ADR-0024's revoke semantics. *Multi-AZ RDS and a staging environment* — both deliberately deferred to operating-envelope.md's revisit trigger 2. *AWS-managed KMS keys* — rejected for the certification evidence CMKs produce at negligible cost. *CDK instead of Terraform* — rejected to keep infrastructure out of the pnpm workspace and its dependency rules.

**Open — not decided here.** The **CSPP program tier and its licensing** remain ADR-0043's open commercial items. **Entra's tenant model** for a genuinely multi-organisation deployment — one multi-tenant application with per-organisation admin consent, versus per-organisation registrations — is deferred with the identity work and is a design question in its own right, not a configuration detail. **Sovereign-tier infrastructure** stays designed-not-built per ADR-0037 §8. **Audit-log export format** for certification evidence is untouched here and remains with Q-015. Whether the pilot's US inference position is acceptable to a specific buyer is a commercial judgement per engagement, not a platform property.
