# ADR-0037 - Security posture is a per-deployment policy enforced at the model router, not a fixed property of the build: deployment tiers (standard UK-region, sovereign) selected per client and data classification; the router enforces region, retention, jurisdiction and classification as route attributes and fails closed; data sovereignty is a tier-parameterised invariant; and the architecture evidences the standards that underpin CCS/G-Cloud listing

**Status:** Accepted (2026-07-22; built and tested T-139–T-144). Extends ADR-0028 §9 (the router seam) and ADR-0024 (colocated store, model pinning). References ADR-0026 (zero training on customer data; the distillation/egress boundary), ADR-0025 (the assembly environment), ADR-0027 (code-first for deterministic rules) and ADR-0002 (immutable audit).

> Drafted this cycle as "ADR-0035"; renumbered to **0037** on filing because a non-review-transmittal ADR took 0035 and the sandbox-participant-scope ADR took 0036. All self-references updated accordingly.

> **Amended 2026-08-01 by [ADR-0047](0047-pilot-deployment-substrate.md) — a third tier, `pilot`.** The infra/security session established that **there is no UK-region route to Claude on any hyperscaler** (Foundry serves it only on Global / Data Zone US deployments; Bedrock's London region does not carry it and the EU inference profile excludes the UK), so this ADR's `standard` tier cannot be satisfied by the model the product runs on. The owner ruled the pilot runs Claude on Anthropic's public US API. Rather than relax `standard` to admit `us` or bypass the router — either of which would turn an enforced guarantee into a comment — ADR-0047 uses the extensibility **§2** promises and adds a tier whose declared attributes are **true**: `region: us`, `retention: zero` (valid **only** under a zero-data-retention agreement with Anthropic), `jurisdiction: foreign-reachable`, `eligibility: enterprise-zdr`, `classifications: official` only. It is never a default, it is the only tier permitted to carry `us`, and it expires at [operating-envelope.md](../operating-envelope.md)'s revisit trigger 2 (any paid contract). §3's fail-closed selection, §4's classification-carrying and §6's egress audit are unchanged and now enforce this tier exactly as they enforce the others.

**Open items ruled on acceptance (owner, 2026-07-22).** (1) **Tier set:** ship `standard` + `sovereign` only; the enum stays extensible so a third tier is a policy entry, not a refactor — add EU-region / isolated tiers when a contract names the need. (2) **Tier scope:** the tier is a **deployment-level** setting (a physical boundary, not a per-request choice); a client operating across classifications runs **separate deployments**. Classification, by contrast, travels per-request. (3) **Standard-tier provider route:** the vendor stays procurement's call; the build encodes the required *attributes* as policy and attaches honest attributes to the current dev endpoints — which, being the public US-region APIs, conform to no tier, so a production `standard` deployment fails closed until pointed at a conforming UK-region ZDR endpoint. (4) **Classification source:** resolved by **inheritance** (deployment default → project → request), carried on the request as a first-class field so per-deliverable **elevation is representable**, but no elevation flow is built in v1 — v1 resolves the deployment default on the Router.

**Context:** Clients differ in what security they require, and the difference is not cosmetic. Most infrastructure planning and DCO work is OFFICIAL, for which UK government guidance (the NCSC Cloud Security Principles, the Cloud First strategy) permits a risk-based judgement rather than mandating UK-only processing. Some work — nuclear-adjacent, station security, anti-terror measures — is SECRET-capable or carries a client mandate for strict isolation, where the flexibility disappears: processing must stay within a UK-sovereign boundary free of foreign legal jurisdiction, and calling an external third-party inference API is not permitted.

The wrong response is to hard-code one security posture. That would either over-build (imposing sovereign-tier cost on every client) or under-serve (unable to take the classified work). The requirement is that one codebase supports different security postures, chosen per deployment. So the decision that is actually hard to reverse is not the set of rules — those are configuration — but where and how the rules are enforced: whether every model call is forced through a single point that reads the deployment's policy and cannot be bypassed.

The platform already has the seam. ADR-0028 §9 established a single Router through which all chat and embedding calls pass, with each provider behind a `ChatAdapter` / `EmbeddingAdapter` interface and a `task` parameter present so selection logic can arrive without changing callers. Model identity is already recorded to the Step audit fields (ADR-0028 §7). What the router does not yet carry is any notion of region, retention posture, legal jurisdiction, data classification, or fail-closed behaviour; `fromEnv()` currently binds whatever endpoint the environment supplies. This ADR fills that gap. It is a formalisation and extension of an existing choke point, not the construction of a new one — the same architectural pattern as the access wall (ADR-0025): one gateway, policy-enforced, never per-call-site convention.

Training is out of scope here and is not re-decided: ADR-0026 settles that the moat compounds by retrieval and codified workflows with zero training on customer data, and any future per-tenant fine-tune is constrained to pre-abstracted owned material. This ADR governs only where inference happens and what leaves the boundary.

**Decision:**

**1. Security posture is a per-deployment policy, not a build property.** A deployment runs at a named security tier, selected by client requirement and the classification of the data in scope. One codebase supports all tiers; the tier is configuration, enforced at runtime, never a fork.

**2. Two tiers are defined now; the model is extensible.**

- **Standard (UK-region).** Frontier models reached through a UK region of an enterprise provider (hyperscaler or direct), under a contract carrying zero data retention, no training on our data, a data-residency clause and disclosed sub-processors. Appropriate for OFFICIAL. Data is processed in the UK but rests transiently on the provider's infrastructure.
- **Sovereign.** Self-hosted open-weight models running inside a UK-sovereign boundary that excludes infrastructure subject to foreign legal jurisdiction. No project data is transmitted to any third-party inference API. Appropriate for SECRET-capable work or a client mandate for strict isolation. (Note: a UK region of a foreign-headquartered hyperscaler does not satisfy this tier, because foreign legal process — e.g. the US CLOUD Act — can reach it regardless of physical location.)

- **Pilot (US-region, added 2026-08-01 by [ADR-0047](0047-pilot-deployment-substrate.md) §12).** Claude reached through Anthropic's public US API under a zero-data-retention, no-training commercial agreement. Appropriate for OFFICIAL **only**, and only for the first pilot. It exists because no provider offers a UK-region route to the product's model (see the amendment note above), and it is declared honestly — `region: us`, `jurisdiction: foreign-reachable` — so the router enforces rather than excuses it. **Never a default; the only tier admitting `us`; expires at the first paid contract.**

The tier set may grow (e.g. an EU-region tier); adding one is a policy addition, not a structural change — as the `pilot` tier's own addition demonstrates.

**3. The router enforces the tier's policy as route attributes, and fails closed.** Extending ADR-0028 §9, every route the router can dispatch to carries declared attributes: processing region, retention posture, jurisdiction, and provider eligibility. The router selects only a route conforming to the active deployment's tier policy, and:

- it **fails closed** — if no conforming endpoint is available, the call errors; it never falls back to a non-conforming region or provider to preserve availability;
- a **misconfigured or unattributed endpoint is treated as non-conforming and is refused**, not dispatched to on trust (closing the `fromEnv()`-picks-up-any-URL gap);
- the choice is made centrally at the router, **never delegated to a call site**.

Selection has two axes applied in order: the tier policy is a **hard constraint filter** applied first, reducing the candidate routes to the conforming set; task-based optimisation applies only *within* that set. The tier is never a task heuristic and can never be traded off for availability or cost.

**4. Data classification travels with the request.** Classification is an attribute carried on the request into the router — the same discipline by which the access slice travels with a retrieval (ADR-0025) — so the router can select the conforming route. Classification is resolved upstream and rides along; it is never inferred at the point of dispatch. A classified request and an OFFICIAL request must not share a default egress path.

**5. Data sovereignty is a tier-parameterised invariant.** No project data egresses beyond the boundary the active tier permits. At the sovereign tier that boundary admits no foreign-jurisdiction infrastructure and no third-party inference endpoint. The invariant applies to every model and sub-agent call without exception, because all of them pass through the router — including the sub-agent retrieval and drafting calls, which is where an unenforced boundary would otherwise leak.

**6. Every call is audited with its egress facts.** Extending the Step audit (ADR-0028 §7), each model call records the endpoint, region, retention posture and data classification it used. This makes the guarantee provable after the fact per call, not merely asserted — the evidence a security review will require rather than accept on trust.

**7. The architecture evidences named standards; framework listing rests on that evidence.** The controls above are written to satisfy, and the platform is assured against: the NCSC Cloud Security Principles; the Secure by Design principles and the government Cyber Security Standard (both named in the AI Playbook, Principle 3); Cyber Essentials Plus and ISO 27001 as the expected certifications; and, for the AI-specific controls, the NCSC Guidelines for Secure AI System Development and the AI Cyber Security Code of Practice, with AI Management Essentials tracked as it moves into procurement frameworks. Note the distinction the ADR must keep honest: G-Cloud and CCS are procurement routes, not security standards. Listing on the Digital Marketplace / a CCS framework or DPS (under the Procurement Act 2023) is a commercial workstream that rests on the technical evidence above; the build conforms to the standards, which is what makes the listing achievable. The ADR does not claim "G-Cloud compliance" as a technical property. (The specific certifications a given framework or DPS demands shift; treat this list as "verify against the framework's current requirements at listing time," not a fixed guarantee.)

**8. The sovereign tier is designed now, built when a client needs it.** The enforcement point, the route-attribute model and classification-carrying are built now, so the sovereign tier is a new conforming route through existing structure. The self-hosted sovereign environment itself — GPUs, cleared personnel, a separately accredited boundary — is not stood up until a contract requires and funds it. Designing for it early is cheap; building it early commits expensive infrastructure before there is a Sizewell-shaped need.

**Consequences:** The router seam (ADR-0028 §9) gains a policy layer: route attributes, tier-conformant selection, fail-closed dispatch, and classification as an input. Callers are unaffected — the whole point of the seam — so this is additive, not a refactor of scattered call sites. The Step audit (ADR-0028 §7) gains egress facts. Data sovereignty becomes an enforced, tier-parameterised invariant rather than a deployment assumption. The `fromEnv()` endpoint-on-trust weakness is closed. Training remains governed solely by ADR-0026; this ADR neither restates nor relaxes it. The standards conformance is stated as the basis for CCS/G-Cloud listing without conflating the two.

**Open items to confirm on acceptance.**

- **Tier taxonomy and naming.** Two tiers are defined; confirm whether an intermediate EU-region tier or a distinct client-mandated-isolation tier (separate from SECRET-driven) is wanted from the start, or added on demand.
- **Where the tier is set.** Per deployment/tenant is assumed; confirm it is a deployment-level setting rather than per project or per request, and how a single client operating across classifications is handled (likely separate deployments).
- **Standard-tier provider route.** Whether the standard tier reaches frontier models via a hyperscaler (Bedrock/Vertex/Azure UK region) or a direct enterprise contract is left to procurement; the ADR fixes the required contractual terms (ZDR, no-training, residency, sub-processor disclosure), not the vendor.
- **Classification source.** Confirm how a request's classification is set and propagated — inherited from the project/deployment, or capable of per-deliverable elevation — since §4 depends on it arriving reliably.
