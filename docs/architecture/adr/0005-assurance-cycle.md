# ADR-0005 - Assurance cycle: version lifecycle inside a deliverable; lead reviewer closes rounds; review period is a guide, not a gate

**Status:** Accepted. Refined by ADR-0032 (2026-07-18): the cycle is role-agnostic (authoring side / reviewing side, not consultant/client) and runs at two scopes (org-private sandbox, wall-crossing project); the cycle is the instance unit with two terminal states — accepted, and **closed-rejected** by explicit audited action of the lead author or project owner (this ADR named no end other than acceptance). The round/close/review-period mechanics below are unchanged.

**Context:** A promoted version is reviewed, responded to, and re-reviewed across rounds until the deliverable is accepted. Something must own the transitions, and review periods exist on real schemes but are not always hard deadlines.

**Decision:** A deliverable is long-lived and spans versions; it ends when a lead reviewer applies an accepting code. Each version moves through: promoted (round opens, reviewers notified), in review (reviewers comment and code on the PDF), review closed (comment set goes to the consultant), responded (consultant addresses comments in the sandbox, writes responses with mandatory links, promotes the next version, opening a fresh round). A round closes only by an explicit lead reviewer action. A round carries a configurable review period that sets a target date, drives automatic reminders, and marks the round overdue once passed, but the period never closes a round or locks commenting; only the lead reviewer closes it. Even as the assurance cycle becomes configurable per project, closing a round stays a human action and is never rule-automated.

**Consequences:** State transitions are owned by people, not the clock. The review period is a notification-and-status attribute with no power over state. Configurability extends to the gate sequence and codes but never to automating the close of a round. Builds on ADR-0002 (immutable versions), ADR-0003 (acceptance coding) and ADR-0004 (PDF review).

**Addendum (owner-ruled 2026-08-22, DMS walkthrough session 2): the review period gains an owner.** The decision above gives a round "a configurable review period" without ever saying *who* configures it or *when*, and the build showed what that costs: `rounds.review_period_target` shipped, the status bar rendered a target date and an overdue state, and nothing anywhere ever set the value — chrome ready and permanently idle. The period now has two owners and no new powers. **The project carries a default of ten working days**, set by the owner super-user beside the deliverable schema — project configuration, deliberately *not* a schema attribute field, because the schema's fields are the header row of the fillable deliverables template (T-337/T-359) and a review period would arrive there as a column nobody should be filling in. **The lead author may override it for one submission** in the promotion window (ADR-0008 addendum, same session), and the target is computed at round creation from the promotion date. Working days are Monday to Friday: no holiday calendar is modelled anywhere in the system, and a per-jurisdiction one is a separate job, not an implementation guess. Nothing about the period's *power* changes — it chases and flags overdue, and only the lead reviewer closes a round. That the producing side may set it is safe **because** of that: a guide carries no access or state consequence, which is precisely the opposite of the review group sitting in the same window (ADR-0033 addendum, same session).
