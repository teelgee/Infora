# ADR-0003 - Acceptance coding: two levels, configurable per project, lead reviewer authoritative

**Status:** Accepted. Refined by ADR-0032 (2026-07-18): a rejecting deliverable code leaves resubmission open — the cycle (and its work item) closes either on an accepting code or by an explicit audited close to rejected; "client acceptance closes the work item" below gains that second terminal. Made storable same day (Slice A session, data-model Drawer 5): codes are per-project rows **copied** from Infora's default scheme at project creation (never a shared reference, so history can't re-read); each carries a level (comment | deliverable | both) and `is_accepting`; a code ever referenced is immutable — **retire and replace, never redefine**.

**Context:** A deliverable is reviewed by several reviewers and accepted or rejected by the client against a specific version. Verdicts are expressed as codes, and different projects use different classification schemes. A verdict is needed both on each comment and on the whole deliverable, and someone must own the deliverable verdict.

**Decision:** Acceptance codes live at two levels. Reviewers set a code on each comment; the lead reviewer sets one authoritative code for the deliverable. The system suggests the deliverable code from the comment codes, and the lead reviewer confirms or overrides it. The classification scheme is configurable per project: Infora ships a default scheme and a project may replace it. Whether a code blocks acceptance is a property of that code in the project's scheme, not hard-wired.

**Amended 2026-08-27 (the document-status session) — a code carries two more properties, and the default scheme becomes ISO 19650's.** The scheme seeds from the **2021 UK National Annex** set — `S0`–`S5` and `A1, An…` — rather than an Infora invention ([iso-19650.md](../../reference/iso-19650.md)). ⚠ **Seed from the 2021 NA, not the 2018 one**: the 2018 table is what most free material online still reproduces, and in it `S5` meant *withdrawn*, `S6`/`S7` and `CR` existed, and `A2` implied a RIBA stage. All of that is gone. `B1`/`Bn` (partial sign-off) is **deprecated** but may still be added by a project, since the NA permits codes to be expanded or excluded where the project's information standard documents them.

**Two properties join `is_accepting`.** **`is_contractual`** — an accepting code ends the cycle, but only a *contractual* one issues the `C` revision (ADR-0041); this is ISO's own preliminary/contractual split, and it is what separates *we have agreed this* from *we have agreed most of this, with comments*. **`grounds`** — whether a deliverable accepted under this code enters the AI's reach (ADR-0013 §6).

**Why `grounds` must be configurable rather than a fixed mapping, and it is the standard that forces it.** The 2021 NA makes Published status codes **stage-agnostic** and requires that *"the reason for each `An` code must be written into the project's information standard"* — `A4` might mean suitable for construction, `A5` suitable as a construction record, **only because that project said so**. Since the standard explicitly refuses to fix what an A-code means, Infora cannot ship a fixed grounding mapping even in principle. The default follows the revision column (contractual grounds, preliminary does not) and the project owner may change it.

**The owner sets this, and sees the consequence before saving.** The scheme is the owner organisation's, per-project and copied at creation as this ADR already requires. Because a change here alters what the AI may rely on across a whole project — silently, since every existing citation still resolves — the editor **states the blast radius** (how many live deliverables carry each code) and the change is **audited like a rails change** (ADR-0030), not saved like a preference. Retire-and-replace-never-redefine already applies and now matters more: a code's grounding rule is part of what it meant.

**Consequences:** "Acceptance code" is the single canonical term for a review verdict, replacing the loose "decision" on Comment. Readiness logic is driven by the project's scheme. The DRR must attribute every comment, response and code to a specific version. Builds on ADR-0002; client acceptance of a version closes the work item, per the work-item lifecycle.
