# ADR-0042 - Sandbox provisioning is a super-user act; every participant has an auto-provisioned personal sandbox

**Status:** Accepted (owner-ruled 2026-07-25, sandbox-structure build session). Refines ADR-0036 §5 (who provisions) and closes the T-133 open item ("the precise self-serve boundary … who may create, scope and revoke project-wide provisions and shared sandboxes") for sandbox creation. Builds on the classes-of-user model (T-176) and ADR-0040 (per-sandbox configuration is a super-user act).

**Context:** ADR-0036 §5 let any participating-organisation member self-serve single-organisation/team/named-user sandboxes, gating only the cross-organisation (shared) sandbox to the owner. In practice that put sandbox *provisioning* — laying out whole working areas — in every member's hands, which sits awkwardly beside ADR-0040 (folder-structure and settings are a super-user act) and the owner's mental model: a super-user lays out the structure, ordinary members work within it. The owner asked to "unpick ADR-0036" here: creation should be a super-user act, and every user should still have a private place to work regardless.

**Decision:**

**1. Creating a sandbox is a super-user act** (`canCreateSandbox`, governance). An ordinary participant cannot create sandboxes. A **guest super-user** creates private sandboxes for its own organisation (single-org / team / named-user). A **shared (cross-organisation) sandbox stays the owner super-user's act** — cross-org visibility is the owner's to open (ADR-0018), so only the owner-super provisions one and admits the other organisations. *(Inference flagged for the owner: guest-super is confined to private creation. If the owner wants any super-user to open a shared sandbox and pick organisations, relax the `multi_org` branch of `canCreateSandbox` — but that would move cross-org visibility off the owner, against ADR-0018.)*

**2. Every participant has an auto-provisioned personal sandbox** in the project — a named-user sandbox granted only to its owner, **server-provisioned** (never through the super-user-gated create path), one per participant (a partial unique index enforces it). It is created lazily on first sandbox read, so it exists for every current and future participant. This is the private place an ordinary member always has to work.

**3. What each class sees.** An ordinary member sees **their personal sandbox plus any sandbox they are a member of** (via a live org- or participant-grant), and within those may create *folders* (per ADR-0040's toggle) but not sandboxes. A super-user additionally sees the create control, and the surface offers the scopes their class may provision.

**Consequences:** `POST /projects/:id/sandboxes` is gated on `canCreateSandbox` (403 for an ordinary member; a guest-super is refused `multi_org`). `sandboxes` gains `is_personal` (and the personal partial-unique index); the sandbox read carries it, and the surface labels the personal card and sorts it first, hiding the create control from non-super-users. Provisioning is now consistent with configuration (ADR-0040) — both super-user acts — so the super-user owns the shape of the working area (which sandboxes exist, their structure, and their settings) while ordinary members work inside it. **Follow-up (T-187):** the create flow becomes a short wizard — private vs shared, then (if shared) the organisations, then the users — so a super-user admits participants at creation rather than only afterward.
