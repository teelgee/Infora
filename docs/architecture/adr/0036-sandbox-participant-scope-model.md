# ADR-0036 - The sandbox participant-scope model: unlimited sandboxes, each scoped on a broad-to-narrow participant ladder; access is live and revocable; separation is by provisioning a narrower sandbox, never by walling a shared one

**Status:** Accepted (owner-ruled 2026-07-21, producing-side-lifecycle grill). Refines ADR-0018 and ADR-0019, and supersedes CONTEXT.md's "sharing is set at creation" wording. References ADR-0024 (colocated store, immediate effect), ADR-0033 (interval grants), ADR-0035 (revocation model).

**Context:** ADR-0018 and ADR-0019 established that work in progress is shared through sandboxes and that only the owner opens cross-organisation visibility, but they left the sandbox's own shape underspecified: how many a project may have, at what granularities a sandbox may be scoped, whether that scope is fixed at creation or mutable, who may create one, and how "a team" relates to the access primitives. The glossary said "sharing is set at creation", which contradicts the interval/revocation model that the rest of the platform runs on (ADR-0033, ADR-0035) and the colocated store's same-transaction effect (ADR-0024). It also risked implying that a shared sandbox might be internally partitioned — a wall inside a shared space — which would reintroduce exactly the leak surface the ethical wall exists to remove. The producing-side lifecycle depends on this model being precise, because a formal deliverable is drafted in a sandbox before promotion.

**Decision:**

**1. Unlimited sandboxes, each on a participant-scope ladder.** A project holds an unlimited number of project sandboxes. Each carries a **participant scope** on a ladder from broad to narrow: shared across a chosen set of organisations (e.g. Org B and Org C together) ⊃ a single organisation ⊃ a team within an organisation ⊃ specific named users. Narrower is a strict subset of broader — the same subset shape as ADR-0035's intra-organisation deliverable narrowing and ADR-0015's access ceiling.

**2. Separation is by provisioning a narrower sandbox, never by walling a shared one.** The sandbox *is* the boundary; there is no wall inside it. Two parties who must not see each other's work are separated by giving each its own narrower sandbox, not by admitting both to one shared sandbox and partitioning it. A sandbox, and any internal review run inside it (ADR-0032), is therefore **participant-private**: visible only to its admitted participant set at whatever rung. This generalises the participant-private property and is what replaces any notion of a wall within a shared space.

**3. "Team" is not a first-class entity.** The team rung is simply a named set of an organisation's users, not a new access primitive. It composes from Participants; it introduces no new access object.

**4. Access is live, set as an initial scope at creation and mutable and revocable thereafter.** A sandbox's participant scope at creation is only its *initial* scope. Over its life the scope can be widened, narrowed and revoked, consistent with the interval-grant model (ADR-0033) and the colocated store's immediate effect (ADR-0024): adding an organisation or user grants access from that moment; revoking drops the revoked party's live visibility and retrieval **immediately, in the same transaction as the read**, with no stale window — while everything that party authored stays in the sandbox, attributed and intact (nothing is deleted; a closed interval is no access). This supersedes "sharing is set at creation".

**5. Who creates and scopes, split along the wall.** Within its own organisation, a participating organisation **self-serves** — it freely creates single-organisation, team and named-user sandboxes for its own people, because none of these opens cross-organisation visibility and there is nothing for the owner to gate. A **cross-organisation (shared) sandbox is owner-gated**, because it opens cross-organisation visibility, which ADR-0018 reserves to the owner: either the owner creates and scopes it, or a member proposes and the owner confirms (the ADR-0019 sub-invite pattern). Cross-organisation visibility still reduces to a deliberate owner act.

**6. The single-organisation sandbox is the default home for formal deliverables.** A producing organisation drafts its formal, TIDP-planned deliverables (ADR-0008, ADR-0033) in its own single-organisation sandbox before promotion. A shared sandbox is the exception, for cross-organisation collaboration and co-authoring, where the authoring team may span the organisations sharing it (ADR-0019).

**Consequences:** The sandbox becomes a first-class, scope-bearing, interval-access object in the data model — carrying a participant scope on the ladder, mutable and revocable, with the same append-only interval discipline as memberships and appointments (ADR-0033). The "sharing set at creation" wording is retired from the glossary. Because separation is by narrowing rather than partitioning, there is never a within-sandbox wall to enforce or audit, which keeps the ethical-wall audit reducible to sandbox membership plus owner sharing acts. The self-serve/owner-gated split keeps cross-organisation visibility an owner act while removing the owner from the path of an organisation's purely internal working areas.

**Open — not decided here.** The precise self-serve boundary and any **elevated super-user abilities** (who beyond a plain participating-org member may create, scope and revoke project-wide provisions and shared sandboxes, and hold destructive lifecycle powers) remain the T-133 open item, to be reconciled with the org admin (ADR-0033) and ADR-0016's owner/member collapse. Whether an org admin can reach a user's **personal sandbox** (the per-user workspace sandbox, ADR-0018) also stays open, to settle with the sandbox drawer. Builds on ADR-0015, 0016, 0018, 0019, 0024, 0033, 0035.

**Addendum (2026-07-25, ADR-0043 — the co-authoring substrate):** the sandbox is also the WOPI co-authoring **collaboration space**. Files served by the WOPI host are gated by the same `sandbox_scope_grants`, so the ethical wall is enforced where the bytes are served and the collaboration space **inherits its grants** (the NetDocuments CollabSpaces pattern). This introduces no new access object, and — consistent with decision 2 — there is still no within-sandbox wall; a revoke drops co-authoring access in the same transaction as the read (ADR-0024).

> **Note (2026-10-25, T-486 — ruled by Claude under the owner's delegation of 2026-10-23; clarifies decision 6, reverses nothing).** *Plainly: when a person uploads a file or starts a draft without choosing a working area, it goes to their organisation's default working area. Until now, if the organisation had several working areas, "the default" was whichever one the database happened to read first, so a file could land in a different working area from one request to the next — and even in one the organisation could no longer open. Now the default is always the organisation's oldest single-organisation working area that it can still open; if there is none, one is made, as before.* Decision 6 names "its own single-organisation sandbox" as the default home, which assumed an organisation has one. It may have many (the ladder above lets a super-user provision as many as it likes), and the code picked among them with no rule. The rule is: **the oldest single-organisation sandbox of the organisation on the project (creation time, then id) among those holding a live organisation grant for it**; none qualifies → a new one is provisioned, as before. Every caller that files into "the default" — creating a document with no sandbox named, the upload, Ask's save to a sandbox — takes this one rule, and a folder named without a sandbox is checked against it. Known and left: two simultaneous first requests can each provision a default; the older wins from then on, and preventing the pair would need a unique index (a migration), which the harm does not justify.
