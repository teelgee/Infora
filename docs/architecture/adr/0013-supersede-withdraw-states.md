# ADR-0013 - Record state: supersede and withdraw keep a document in the library and stop it grounding; authority over the state follows the publication boundary, supersession is an edge and withdrawal is a state

**Status:** Accepted. Refined by ADR-0032 (2026-07-18): the state set gains **rejected** — a deliverable whose cycle was closed-rejected and never resubmitted stays in the library as a record, badged, with its DRR attached, and never grounds (it also never had an accepted version). Same currency-by-state, nothing-deleted principle as below.

**Context:** Promoting a new version structurally supersedes the prior one. Separately, an owner needs to mark a document superseded or withdrawn while keeping it in the library as a record. ADR-0011 auto-admits accepted deliverables to the trusted corpus, so withdrawal needs a defined effect on grounding.

**Decision:** Supersede and withdraw are lifecycle states an owner sets on a document; the document remains in the project library and fully auditable. Library membership and groundability are distinct: a withdrawn or superseded document stays in the library but is removed from the trusted corpus the AI grounds on, so it no longer informs answers or drafting. Structural supersession by a newer version is automatic; owner-set supersede and withdraw are deliberate actions.

**Consequences:** Nothing is deleted; currency is expressed by state, not removal. The library is a superset of the grounded corpus. Refines ADR-0011. Sign-off needs no separate mechanism: the lead reviewer's acceptance (ADR-0003) is the sign-off, recorded in the audit trail, and consultant-side authorship lives on the document's own cover sheet, not in system state.

---

**Amended 2026-08-27 (owner-ruled, the document-status session) — the state set is named `record state`, and the "owner-set" framing above is replaced by a boundary rather than a party.** This closes **`Q-036`**, which asked who may end another organisation's deliverable, and it resolves the apparent conflict that raised it: ADR-0013 called supersede and withdraw *"owner-set states"* while ADR-0033 and T-176 built every container write as a producing-organisation act. **The two never disagreed** — they describe **two different acts that share one word**. T-189's `withdrawal` removes a row from a producer's own delivery plan (*"Remove a planned deliverable from the plan"*); this ADR's withdraw stops a **promoted** deliverable being relied on. Same enum column, opposite owners, and the build implemented only the first.

**1. Record state is one of four axes, and it is the only one that is Infora's own.** The other three come from ISO 19650 and are adopted whole ([iso-19650.md](../../reference/iso-19650.md)): **CDE state** (where a container sits), **status code** (what an issue may be used for), **revision code** (which issue it is). Record state answers a fourth question none of them asks — *may this still be relied on* — and it exists because ISO never had to ask it: a human always reads the current revision from a register, whereas an un-withdrawn container **grounds silently**. Values are unchanged: `live`, `superseded`, `withdrawn`, `rejected`.

**⚠ Do not reach for ISO's Archive to carry this.** Archive is *"a journal of information transactions providing an audit trail of container development — continuous, running alongside all three"* states. It is not a destination a document moves to, so there is nothing to extend and no deviation to justify; record state simply stands beside the ISO axes rather than inside them.

**2. Authority follows the publication boundary, not the party.** While a container is **pre-publication**, the record is the producing organisation's: T-189's producer-only guard is correct and stays. Once **published into the owner's library**, the record is the owner's: the owner sets record state, and the producing organisation **proposes**. This is the record-scope principle ruled the previous day ([ADR-0050](0050-the-privacy-programme-operator-access-and-deletion.md), 2026-08-26) applied to a lifecycle boundary — *the record decides, not the organisation* — so it introduces no new authority model.

**3. Supersession is an edge; withdrawal is a state.** Where a **different document** (not a newer revision) becomes authoritative, that is a `supersedes` **relationship edge** between two containers — the mechanism ADR-0045 already built, proposed by either party and **confirmed by the owner**, whose confirmation sets the target's record state to `superseded`. Where a document is simply no longer to be relied on and **nothing replaces it**, there is no second endpoint and no edge to draw, so it is the `withdrawn` **state**, carrying a **mandatory reason**. Structural supersession by a newer version of the same container stays automatic and needs neither.

**4. The reason's visibility follows the container it is about**, exactly as a notification's follows its subject (ADR-0049) and a guidance note's follows document access (ADR-0002). So the producing organisation reads why its deliverable was withdrawn, and an organisation the deliverable was never shared with learns nothing — the wall holds by construction, with no new visibility rule to enforce. The producing organisation is additionally **notified** (ADR-0049, as amended), by a pointer carrying the bare fact and never the reason.

**5. Restoration stops being symmetric.** As built, either side could restore what the other withdrew and neither act recorded the other. The container now records **which side withdrew it**, and only that side — or the owner, over a producer's act — may undo it. The code comment justifying free restoration (*"recovery is never a helpdesk ticket"*) was reasoning about a producer undoing its own mistake and does not survive a cross-organisation act.

**6. Groundability is now derived from two conditions, not one, and is never set directly.** A container grounds when it is in the library **and** its record state is `live` **and** the acceptance code that admitted it carries the project's grounding rule (ADR-0003, as amended). That derived answer is **context state**, it is computed and never stored as a decision, and the platform enforces that `superseded`, `withdrawn` and `rejected` never ground **whatever code got the deliverable there** — a project may configure which codes admit, never configure its way past this ADR.

**Consequences.** `Q-036` closes. Nothing is deleted and nothing becomes unreadable: a superseded or withdrawn document stays in the library, stays auditable, and a user may still pin it as an **attached source** (ADR-0022) to ask about it deliberately — badged user-supplied, carrying the withdrawal reason, never emitting a citation. **Context state is not access**: component 2 remains the only place access is resolved, and none of this changes what anyone may see. The two enum values were already present, so the state machine needs no migration — what changes is who may write them, and what reads them.
