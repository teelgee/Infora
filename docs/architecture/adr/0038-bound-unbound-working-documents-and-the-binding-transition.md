# ADR-0038 - Working documents are bound or unbound by one fact — the link to a planned container; identity metadata is plan-owned and locks on binding while authoring metadata accrues freely; binding is a first-class, one-way event distinct from and prior to promotion

**Status:** Accepted (owner-ruled 2026-07-22, producing-side-lifecycle grill). Refines ADR-0008 (the deliverable plan; "not a metadata gate"), ADR-0002 (immutable revisions; reference unchanged across versions) and ADR-0032 (the sandbox-document → container link, the addendum's nullable join). References ADR-0033 (container creation is a producing-org act) and ADR-0034 (origin/kind/format).

**Context:** A document drafted in a sandbox may be destined to become a formal deliverable, or may be free internal working material that never leaves. ADR-0032's addendum gave the sandbox document a nullable `container_id` but did not settle the model around it: what distinguishes the two kinds, which metadata is fixed by the plan versus accrued in the sandbox, and how a free working document becomes a planned deliverable. ADR-0008 fixed that promotion is "not a metadata gate" — metadata and naming come from the plan — but a working document accrues its own document-specific metadata as it is drafted, and an unplanned document has no plan row at all. The risk in getting this wrong is either reopening the metadata gate (asking the user for code/naming/reviewers at promotion) or letting a free draft slide into the controlled record with no recorded moment.

**Decision:**

**1. Two tracks, distinguished by exactly one fact: the link to a planned container.** A **bound** working document carries a `container_id` linking it to a planned TIDP container, so it wears that container's coded reference and plan-owned identity, inherited by reference through the link. An **unbound** working document has no link — a free, internal-only working document with light, author-owned metadata that may never leave the sandbox. The distinguishing fact is the link's presence, never a status flag or document kind.

**2. The metadata split: identity is plan-owned, authoring accrues.** **Identity metadata** — the coded reference, discipline, and the review-group / authoring appointments — lives on the container / plan (ADR-0033), set by the producing organisation at planning. On a bound document it is **read-only in the sandbox**, inherited through the link, so it stays stable across the working-doc → version → container lifecycle (ADR-0002's reference-unchanged rule). **Authoring metadata** — revision / suitability attributes, document classification, relationships, `origin`/`kind`/`format` (ADR-0034) — accrues on the working document in the sandbox and carries on promotion into the version. This refines ADR-0008 **without reopening "not a metadata gate"**: the risky identity fields stay plan-owned and locked, so promotion still never asks for them in the moment; authoring metadata is document content riding along, not a gate.

**3. The lock is a consequence of binding, not a property of every sandbox document.** On an unbound working document there is no plan owner, so **all** its metadata is authoring metadata — freely editable, author-owned. Identity fields become plan-owned and lock only at the binding transition.

**4. Binding is a first-class, audited, one-way event, distinct from and prior to promotion.** Binding links a working document to a planned container: it is the recorded moment the document becomes the intended draft of that deliverable, wears the container's code, and has its identity metadata locked. It is a **coordination act, not promotion** — it tells the team "this draft will become deliverable X", but the document stays a live sandbox draft (editable, not snapshotted, not in any cycle) and may sit **bound but not promoted** indefinitely while drafting continues. It is fired by the **producing side** (creating a plan row is a producing-org act, ADR-0033; the lead author is the natural hand), and can coincide with "draft this planned deliverable" (created already bound) or happen later on an existing working document (the unplanned path — ADR-0008's "the plan may evolve"). It is **one-way**: a bound document never silently reverts to a free working file, because that would let the plan-owned code be edited off-plan; a binding mistake is unwound through the records lifecycle (withdraw / reject the container), never by unbinding. **Binding does not snapshot** — promotion is the later event that snapshots the head into an immutable Version and launches the review cycle.

**5. What carries on promotion.** Identity metadata is already on the container. Authoring metadata carries into the version. The internal (sandbox-scope) DRR does **not** carry — it is participant-private QA evidence that stays at sandbox scope and never reaches the project record (ADR-0032).

**Consequences:** The sandbox document is a two-track object keyed on `container_id`; binding is a distinct, audited event, giving a clean point for the identity-lock to engage and a clean audit record of the moment a free draft became a controlled-deliverable draft. The unplanned path is create-plan-row → bind → promote, each step recorded. "Not a metadata gate" (ADR-0008) is preserved because the plan-owned identity fields are locked before promotion and inherited, not supplied at promotion. Modelling binding first-class makes the informal-to-controlled crossing traceable rather than an untracked field change — the discipline the controlled record exists to enforce. Builds on ADR-0002, 0008, 0032, 0033, 0034.

**Considered and not taken.** *One track (every sandbox document bound to a container from creation)* — rejected: it forces a plan row for every scratch note and internal working file, which never become deliverables. *Binding as a mere field set, not an event* — rejected: a document sliding from informal scratch to controlled deliverable with no recorded moment is exactly the untracked state change the controlled record guards against. *Two-way binding (unbind to revert)* — rejected: it would allow the plan-owned code to be edited off-plan; the records lifecycle handles mistakes without reopening identity.

---

**Addendum (owner-ruled 2026-08-09, DMS walkthrough session): bound documents read the row through.** §2's inheritance becomes visible everywhere the document is shown: a bound document **displays its plan row's title and schema metadata by reference over the `container_id` link** — read-through, never copy — so `container_id` stays the only link, there is no second store, and drift between the row and the draft is impossible by construction (consistent with `Q-037`'s seed-read-only-facts direction, and with the plan-derived folder tree tracking the row, ADR-0040). Consequences, stated: a bound draft **cannot be retitled from the sandbox** — title changes happen on the plan row, under the ADR-0033 row-edit delegation, and flow through to sandbox lists, the editor chrome and the plan-locked folders alike; the document's own working title is retained dormant beneath the link and is revealed again only where the records lifecycle unwinds a binding (one-way binding is not reopened). The binding act itself gains a **confirmation card**: bind pops a card that shows what the document is about to wear — the coded reference, the row's title and schema metadata, the appointments — and states the consequence before an explicit confirm; where a draft sits in a plan-derived deliverable folder that container is **pre-selected as the bind target, never silently bound** (ADR-0040).
