# ISO 19650: what the standard says

*Reference digest — the external standard's own position, in Infora's words. No Infora
decisions live here; those belong in ADRs that cite this file.*

> **Scope and limits.** This is a digest, not a copy. The ISO 19650 series is BSI
> copyright and paywalled; the UK BIM Framework guidance that explains it is free but
> its tables carry BSI copyright too (Guidance Part C p.2 reserves Figure 2 and Table 2
> explicitly). Nothing here reproduces a copyrighted table or figure. Code
> *identifiers* are stated as facts with a citation; everything else is paraphrase.
> **The normative wording is in the standard — where an exact form of words matters
> contractually, read the standard, not this file.**

## 1. The series

Six parts, all published:

| Part | Subject | First published |
|---|---|---|
| 19650-1 | Concepts and principles | 2018 |
| 19650-2 | Delivery phase of assets | 2018 (UK NA revised 2021) |
| 19650-3 | Operational phase of assets | 2020 |
| 19650-4 | Information exchange | 2022 |
| 19650-5 | Security-minded information management | 2020 |
| 19650-6 | Health and safety information | 2025 |

UK implementation is carried by National Forewords in Parts 1 and 2 and a **UK National
Annex to Part 2**. Much of what practitioners call "ISO 19650" — the status codes, the
container ID fields — is in fact **national convention in that Annex**, not
international requirement. Other territories annex differently (Ireland and Canada both
publish their own).

## 2. The CDE is a workflow first, a solution second

ISO 19650-1 cl. 3.3.15 defines the common data environment, and distinguishes the CDE
**workflow** (the process) from the CDE **solution** (the technology). Guidance Part 1
§6.1 and Part C §2.0 both open by naming the same misconception: that a CDE is a
technology, and a single one. It is neither. Part C §2.0: workflows are developed
first, and solutions are selected to facilitate the workflow. A CDE solution need not be
software at all — Part C §1.1 offers a postal service and an organised hard-copy cabinet
as legitimate solutions on a project where digital methods are barred.

A project may run **multiple CDE solutions** that together implement one project CDE.
ISO 19650-2 envisages the appointing party providing *the project CDE*, with delivery
teams permitted their own distributed CDEs **as well as, never instead of** it
(Part C §1.1). Part C §3.2 is candid that there is no industry-standard exchange
protocol between solutions, so metadata transfer between them is commonly manual
re-registration.

## 3. Information container states

ISO 19650-1 Figure 10 (reproduced in Part C as its Figure 2) gives four states:

- **Work in progress** — being developed by its originator or task team, not visible or
  accessible to anyone else.
- **Shared** — approved for sharing with other task teams, other delivery teams, or the
  appointing party. Reached via *check / review / approve*.
- **Published** — authorized for use in more detailed design, for construction, or for
  asset management. Reached from Shared via *review / authorize*.
- **Archive** — a journal of information transactions providing an audit trail of
  container development. Continuous, running alongside all three.

Part C §2.1 stresses this is a simplification: containers can cycle WIP → Shared
several times before any of them is Published, and can traverse different workflows
using different solutions.

Part C §6.1 makes a point Infora should not lose: the **status code is what tells you
which state a container is in**, and doing it that way *"avoids the need to create
physical segregations within the CDE solution using folders or other types of dedicated
areas that can fragment the CDE workflow."* State is metadata, not location.

Part C §6.1 also separates two things routinely conflated: a **status code is not a
purpose of issue**, though fixed relationships exist between them (information issued
for construction must carry a Published status).

## 4. Information container

Defined at ISO 19650-1 cl. 3.3.12 as a *set of information retrievable from within a
file, system or application storage hierarchy* — explicitly including a sub-directory, a
file, **or a distinct subset of a file** such as a chapter, section, layer or symbol.
Part F §4.4.2.2 flags that this is widely misread as meaning "file", and that the
misreading changes how a delivery plan is written.

**Information models** are made up of one or more information containers, at asset,
project and delivery-team level. "Model" is abstract — not necessarily geometry
(Part 1 §6.2).

## 5. Required metadata

ISO 19650-1 cl. 12.1 **recommends** each container in a CDE carries:

- a **revision code**
- a **status code**

ISO 19650-2 cl. 5.1.7 then **requires** the CDE to enable assignment of those two plus:

- a **classification code**

The container's unique ID is itself metadata, but ISO 19650-2 requires the three above
to be assigned *separately from* the ID, not encoded within it (Part C §2.2). The
scope may be extended beyond these three by the project (Part C §2.2, §3.1).

Authors retain strict control of their information throughout its development, and the
series expects that control to be exercised **through metadata assignment** — it is the
metadata that communicates what version a container is at and what it may be used for
(Part C §2.2).

## 6. Revision codes (UK National Annex cl. NA.4.3)

Three components, e.g. `P01.02` (Part C §5.0, Figure 5):

| Component | Meaning |
|---|---|
| Letter prefix — **only** `P` or `C` | `P` = Preliminary (non-contractual). `C` = Contractual |
| Two-digit integer | The **primary revision** — the revision shared outside the author's task team |
| Two digits after a decimal point | The **WIP version** of that primary revision |

`P01.01`…`P01.05` are WIP versions; `P01` is what gets Shared; a decision to develop
further starts `P02.01`. **Published (contractual) information takes the `C` prefix** —
reached only after authorization by the lead appointed party *and* acceptance by the
appointing party (Part C §5.3). The prefix is the reader's signal for whether what they
hold is preliminary or contractual.

Not every container type reaches Published: Part C §5.3 gives coordination-only
geometrical models as an example of information that may stay preliminary for life,
while the drawings and schedules generated from them do go contractual.

This part of the National Annex was **not changed in 2021**.

## 7. Status / suitability codes (UK National Annex, 2021)

The 2021 NA restructured these so that each code aligns to a specific ISO 19650-2
process clause, rather than to a vaguely-worked notion of suitability.

| Code | Alignment / purpose | Revision |
|---|---|---|
| `S0` | Work in progress — initial status, not yet suitable to share outside the task team | Preliminary revision **and version** |
| `S1` | Shared — suitable for coordination. Aligned to cl. 5.6.5 (information model review) | Preliminary revision |
| `S2` | Shared — suitable for information. Aligned to cl. 5.6.5 | Preliminary revision |
| `S3` | Shared — suitable for review and comment. Aligned to cl. 5.6.5 | Preliminary revision |
| `S4` | Shared — aligned to cl. **5.7.1**: submit information model for **lead appointed party authorization** | Preliminary revision |
| `S5` | Shared — aligned to cl. **5.7.3**: **appointing party review and acceptance**. *New in 2021* | Preliminary revision |
| `A1`, `An`… | Published — **authorized and accepted** | **Contractual** revision |
| `B1`, `Bn`… | Published — partial sign-off with comments. **Deprecated in 2021** | Preliminary revision |

Sources: Guidance Part 2 Ed 6 §3.1.10 for the 2021 changes and clause alignments;
Part C §6.2/§6.4 for the S0–S3 purposes, which the 2021 NA did not alter.

Two things the 2021 NA settled about the **A codes** (Part 2 Ed 6 §3.1.10):

1. They are **stage-agnostic**. The 2018 reading — `A2` means RIBA Stage 2 — is gone.
   The 2021 NA adds a note that Published status codes *do not* imply a particular
   reason for issue, and that the reason for each `An` code **must be written into the
   project's information standard**. The guidance's own worked example: `A4` might be
   defined as *authorized and accepted as suitable for construction*, `A5` as *suitable
   as a construction record* — but only because the project said so.
2. The default stage definitions for the 2021 NA are **BS 8536**, not RIBA. Any
   alternative (RIBA, CIC, APM, GRIP, PCF) is permitted but its stage outputs must be
   defined in the project's information standard.

The NA permits codes to be **expanded or excluded** to suit a project, provided the
project's information standard documents them and they are agreed (ISO 19650-2
cl. NA.4.2 Note 2, via Part C §6.4).

**Authorization and acceptance are two distinct acts** performed by two distinct
parties. `S4` → the lead appointed party authorizes. `S5` → the appointing party
accepts. Only after both does a `C`-revision `An` container exist. The 2021 NA
introduced `S5` precisely because the industry was collapsing these into one code — and
Part 2 Ed 6 §3.1.10 accepts that they *are* sometimes one act in practice, where the
delivery team is a single organisation that is both lead appointed party and appointed
party.

## 8. Container unique ID (UK National Annex cl. NA.2)

**Applies to files only.** This is the single largest 2021 clarification: the 2018 NA
gave a field codification without saying what it applied to, and it did not logically
suit layers or objects. The 2021 NA states the codification applies to files, and that
the **project's information standard** defines which file types. Layers are referred out
to BS EN ISO 13567-2 (Part 2 Ed 6 §3.1.1).

Field-length limits were **removed entirely** in 2021 — for every field. Structure is
carried by the **delimiter** (cl. NA.2.3); field lengths, if any, are set in the
project's information standard. The 2021 NA recommends only that fields be kept as
short as practical (§3.1.2).

Field names and purposes, as revised in 2021 (§§3.1.3–3.1.9):

| Field | 2021 position | Was (2018 / BS 1192) |
|---|---|---|
| Project | No length limit | 2–6 chars |
| **Originator** | The **organisation of the information author identified in a TIDP** (cl. 5.4.4) | Ambiguous — task team or lead appointed party |
| **Functional Breakdown** | Renamed; "function" per ISO 19650-1 cl. 10.4 | "Volume/System" — *Volume* was undefined in ISO 19650 |
| **Spatial Breakdown** | Renamed; covers levels, locations, zones, chainage, risers, separate structures | "Levels/Location" |
| **Form** | The **form the information is presented in** only, per BS ISO 29845 (M / D / L / T / I…) | "Type" — mixed content, form, and content+form codes |
| **Discipline** | The **discipline** the container relates to — the task carried out | "Role" — mixed contractual status with job title |
| Number | Length set in the project's information standard | Fixed length |

The Form/Discipline changes both resolve the same 2018 failure: codes that mixed
orthogonal axes, so that two practitioners could legitimately assign different codes to
identical work. Form is now presentation only; **content is the classification
metadata's job, not the ID's**. Where a container mixes forms, the **principal** form
governs (a model containing specification is `M`; a drawing containing tables is `D`; a
report containing photographs is `T`).

Where Functional Breakdown is being used to describe content, care is needed not to
duplicate it in the classification metadata — classification should complement or extend
it, not restate it (§3.1.11).

## 9. Classification

ISO 19650-2 cl. 5.1.7 requires classification metadata per ISO 12006-2. **Uniclass 2015**
is the UK implementation and the NA's referenced system. The 2021 NA cl. NA4.4 adds
direction that the **Uniclass 2015 `PM` table** should be used where possible, being the
table developed to classify *information container content* (Part 2 Ed 6 §3.1.11).

Classification indicates the **contents** of a container, never its type — type is the
ID's Form field (Part C §4.1). Nothing already carried by the unique ID should be
duplicated in the classification.

Two cautions the guidance itself raises:

- Uniclass 2015 is a **living resource**, revised regularly, and its granularity is
  uneven across container kinds. The appointing party should **record the version and
  status date** of the PM table in the project's information standard, and review before
  adopting any later version (§3.1.11).
- Where a container holds mixed information, a **higher level of the PM hierarchy** is
  the right answer (the guidance's example: a business case containing cost models
  classifies as `PM_50_30` Economic viability information).

Part C §4.2 notes that solutions without a classification field commonly accommodate it
as folder structure, and warns that folders should **complement** metadata, never
duplicate it.

## 10. Delivery planning: TIDP and MIDP

From Part F §4 and the ISO 19650-2 clauses it cites.

- **TIDP** (cl. 5.4.4) — every task team produces a delivery plan for its own
  information. It schedules an agreed list of information containers, each with: name
  and title; predecessors / dependencies; level of information need; estimated
  production duration; author; delivery milestones.
- **MIDP** (cl. 5.4.5) — the **lead appointed party aggregates** its appointed parties'
  TIDPs into one plan for the delivery team, accounting for the detailed responsibility
  matrix, cross-task-team dependencies, and appointing party / lead appointed party
  **review durations**. It must then baseline deliverables and dates, notify task teams
  of changes, and inform the appointing party of risks.
- **Neither is a document.** ISO 19650-2 mandates no template and identifies both as
  *resources* — a spreadsheet, a programme tool, or any other digital management tool
  (§4.4.2.1, §4.5.2).
- Both are **contractual**: cl. 5.4.7 requires each appointed party's appointment to
  include its TIDP; cl. 5.4.6 requires each lead appointed party's appointment to
  include the MIDP. Post-appointment updates run through agreed change control.
- A container's **name and title is not its unique ID** (§4.4.3.1). Both are recorded.
- Milestones are expressed **in status codes** — Part F's own worked example is
  "for comment with status S3", "published within stage 4 with status A4" (§4.4.3.6).

Part F §4.4.2.2 sets out a fork Infora's plan sits directly on top of. A TIDP can list
either:

1. **Files** — every predicted file, with predicted IDs. Guidance verdict: hard to
   predict at appointment, forces a focus on presentation over information, and when one
   detail turns out to need six drawings the IDs must be added, withdrawn or re-assigned
   *and* the change controlled — "dozens, if not hundreds, of times". A significant
   administrative burden.
2. **Information production tasks** — what information is needed, not how many files
   carry it. Looser, but survives one-file-becomes-six without a change-control event.

The guidance recommends neither exclusively; it says both should be considered, and that
in either case the lead appointed party's job is unchanged.

Above the delivery plans sit the **federation strategy** (why and how the information
model is divided) and the **information container breakdown structure** (the manageable
units), then the **responsibility matrices**. The breakdown structure is determined by
the lead appointed party with the delivery team; the federation strategy by the
appointing party where they have project-wide requirements, otherwise by the lead
appointed party (Part 1 §6.3).

## 11. Information requirements hierarchy

Four resources, all the appointing party's (Part 1 §5.2, ISO 19650-1 cl. 5):

| | |
|---|---|
| **OIR** | Organizational information requirements — against organisational objectives |
| **PIR** | Project information requirements — the purpose, design and construction of an asset |
| **AIR** | Asset information requirements — operation and maintenance |
| **EIR** | Exchange information requirements — **in relation to an appointment** |

Requirements pass *down* delivery and task teams to where information is most
efficiently produced, and information is collated as it passes back *up*. Lead appointed
parties may add their own requirements when passing down (cl. 5.4.3), proportionately.

**Level of information need** (ISO 19650-1 cl. 11.2) is the framework for how rich each
deliverable must be — set to avoid both too little (risk) and too much (waste). The
*method* for defining it is set by the appointing party in the project's information
standard; it is then identified per information container. Note it is never abbreviated.

## 12. Parties, teams, roles

- **Appointing party** — the client. Provides and manages the project CDE (or a third
  party does on their behalf). Owns the project's information standard, information
  production methods and procedures, reference information and shared resources.
  **Accepts** information models (cl. 5.7.3/5.7.4).
- **Lead appointed party** — accountable for timely and complete production of
  information per the MIDP. **Authorizes** information models (cl. 5.7.1/5.7.2).
- **Appointed party / task team** — responsible for generating the information assigned
  to it, per its TIDP. Assigns status and revision metadata.

A single organisation can be both lead appointed party and appointed party — managing
information and generating it (Part 2 Ed 6 §3.1.4).

The **information management function** is a function, not a job title (Guidance Part A).

## 13. Open data

From Part B. ISO 19650-1 cl. 6.1 states information exchanges should use **open
standards wherever possible**; reiterated at ISO 19650-2 cl. 5.1.6 and in the NA. Open
data is data not restricted to specific software solutions — the guidance's list of open
formats includes HTML, PDF, DOCX, XLSX, PPTX, ODT/ODS/ODP, IFC, PNG, GIF, MP3, CSV, ZIP.

The archival argument is the one that carries: assets outlive software, and there is no
guarantee a future solution can read today's proprietary format (§1.2).

buildingSMART solutions and where the guidance maps them to 19650-2 clauses:
**IFC** (ISO 16739) for requirements structuring and exchange · **IDM** (ISO 29481-1) for
QA-check and review methodologies, cl. 5.6.3/5.6.4/5.7.2/5.7.4 · **MVD** for
purpose-specific IFC subsets (COBie 2.4 is one) · **BCF** for issue exchange in place of
email chains · **bSDD** (ISO 12006-3) for unambiguous property definitions.

## Superseded — do not cite

The 2018 National Annex and everything written against it. This matters because most of
the free material online — including UK BIM Framework **Guidance Part C Edition 1, which
is still the current edition of Part C** — predates February 2021 and does not say so
prominently. Part C p.7 does carry the warning that an Edition 2 was planned for Q2 2021
to reflect the 2021 NA; **that edition was never published.** Part C's Table 2 and
Table 4 are 2018 and are wrong.

| 2018 (do not use) | 2021 |
|---|---|
| `S5` = "Withdrawn — no longer used" | `S5` = appointing party review and acceptance (cl. 5.7.3) |
| `S6` = suitable for PIM authorization | **Removed** |
| `S7` = suitable for AIM authorization | **Removed** |
| `CR` = as-constructed record document | **Removed** — duplicated an `A` code |
| `B1`/`Bn` = partial sign-off | **Deprecated** |
| `A2` = RIBA Stage 2, etc. | Stage-agnostic; meaning set in the project's information standard |
| `S4` = "suitable for stage approval" | Reworded; aligned to cl. 5.7.1 |
| ID field "Type" | **Form** — presentation only |
| ID field "Role" | **Discipline** |
| ID field "Volume/System" | **Functional Breakdown** |
| ID field "Levels/Location" | **Spatial Breakdown** |
| Fixed field lengths | No limits; delimiter carries structure |
| ID applies to "information containers" | ID applies to **files** only |

Also withdrawn upstream: **BS 1192:2007+A2:2016**, which the NA replaced and from which
much surviving industry practice (and its `D` status codes) descends.

## Known gaps in this digest

Flagged rather than guessed. Anything below is unverified and must not be relied on
without reading the source.

1. **The 2021 NA has not been read directly.** Everything in §7 and §8 is via Guidance
   Part 2 Ed 6, which is authoritative on the *changes* but does not reproduce Table NA.1.
   The exact 2021 wording of the S0–S3 purposes is carried forward here from Part C
   (2018) on the strength of Part 2 Ed 6 saying only that S1–S3 were *"aligned with"*
   cl. 5.6.5 — not reworded. **Verify against the NA before any wording is quoted
   contractually.**
2. **ISO 19650-4:2022 (information exchange) has not been read.** It is the part closest
   to what a review-and-issue cycle actually does — it specifies the criteria for
   deciding an exchange is acceptable (completeness, conformance to exchange schemas,
   continuity of concepts between exchanges, elimination of spatial and specification
   conflicts). UK BIM Framework Guidance 4 covers it.
3. **19650-3 (operational), -5 (security-minded), -6 (health and safety) not read.**
   -5 in particular bears on any cross-organisation access model.
4. **Guidance Part 1 was read at Edition 2 (2019); Edition 3 (2024) supersedes it.**
   The concepts cited here are stable ones, but Ed 3 should be the citation.
5. **Guidance Parts A, D, E and the Information Protocol were located but not read.**
   The Information Protocol is the contractual appendix — where liability for
   information actually lands.
6. **Uniclass PM table contents not held.** The live tables are published by NBS and
   revised on a rolling basis.
