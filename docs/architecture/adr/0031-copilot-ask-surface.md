# ADR-0031 - Microsoft 365 Copilot is an external Ask surface: `@Infora` reaches the chat agent through the same API, and a context-free Copilot conversation binds to exactly one project environment

**Status:** Accepted (2026-07-01). An MVP scope addition. Builds on ADR-0028 (Ask = a Run in a Conversation with no Work item; every execution is audited), ADR-0029 (the one Context-assembly gateway with no scope-widening parameter), ADR-0025 (exactly one assembly environment per request), ADR-0020/0022 (access-resolution before retrieval; a scope grounds only its own projects). Mirrors the Word add-in as a thin-client M365 surface (component 8).

**Context:** The MVP should let a user invoke Infora from inside Microsoft 365 Copilot — tag `@Infora` in a Copilot chat and get an answer from Infora's chat agent (the Ask / Project chat path). The mechanism is Microsoft's documented extensibility model: a **declarative agent** published to M365 Copilot (what users tag), with an **API plugin** (OpenAPI/REST or MCP) that calls Infora's API, authenticated by **Entra ID SSO** so the M365 user's identity passes through. Nothing about the chat agent itself is new — it already exists in the design. Two things are new and load-bearing: how the external M365 identity becomes an Infora subject of access, and — the real fork — how a *context-free* Copilot chat resolves *which project* it answers over. The Word add-in resolves its project from the open document; a Copilot chat has no such anchor, and access resolution (ADR-0025) cannot run without an environment.

**Decision:**

**1. Copilot is a Surface, not new capability.** It is a thin client over the one typed API, exactly like every other surface (component 8): the declarative agent + API plugin hold no intelligence; they call Infora's API, which runs the existing Ask path — a Run in a Conversation with no Work item (ADR-0028 §1), assembled by the Context gateway (ADR-0029). Orchestration, context, governance, audit and access scoping all stay behind the API and are inherited, not re-implemented.

**2. A Copilot conversation binds to exactly one project environment.** Because a request must run in exactly one assembly environment (ADR-0025) and Copilot supplies none, the user names or picks the project (in the query, or via a first-turn prompt), and the Copilot thread **binds to that project's environment for its life**. Every turn in that thread runs in that one project environment. This is the explicit-project-binding rule.

**3. Cross-project and workspace-scoped Ask are deferred.** Answering "across all my projects" in one Copilot thread is out of scope for v1: it breaks the scope-grounding rule (ADR-0020 — a scope grounds only its own projects) the moment two of a user's projects have different owners, forcing either a cross-wall leak or silently dropped grounding. A workspace-scoped Ask (the org's own informing channel + authority corpus, no project grounding — the ADR-0025 workspace case) is a coherent later addition but not v1.

**4. The ethical wall holds by construction, unchanged.** The Copilot call goes through the same API and the ADR-0029 gateway, which has no scope-widening parameter. A Copilot query therefore reaches only what the requester's Participant could already reach in the bound project; the surface cannot widen scope. Adding Copilot does not touch the wall — the backend enforces it regardless of doorway.

**5. Identity is Entra SSO mapped to an Infora Participant.** The M365 user authenticates via Entra ID SSO; Infora maps that external identity to an Infora User and resolves its Participant on the bound project. A user with no Infora Participant on that project gets nothing — access resolution denies exactly as it would on any surface. No Copilot-specific access path exists.

**6. Read-only Ask in v1; no drafting, no Signals.** Copilot is a read surface: grounded, cited answers rendered back in Copilot. It does not draft controlled content and does not capture accept/edit/reject Signals — the Word add-in remains the drafting and Signal surface (component 8, ADR-0004 split). Citations are returned in the response for Copilot to render.

**7. Every Copilot-originated Run records its origin.** A Run carries the surface it originated from, so a Copilot-initiated execution is distinguishable in the append-only audit trail (ADR-0028 §3).

**Consequences:** A new thin-client app (`apps/copilot-agent` — the declarative agent manifest + API-plugin definition, sibling to `word-addin`) and an Entra-SSO → Infora-Participant identity mapping are added; the chat agent, assembly, access and audit are reused untouched. The data model gains a `surface` field on the Conversation (inherited by its Runs) and an external-identity link on the User; the Conversation's existing `project_id` is what carries the project binding (§2), so no new environment machinery is needed. This reinforces the M365 GTM lever — the Copilot agent, like the Word add-in, deploys centrally through M365 admin, so an owner can turn Infora on for every appointed user at once. Honest limits, deliberate for v1: one bound project per Copilot thread (a user cannot ask across projects in a single thread — a confidentiality-driven UX constraint, not a technical one); no Signal capture from Copilot (it is a read surface); cross-project and workspace-scoped Ask left as later design problems. None of these weakens the wall, because all of them are *narrower* than what the backend already permits.
