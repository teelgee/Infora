# ADR-0024 - Vectors live in Postgres + pgvector, co-located with the relational access and metadata, as the long-term store for the per-tenant corpora; embeddings are pinned and versioned per index

**Status:** Accepted. Builds on ADR-0020 (access resolved before retrieval) and ADR-0022 (hybrid retrieval and the document-state filters). Relates to ADR-0023 (the authority register as the one corpus that may later split out).

**Context:** ADR-0022 fixed that grounded retrieval pre-filters on relational facts — memberships, per-deliverable grants, ethical walls, document state, version currency — *before* vector search, and that search is hybrid (vector recall plus lexical match on the deliverable code and metadata). The store had to support all of that. pgvector was noted for the walking skeleton; the open question was whether it is the long-term substrate or a placeholder to be swapped for a dedicated vector database (Pinecone, Weaviate, Qdrant, Milvus). The repo is greenfield, so the choice was genuinely open rather than inherited.

**Decision:** Postgres with the pgvector extension is the **long-term** store for the per-tenant corpora — the project library and org and programme context — not just the skeleton. Vectors sit in the **same database as the relational access and metadata**, so a single query performs vector similarity, lexical code/metadata match, structured filters (code, type, status, version) and the access-control join together, with access applied as a genuine **pre-filter**.

The deciding reason is a security property, not performance. The access pre-filter that ADR-0020 and ADR-0022 require is relational; co-locating the vectors with that data keeps resolve-before-retrieve a real pre-filter. A separate vector database forces either weaker metadata-only filtering or post-filtering, and **post-filtering across an ethical wall risks leakage** and breaks the guarantee. Secondary reasons: one datastore to secure, audit and back up, which serves the SOC 2 / Cyber Essentials / GDPR posture; and the corpora are not web-scale — a project library is thousands to tens of thousands of chunks, comfortably within pgvector's HNSW indexing, far from the regime where a dedicated ANN store earns its keep.

Embeddings are **model-agnostic but pinned and versioned per index**: query and document vectors must come from the same model, so an embedding-model change is a **re-index migration, not a hot swap**, and the embedding model id and version are stored beside every vector. Build 1 uses a strong general provider embedding behind the model-layer router; domain-tuned embeddings are a later option, not a build-1 need — and if ever pursued, only on de-identified or non-client data, never trained per-client on customer corpora (ADR-0026, zero training on customer data).

The authority corpus is the sanctioned exception. Being universal, public and not access-resolved (ADR-0023), it is the one corpus that does not need co-location with ACLs, so if it alone ever outgrows pgvector's ANN comfort it may move to a dedicated index without weakening any wall.

**Consequences:** One datastore holds vectors, metadata and access together, which is what keeps the no-leak property at the retrieval layer rather than relying on output-time filtering. The hybrid search needs a structured metadata layer beside the vectors, but that layer is mandatory for the state rules regardless, so its marginal cost is small. A dedicated vector database is explicitly **not** adopted now; the trigger to revisit is a single corpus outgrowing pgvector's ANN scale or latency — most likely the authority corpus, which is the clean seam to split. Re-indexing on an embedding-model change is the accepted cost of staying model-agnostic, and is a planned migration rather than a surprise.
