# ADR-0040 - Per-sandbox super-user settings: configuration is a property of the sandbox, set by the owning org's super-user or the owner-super; the first setting gates ordinary members' folder creation

**Status:** Accepted (owner-ruled 2026-07-25, sandbox-structure build session). Builds on ADR-0036 (sandbox participant-scope model) and the classes-of-user model (T-176: `owner_super` / `guest_super` / `ordinary`, derived from `membershipRole × elevated`; T-174's `participants.elevated`). Refines ADR-0036's "Open — elevated super-user abilities" (the T-133 item), for the sandbox-configuration slice of it.

**Context:** ADR-0036 made the sandbox a first-class, scope-bearing object but left it with no *configuration*: every participant in a sandbox's scope could do everything the sandbox allowed, uniformly. The owner asked for a concrete lever — whether ordinary users may create new folders, or must work within a structure a super-user laid out (T-182) — and named the broader concept behind it: a **super-user settings surface**, where a super-user configures how a project (or a sandbox they are even a guest in) behaves. The question was where the setting lives (per-sandbox vs per-project) and who owns it, reconciled with ADR-0036 §5's self-serve/owner-gated split and the T-176 class model.

**Decision:**

**1. Settings are per-sandbox, carried on the sandbox row.** A setting is a column on `sandboxes` (the first is `allow_member_folder_create`, default `true` — the prior self-serve behaviour). Per-sandbox, not per-project: a project holds unlimited sandboxes at different scopes owned by different organisations (ADR-0036), and each owning organisation configures its own working areas independently. A project-wide policy would force one organisation's structure discipline onto another's sandbox, which the wall model rejects.

**2. Configuration is a super-user act, split along the wall exactly like provisioning.** `canConfigureSandbox` (governance): the **project owner super-user** may configure any sandbox (the owner-super override), and a **guest super-user** may configure a sandbox **its own organisation owns**. An ordinary participant never configures — settings are a super-user surface. This mirrors ADR-0036 §5's self-serve/owner-gated split: an organisation configures its own sandboxes freely; nothing here opens cross-organisation visibility, so the owner is not in the path of an org's internal working-area settings, but the owner-super retains a project-wide override.

**3. The setting governs the ordinary participant's reach; the super-user is never gated by it.** With `allow_member_folder_create = false`, only a super-user *of that sandbox* (guest-super of the owning org, or owner-super) may add or nest folders; ordinary members work within the structure. The enforcement gates on `canConfigureSandbox`, not on mere elevation — a foreign guest super-user present in a shared sandbox follows the owning org's setting, because the structure is the owning organisation's to shape. `canConfigure` is returned as a **self fact** on the sandbox read (decided server-side per requester), so the surface shows the Settings control and the folder affordances to exactly those who hold them.

**Consequences:** `sandboxes` gains a settings column (and will gain more — this is the seed of a per-sandbox settings surface, not a one-off toggle). The sandbox read carries `allowMemberFolderCreate` and the per-requester `canConfigure`. A new `PATCH /sandboxes/:id/settings` (super-user only) and folder-creation enforcement (`member_folder_create_disabled`, 403) land. No new stored role — the act composes from the existing `elevated` capability and `owningOrganisationId`, so ADR-0016's owner/member collapse is untouched. **Deferred:** project-scope settings (a genuine project-wide policy surface), and richer per-sandbox settings beyond folder creation — added here as they are needed, on the same per-sandbox, super-user-configured substrate.
