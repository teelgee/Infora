# Flows: Document management and Collaboration (build reference)

Prepared 2026-10-05 for the pillar walkthroughs (`demo/plans/BRIEF.md`).
This file builds on `demo/archive/2026-10-sizzle/research/product-inventory.md`. It does not repeat
that file's design-token tables, claims list or app-builder notes. It adds the
**screen-by-screen flows**, the **exact copy on each screen**, the **layout
geometry** needed to rebuild each screen in React, and a ruling on every
conflict between sources.

Where this file and a cited source disagree, the source wins. Screenshots are
in `docs/architecture/user-story-screens/` and are cited by filename only.

## 0. How to read this file

### 0.1 Status marks

- **BUILT**: running in the app today. Where a screenshot exists, it is the
  spec. Where none exists, the cited code is the spec.
- **BUILT, NOT PHOTOGRAPHED**: the code exists, but nobody has captured it.
  Rebuild it from the cited component and its copy, which this file quotes.
- **RULED, NOT BUILT**: an accepted ADR decides it and no screen shows it. Draw
  it in the design system's language, and the caption may call it "coming".
- **DESIGNED, NOT RULED**: the user story describes it, and an open question
  (`Q-###`) still gates it. Show it only as vision, and only if needed.
- **VISION (proposed here)**: in neither the record nor the code. This file
  proposes a drawing in the design system's language. It needs the owner's
  nod before it is final.

### 0.2 Frame size: rebuild at 1536×864 CSS px, rendered at 1.25×

Every screenshot is **1440×900 (16:10)**. The exception is `13a-promotion-window.png`,
which is 1440×1180 because it is a full-height capture.

The recommendation is to build the React shell at a **CSS viewport of
1536×864** with a device scale factor of **1.25**. That renders to exactly
1920×1080. Every pixel measurement in this file is a CSS px taken from the
1440-wide screenshots, so it transfers one to one. The frame gains 96px of
width, which goes to the main pane: the content column stays at its
`max-width: 1120px` and centres. It loses 36px of height, so pages scroll or
crop slightly lower. Type then reads at the same size as the product. Rendering
natively at 1920 CSS px would make the UI look small and empty.

### 0.3 Vocabulary, with plain glosses for captions

Captions must be plain. These glosses are safe to put on screen.

| Term (CONTEXT.md) | Plain gloss for a caption |
|---|---|
| **Project** | One infrastructure scheme. Here: *Wrenfield–Ashcombe 400kV Connection*. |
| **Organisation / owner / member** | A company on the project. The **owner** (Trentmoor Energy, the client) runs the project. Every other company is a **member**. |
| **Ethical wall** | Each company sees only its own work, plus what has been deliberately shared with it. |
| **Deliverable plan (TIDP)** | The list of documents a company has promised to produce. The client's combined view is the MIDP. |
| **Container / deliverable** | The permanent slot for one planned document. It holds every version under one reference. "The document's home in the plan." |
| **Document reference** | The document's code, generated by the plan (`WA-EIA-MST-001`). "Its reference number, issued by the plan, never typed by hand." |
| **Sandbox** | The working area where drafts are written. It has no document controls, and the AI never treats it as a source. |
| **Working area** | Built UI name for a company's own sandbox ("Calder & Hale — working area"). |
| **Bind** | Link a draft to its planned slot. The draft takes the plan's reference and title. |
| **Freeze** | Lock a snapshot of the draft so it can be checked without it changing underneath. |
| **Internal QA round** | The company's own check before anything leaves it. The client never sees it. |
| **Promote** | Send a checked version to the client for review. On screen: "Promote" and "Promote to review". |
| **Revision code** | Which issue this is. **v0.x** = a working draft, **P01, P02** = issued for review (preliminary), **C01** = the accepted, contractual issue. |
| **Status code** (UI label: "Suitability code") | What an issue may be used for. **S0–S5** = work in progress or shared, **A1** = published, authorised and accepted. Prefer "status code" in captions. |
| **Acceptance code / verdict** | The code a reviewer puts on a comment, and the one the lead reviewer puts on the whole document. |
| **Review round** | One pass of review on one version (round 1 on P01, round 2 on P02). |
| **Review group / lead reviewer** | The named people reviewing. The lead reviewer (Rachel Bowen) alone closes a round and sets the verdict. |
| **Lead author / authoring team** | The people producing the document and answering comments. Eleanor Price is the lead author. |
| **Review record (DRR)** | The single live table of every comment, its code and its answer, across all rounds. It replaces the emailed comment spreadsheet. |
| **Acknowledge** | The client's receipt of a submission. This act opens the round. |
| **Close & issue** | The lead reviewer ends the round and hands the comments back to the authors. |
| **Response** | The author's answer to a comment. It either points at the change in the next version, or says "no change" with a reason. |
| **Transmittal** | The record of who issued which version to whom, and when. Nothing is emailed. |
| **Project library** | The approved documents the AI is allowed to draw on. |
| **Context state** | Whether the AI may use a document. On screen: "Not used for AI answers — <reason>". |
| **Authoritative** (brief's word) | Accepted under an accepting code (A1), issued as the contractual revision **C01**, and in the project library. It is now the project's record, and the AI may rely on it. |
| **Multiplayer** | Several people working one document and one shared agent chat at the same time (ADR-0039). |
| **Presence** | Who else has the document open, shown as avatars (T-175). |
| **Shared sandbox** | A working area that more than one company can see. Only the client (the project owner) can open one. |
| **Suggestion** | Text the agent proposes, which a person accepts, edits, refines or rejects. |
| **Source (pill)** | The small tag after a sentence that names the library document backing it. |

**Words that look right but are wrong.** The brief says "issued for review".
In Infora the producer **promotes**, which "submits it to Trentmoor Energy"
(see `13a`). **Issue** is the lead reviewer's act: "Close & issue the round",
or "Issue externally…" from the library. A caption may say "sent to the client
for review", but the button the cursor clicks is **Promote**.

## A. Document management flow

**The story in one line.** Calder & Hale's Eleanor Price drafts the Land
Quality method statement in her working area. Owen Vance checks it in-house.
Eleanor promotes it to Trentmoor Energy. Rachel Bowen reviews it and comments
on the PDF, while Calder & Hale sees nothing. Rachel issues the comments back.
Eleanor answers each one and promotes version two. Rachel accepts it, and C01
becomes the project's record in the library.

**The deliverable throughout:** `WA-EIA-MST-001`, *EIA Scoping Method Statement
— Land Quality*, producer Calder & Hale, discipline EEN, security OFFICIAL,
native format DOCX. Revisions: v0.1 (working) → P01 (round 1) → P02 (round 2)
→ **C01** (accepted, A1).

**Seats.**

- **Consultant seat:** Eleanor Price, Calder & Hale. Badge "● Member" (green).
  User chip "Calder & Hale — Consultant".
- **Internal QA seat:** Owen Vance, Calder & Hale, chip "OV".
- **Client seat:** Rachel Bowen, Trentmoor Energy. Badge "● Owner" (slate).
  User chip "Trentmoor Energy — Owner".

All three share the shell described in §C.

The brief allows about 2 minutes. §A.9 gives a suggested cut. A.1–A.8 are the
full menu of beats.

## B. Collaboration flow

**The story in one line.** Trentmoor's Rachel Bowen opens a **shared working
area** for exactly two people: Calder & Hale's Eleanor Price and Redgate
Ecology's Nadia Okonjo. Both open one new document at the same time. Eleanor
asks the agent for a cited paragraph, Nadia writes beside it, and both see the
same chat, the same suggestion and the same text. No attachment is emailed, and
nobody else on the project can see in.

**Why this casting.** The deck's pillar 03 line is "Shared spaces across
organisations. No attachments, no lost work." A shared sandbox across two firms
is the only built place where two organisations co-author. Only the project
owner may create one (ADR-0036 §5, ADR-0042 §1), which makes Rachel the
creator. A single-organisation version (Eleanor and Owen Vance in Calder &
Hale's working area) is the fallback if cross-organisation co-editing is judged
too visionary. Every mechanic is identical.
