# ADR-0020 - Context has three scoped stores: org and programme are private-by-construction and inform only, project is access-resolved and the sole store that grounds; one working input is assembled per request and org context never reaches another organisation

**Status:** Accepted. Builds on ADR-0011 (the project library is the sole grounded corpus) and ADR-0018 (ethical walls as the standing posture). Refined in Session 3: programme context may carry grounded and guiding channels to its *own* projects, configured per project by the programme owner, so "programme informs only" below is superseded for the programme's own projects; org context remains informs-only. The governing rule becomes: a scope may ground its own projects but never grounds outside itself.

**Context:** Context was named as the umbrella for everything that becomes an agent's working input, with two scopes asserted in the glossary but never pinned down: what each store holds, which is gated by what, how the two combine into one input at query time, and — the load-bearing question — how one organisation's context improves its output without ever reaching another organisation on the same project. ADR-0011 had already drawn a trust line for the document side (only the project library grounds; the AI never grounds on the sandbox or the DRR), and that line needs mapping onto the context stores so it is one rule, not two. Separately, a programme owner runs many projects and wants its knowledge to compound across them, which the two-store model did not express: org context travels to *every* project an organisation touches, including ones it merely joins, so it is too broad to carry programme-specific knowledge cleanly.

**Decision:** Context is three scoped stores, not two.

**Org context** is private to one organisation and portable to every project it touches, owned or joined. It holds the org's sources, distilled knowledge, precedents, and custom workflows — the portable toolkit. It is private-by-construction: keyed to the organisation and readable only by that organisation's Participants, behind the ethical wall, never shared, not even with a project owner (ADR-0018).

**Programme context** is private to a programme owner organisation and scoped to that programme's projects only. It holds the knowledge, precedents, and standards the owner wants to compound across its portfolio but not carry into unrelated projects where it is merely a member. It sits between org and project on breadth of travel — narrower than org context (one programme, not everywhere), broader than project context (the programme's projects, not one) — and is private-by-construction on the same terms as org context: the programme owner's own, invisible to member organisations.

**Project context** is scoped to one project and shared among its members by access. It holds the project's sources, knowledge, and history. It is the only access-resolved store: visibility is decided per deliverable, default-deny, owner-curated (ADR-0011, ADR-0016).

The ground-versus-inform line maps onto the stores by confidentiality: **a scope may ground its own projects but never grounds outside itself** (refined in Session 3). Project context grounds its members through its project-library subset. A programme owner may additionally let its projects ground on programme-scoped corpora and on sibling-project libraries within the programme, configured per project — safe because every such project is the owner's own, so no client boundary is crossed. Org context never grounds: it travels to unrelated clients, so grounding it would carry one client's material into another's request. Private context still steers how output is produced (house style, precedent approach) but is never tied to a generated claim as a citable source outside its own scope. (The original ruling — programme grounding only by the owner deliberately copying a deliverable into another library — is relaxed to this configurable inheritance; the confidentiality result is identical because the breadth never exceeds the owner's own projects.)

**One working input is assembled per request and per Participant**, in the requesting user's own session. Access resolution runs first (the access layer), establishing the requester's organisation, project role, and which deliverables they may see. The engine then assembles one input from: the requester's *own* org context; the requester's programme context if the requester's organisation owns the programme this project belongs to; and the access-resolved slice of this project's context. Grounding draws only on the project-library slice; the private stores are steering inputs.

Org context never reaching another organisation is **structural, not a filter at output time**, resting on three guarantees that apply equally to org and programme context:
- They are private-by-construction. There is no code path that reads organisation A's context into organisation B's request, so there is nothing to filter out.
- They are read sources, never destinations. They are read into a transient working input; nothing distilled back into *shared* project context carries them.
- Only deliberately-shared artifacts cross the wall, and they cross as project artifacts. When a consultant's draft — informed by its own precedents — is accepted, what enters the project library is the accepted deliverable, an owner-curated shared artifact, not the precedent; the precedent stays in org context. Private context improves the organisation's own contribution, which becomes shared only via the deliberate promote → accept → share path, and only ever as project content.

**Consequences:** The data model carries context on three scopes — an organisation key, a programme key, and a project key — with two of the three (org, programme) private-by-construction and one (project) access-resolved through the same machinery that already gates the library. Assembly is three reads in the programme-owner case and two otherwise, composed at request time and never persisted as a merged store, which is what makes "improve shared output without leaking" hold without a redaction pass. The cost is real: programme context adds a third scope to assembly and to access resolution, and a programme key to the model, for a benefit org context already partly delivered; it is justified only by the need to scope an owner's compounding knowledge to its programme rather than to everywhere it works. The ground/inform line is now one rule across documents and context: only the project library grounds, everything else informs, so there is no second trust flag to maintain. Closes the Component 2 open questions on combining the stores at query time and on keeping org context out of other members' view; leaves open knowledge distillation, precedent selection, retrieval ranking within each store, and the long-term store and embedding choice.
