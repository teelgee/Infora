# ADR-0043 - The editing & co-authoring substrate: Infora is a WOPI host and stays the system of record; native Office files are co-authored in place — in real Microsoft Office via Microsoft's CSPP — with files never leaving Infora; the SharePoint-as-substrate route is rejected because it collides with the cross-organisation wall

**Status:** Accepted (owner-ruled 2026-07-25, sandbox co-authoring design session). The engine target — **real Microsoft Office via Microsoft's Cloud Storage Partner Program (CSPP)** — is the owner's decision; the substrate posture and the mechanics are Claude's, defended here. Refines ADR-0034 (canonical format / renditions), ADR-0036 (sandbox participant scope), ADR-0039 (multiplayer collaboration), ADR-0041 (sandbox versioning). References ADR-0024 (colocated store, immediate revoke), ADR-0032 (freeze / the head-lock check-out), ADR-0037 (deployment security tiers). Benchmarked on the two dominant legal DMS: **iManage Work** Microsoft Co-authoring (GA — real-time cursors/presence, auto-save, edits sync back to the iManage workspace, revisions in the timeline) and **NetDocuments CollabSpaces** ("files never leave the DMS", collab spaces inherit the matter workspace's governance) — both keep files in their own DMS and become WOPI hosts, renting Office co-authoring via CSPP.

**Context:** The sandbox is meant to behave like SharePoint/iManage: a producing team drops drafts into it, opens them in Word / PowerPoint / Excel, edits, and expects the edits to sync straight back. ADR-0034 forbade this — an uploaded file was "not edited by Infora", and the only way to edit was a one-way, lossy "Open in editor" conversion to Infora structured text. Two facts framed the reversal. First, real-time co-authoring *inside* the Office applications is a Microsoft capability: the operational-transform/merge engine lives in the Office apps and Microsoft's cloud service, not in any storage layer we could build, so Infora cannot implement Office multiplayer itself. Second — established by research this session — the two market-leading legal DMS solved exactly this problem the same way: they keep files inside their own DMS and expose them to Microsoft Office through the **WOPI** protocol under a CSPP partnership; they did **not** rebuild themselves as a view over the customer's SharePoint. The competing "Infora as a view over SharePoint (via Microsoft Graph)" design was considered seriously and fails on Infora's defining constraint: SharePoint tenancy is per-organisation, whereas an Infora project is cross-organisation with an ethical wall, and Infora's `sandbox_scope_grants` (append-only intervals, revoke-in-the-same-transaction, ADR-0024/0036) are finer than SharePoint ACLs — handing the wall to a per-org SharePoint tenant would be both a tenancy mismatch and a coarsening of the wall. Separately, the grounding corpus is **library-only** (retrieval filters to live library-scope containers; the sandbox never grounds), so making the sandbox a co-authoring surface has **no** grounding implication — a point that de-risks the whole change.

**Decision:**

**1. Infora stays the system of record and the ethical-wall authority; files stay in Infora's own store.** The canonical bytes live in Infora's storage (the `file_ref` pointer, real object storage per ADR-0037), and access, grants, metadata, versioning and the review cycle remain Infora's. This is the iManage/NetDocuments posture. A SharePoint / Microsoft Graph connector may exist as an **optional import/export convenience** for M365 shops, but it is **never** the storage substrate and never owns the ACL.

**2. Infora is a WOPI host.** Infora implements the WOPI host contract (`CheckFileInfo` / `GetFile` / `PutFile` / lock family) over its own store, so an Office editor opens a sandbox file straight from Infora and saves back to Infora. `PutFile` writes a new **`v0.x` ambient working revision** (ADR-0032 history, ADR-0041 numbering). The WOPI **lock reuses the existing check-out**: `head_locked` + the append-only `sandbox_checkout_events` trail (ADR-0032 addendum, T-180), which was already built format-agnostic ("holds for any format… docx/pptx/xlsx"). One lock mechanism, whether the writer is the Office engine or an internal round.

**3. The engine target is real Microsoft Office via CSPP; a self-hosted engine serves only as the interim dev harness.** The shipping co-authoring surface is genuine Microsoft Office for the web (and, as a later CSPP milestone, the desktop apps), for the fidelity AEC clients who live in Office expect — the owner's decision, matching iManage and NetDocuments. Because CSPP is a commercial partnership with an approval process (see the external dependency below), the WOPI host is built and validated against a **self-hosted engine (Collabora Online or OnlyOffice Docs)** as a dev/staging harness, then pointed at Microsoft Office once CSPP is granted. The self-hosted engine is a test rig, not a shipping target; the WOPI host is identical either way, so the swap is a configuration change, not a rebuild.

**4. WOPI file access is gated by `sandbox_scope_grants`; the collaboration space inherits its grants.** The ethical wall is enforced where the bytes are served: the WOPI host resolves the requester's entitlement through the same grant set as every other read (ADR-0036), and a revoke drops co-authoring access in the same transaction as the read (ADR-0024). The co-authoring space **inherits the sandbox's grants** (the NetDocuments CollabSpaces pattern) — it introduces no new access object, and, consistent with ADR-0036 decision 2, there is still no within-sandbox wall.

**5. Real-time collaboration splits by format.** Co-authoring of **Office-format files** is delegated to the Office/WOPI engine — Infora does not build it. Infora's own multiplayer — the shared agent **Conversation** thread, presence (T-175), and any future CRDT (ADR-0039) — governs **Infora-native authored documents and the agent conversation**. The two coexist in one surface: the file is co-authored in Office while the shared agent thread grounds against the library and the informing channel stays per-invoker (ADR-0039 unchanged).

**6. ADR-0034's "Infora does not edit uploads" is relaxed.** An uploaded native file is now **co-authored in place**, its native file staying canonical, with edits syncing back through the WOPI host — no lossy conversion to Infora text is required to edit it. "Open in editor" (convert an upload to authored Infora structured text, for the AI-native drafting substrate) **remains available but becomes one option, not the only edit path**. The origin model, renditions, and the authored = Infora-structured-text substrate are otherwise unchanged.

**External dependency — the CSPP application (owner-driven, gates go-live, not the build).** Real-Office co-authoring cannot ship until Microsoft approves the CSPP partnership; the application has real lead time and is a business action the owner starts, tracked outside the ticket board. It gates **go-live of P3**, not the P1/P2 build: P1 (DMS parity) ships independently of Microsoft, and P2 (the WOPI host) is built and validated against the dev-harness engine while the application is in flight. This is the accepted trade-off of choosing real-Office fidelity over a self-hosted engine as the shipping target.

**Consequences:** `file_ref` becomes a genuine pluggable storage-substrate pointer with a WOPI-addressable item behind it (it was always "a pointer either way"). `head_locked` becomes the WOPI lock as well as the freeze lock — one mechanism, more triggers. Each Office save boundary appends a `v0.x` ambient working revision (ADR-0041); the P/C issue rules at freeze/promotion/acceptance are untouched. Grounding is unaffected: the sandbox never grounds, and library ingest at promotion re-extracts from whichever canonical file the version carries. The change adds a **real infrastructure dependency** for the first time in this family of slices — hosting the dev-harness engine and, later, operating within CSPP — which lands on ADR-0037 and the open infra/security decision session. Desktop co-authoring is a later CSPP milestone; Office-for-the-web co-authoring is the first target (mirroring NetDocuments, whose desktop co-authoring is still "coming soon"). Builds on ADR-0024, 0032, 0034, 0036, 0037, 0039, 0041.

**Considered and not taken.** *Infora as a view over the customer's (or Infora's own) SharePoint via Microsoft Graph* — rejected: per-organisation SharePoint tenancy collides with the cross-organisation project + ethical wall; SharePoint ACLs are coarser than `sandbox_scope_grants`; it is Microsoft-only and cedes control of the wall. Retained only as an optional import/export connector (decision 1). *A self-hosted engine (Collabora/OnlyOffice) as the shipping surface* — rejected by the owner in favour of real-Office fidelity; kept solely as the dev harness (decision 3). *Building an Office-compatible OT/merge engine in-house* — off the table: the merge engine lives inside the Office apps and is not exposed.

**Open — not decided here.** The precise CSPP program tier, its licensing and cost model, and guest/external-user co-authoring licensing are commercial open items for the application. **Desktop** (vs web) co-authoring timing is a later CSPP milestone. The **Infora agent as an Office Add-in** (the task-pane surface that grounds against the library from inside Office) is Slice A3 P4 and converges with the already-planned **Slice B — the Word add-in** (component 8); its design is not settled here. **Google Workspace parity** (a parallel Drive/Docs integration for non-M365 shops) is not designed here.
