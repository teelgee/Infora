# ADR-0035 - Non-review transmittal issues a library deliverable to an organisation and carries an organisation-level acknowledgement gate that withholds visibility and grounding until accepted; deliverable visibility gains optional intra-organisation per-participant narrowing under the org share

**Status:** Accepted (2026-07-20; built and tested T-134–T-138). Refines ADR-0010 and ADR-0016. References ADR-0011, ADR-0014, ADR-0015, ADR-0022, ADR-0024, ADR-0028, ADR-0033.

**Open forks ruled on acceptance (owner, 2026-07-20).** The standing routing rule ships in the MVP (§3), not deferred. A newly admitted organisation defaults to **controller** acknowledgement mode, with the org admin as the fallback acknowledger so an organisation with no controller nominated is never locked out. The acknowledgement gate is **re-triggered per version**: the acknowledgement record keys on the version, and the gate everywhere reads the deliverable's *current* version — a citation to a superseded version still resolves whenever the organisation is currently entitled. Transmittal stays **one table with a `kind` discriminator** (`review` | `non_review`), a CHECK keeping `round_id`/`direction` null for the non-review kind so no edit-lock path can attach.

**Context:** Two decisions never met. ADR-0010 made a transmittal an audited event record, but only inside the review cycle: it flips the DRR edit lock, freezes the internal snapshot, and reveals the closed round to the consultant (ADR-0014, ADR-0009). ADR-0016 made library visibility per organisation, default-deny, opened only by a deliberate owner share. So issuing a promoted library deliverable to an organisation outside a review cycle was a bare visibility flip: no issue event, no receipt, and no way to record that a receiving party had formally accepted the document before working from it.

Two needs surfaced from a concrete three-party project. First, a receiving organisation may need only certain of its own users to see a shared deliverable — the geotechnical team on a geotechnical deliverable, not the whole firm — and ADR-0016's per-organisation floor cannot express intra-organisation differentiation. Second, issuing a deliverable outside a cycle needs the same audit discipline as a review transmittal, and some parties (ISO 19650 practice, certain client contracts) require a recorded acceptance of receipt before access.

The old world does both jobs with document controllers: the sender's controller transmits, the receiver's controller receives and redistributes to the users who need it. Two gates — cross-organisation release and intra-organisation distribution — fused into manual, per-document human work that scales with document volume, which is why the role is an army. The aim here is to serve both needs while dissolving that work rather than relocating it, without changing the owner's frictionless path and without any organisation's confidential differentiation leaking across the wall.

**Decision:**

**1. Transmittal has two kinds; only the review kind touches the cycle.** A **review transmittal** is the existing event (ADR-0010, ADR-0014): it issues a version into its review round, flips the DRR edit lock, and freezes the snapshot. A **non-review transmittal** issues a promoted library deliverable to an organisation and carries none of that — no edit lock, no DRR snapshot, no round. It is the audited realisation of ADR-0016's owner share, now a first-class event rather than a silent visibility flip. Both kinds carry the same audit facts — sender, recipients, deliverable and version, purpose code, issue date — and differ only in consequence. The non-review kind never reaches a review cycle, so no edit-lock semantics may attach to it.

**2. The owner remains the sole issuer of the cross-organisation gate.** Only the project owner issues a non-review transmittal, and issuing it sets the receiving organisation's ceiling on that deliverable, exactly as the ADR-0016 share did. The owner's behaviour does not change: the owner issues, and every entitled recipient is reachable from that one act. The owner never reaches inside a receiving organisation to name individuals (see §3). An organisation that authored a deliverable, and the owner organisation, see it without any transmittal and without any gate — the gate lives only on the receiving side of a non-review transmittal.

**3. Intra-organisation narrowing is optional, default-open, and the receiving organisation's business.** Under the organisation-level ceiling set in §2, deliverable visibility may narrow to named Participants of the receiving organisation. With no per-participant grant present, every entitled Participant of that organisation sees the deliverable — this is the default and it is precisely the owner's "everyone in the firm sees everything made available", requiring no action from anyone. Where a per-participant grant is present, visibility narrows to the granted Participants only. The receiving organisation's **org admin** (ADR-0033) — or, in controller mode, its nominated document controller (see §4) — holds this narrowing, never the project owner. The owner opens the seat by issuing the transmittal; the receiving organisation staffs it, the same division of labour as appointments (ADR-0017, ADR-0033). Grants may be set by hand or driven by a standing rule keyed on the deliverable's coded reference (a discipline or team mapped to a code pattern), so that when a matching deliverable is transmitted the right Participants are granted automatically and routing needs no per-document act.

**4. An organisation-level acknowledgement gate is inherent to every non-review transmittal.** Before the deliverable becomes visible or groundable to anyone in the receiving organisation, the transmittal must be acknowledged once on that organisation's behalf. The acknowledgement is a single low-effort accept action, recorded as an audited row: who acknowledged, for which organisation, which deliverable and version, and when. One acknowledgement clears the gate for every entitled Participant of that organisation — it is organisation-level in effect, not per person.

Who may fire it is a per-organisation configuration with two modes. In **controller mode**, a nominated Participant — the receiving organisation's document controller — is the only one who may acknowledge; the controller accepts receipt on the organisation's behalf and then defines the intra-organisation narrowing of §3, so receipt precedes distribution, the ISO 19650 receiving pattern. In **open mode** (no controller nominated), any entitled Participant may acknowledge; the first to do so accepts on the organisation's behalf and opens the deliverable to themselves and every other entitled Participant of that organisation at once. The two modes differ only in who is permitted to fire the one organisation-level acknowledgement; its effect is identical.

The acknowledgement (§4) and the narrowing (§3) are **independent conditions**: a Participant sees the deliverable only when the organisation has acknowledged *and* the Participant is within any narrowing present. The controller's receipt-then-distribute sequence is therefore a workflow, not a storage-ordering constraint, and the resolution predicate stays an order-independent conjunction.

**5. The gate and the narrowing are enforced at retrieval, not only at the surface.** Because the project library is the grounded corpus for chat and drafting (ADR-0011, ADR-0022), a Participant of an organisation that has not acknowledged, or a Participant outside the narrowing, must be unable to ground on the deliverable, not merely unable to open it in the UI. Both conditions are expressed as pre-filters inside the one retrieval query (`deliverableVisible`), never as a post-filter over fetched rows: the acknowledgement clause at **organisation grain** (has the receiving organisation acknowledged this deliverable, by whichever Participant), the narrowing clause at **participant grain** (is this Participant within any grants present). Until the organisation has acknowledged, no Participant of it retrieves the deliverable's chunks. Because retrieval for agents routes through the same gateway (ADR-0028), the gate holds for agent execution by construction. Because vectors and access are co-located in one store (ADR-0024), an acknowledgement, a grant and a revocation take effect in the same transaction as the read, so there is no stale-cache window in which a withheld deliverable could be seen.

**6. The deliverable's access object is modelled per-participant-capable from the first migration, defaulting to whole-organisation.** Even where the MVP populates only the whole-organisation default and the always-on acknowledgement gate, the schema carries the per-participant grant dimension and the organisation-level acknowledgement record from the first migration. This follows ADR-0028's rule that an extensible shape must be fixed in the first migration because the store cannot be restructured later; switching intra-organisation narrowing on becomes a configuration change rather than a migration against the most load-bearing table.

**Consequences:** Transmittal becomes a general issue-event with two kinds, and ADR-0010's and ADR-0014's edit-lock and snapshot semantics are confined to the review kind. ADR-0016's owner share is realised as the non-review transmittal — the same owner authority, now a first-class audited event with a receipt on the far side.

The document controller's two jobs are dissolved rather than relocated: distribution routing becomes a standing rule keyed on the deliverable code, and receipt becomes a one-click organisation-level acknowledgement — fired by a nominated controller in controller mode, or by any entitled user in open mode. The role's headcount, not the audit discipline, is what goes away; an organisation that wants a single accountable receipt keeps one by nominating a controller.

The cross-organisation audit story is intact and wall-contained. "Who can see what across organisations" still reduces to the owner's transmittals; the intra-organisation narrowing and the acknowledgement add a trail that never crosses an organisation boundary and is owned by the receiving organisation, which is the correct place for it. The confidentiality question this must always answer — *why could a competing organisation see this deliverable?* — is unchanged, and is answerable directly from the record. The risk it guards against is concrete: competing consultants routinely coexist on one project behind the ethical wall — owner Org A engages both Org B and Org C on adjacent packages. If Org C could read or ground on Org B's commercially sensitive deliverable (a cost estimate, or a design embodying Org B's proprietary method) without Org A having deliberately shared it, Org B's confidential position leaks straight to a direct competitor — a breach of the wall with commercial and professional-liability consequences, and a defection risk to the platform's core promise. Because every cross-organisation disclosure reduces to a single deliberate owner transmittal, an alleged breach is answered from the audit: the record shows exactly what the owner shared and with whom, and the absence of such a record is itself evidence that no disclosure occurred. Because the acknowledgement is organisation-level, the trail records the accepting Participant and the entitled set (via the narrowing grants), which is the organisational-custody record document control actually needs; per-reader open-tracking, if ever wanted, is a separate read-logging concern, not this gate.

The cost is deliberate and bounded. `deliverableVisible` gains two clauses; the deliverable stops being a purely per-organisation access object and becomes per-person-capable; a new acknowledgement event, a per-organisation acknowledgement-mode setting, and an optional standing-rule mechanism enter the model. This spends some of ADR-0016's per-organisation simplicity on purpose, and the spend is contained within the receiving organisation.

Builds on ADR-0010, ADR-0011, ADR-0014, ADR-0015, ADR-0016, ADR-0022, ADR-0024, ADR-0028 and ADR-0033.

**Considered and not taken.** *Per-recipient acknowledgement* — each entitled Participant clearing their own gate before access — was considered for the individual-liability trail it would give. Rejected: receipt of a transmittal is an organisational act in document-control practice (ISO 19650), so organisation-level acknowledgement is the faithful model; it also keeps the acknowledgement clause at organisation grain in `deliverableVisible`, colocated with the existing per-organisation visibility checks, rather than forcing a participant-grain join onto the gate.

**Open items to confirm on acceptance.**

- **Standing routing rule scope.** Drafted as part of the decision, since rule-driven granting is what removes the controller rather than relocating the act. If deferred, the MVP ships manual per-participant grants only (and, in controller mode, the controller sets them by hand) and the code-keyed rule becomes a later refinement; the migration shape in §6 is unaffected either way.
- **Acknowledgement-mode default.** Each organisation chooses controller or open mode; the platform default for a newly admitted organisation (controller vs open) is a small configuration decision left to project setup, not fixed here.
- **Personal-sandbox / org-admin reach.** Untouched here but adjacent: whether an org admin can reach a user's personal sandbox remains the open item on the grill tracker and is not decided by this ADR.
